# P10-11 — Deduplicated MTGO production failure issues

## Scope and impact map

P10-11 changes only the MTGO production workflow failure boundary. The changed
contract is a post-pipeline notification, so impact discovery covers
`.github/workflows/update.yml`, its static contract tests, production-operation
documentation, decisions, roadmap, and status. It does not affect source
collectors, generators, candidate validation, Schemas, generated data, Pages,
or either front end.

## Notification contract

1. The `notify` job waits for `fetch`, `build`, and `publish`, and runs only
   when one of those job results is `failure` on `master`.
2. It selects the first failed stage in pipeline order. A downstream `skipped`
   result is not treated as an independent failure.
3. The job has only `issues: write`, performs no checkout, and has no
   repository-content or publication permission.
4. A stable marker identifies one open ordinary issue per stage. The job creates
   it when absent or appends a later run link when it already exists.
5. The issue text contains only a controlled stage, commit SHA, and workflow
   URL. It excludes fetched data, source response fields, raw errors, request
   details, and credentials.
6. Success, cancellation, and a deliberately closed prior issue do not produce
   duplicate or automatic reopening behavior.

## Protected scope

No live production workflow was dispatched and no issue was created during
local development. No generated data, statistics, source selection, privacy
boundary, public URL, front-end file, Pages setting, storage provider, or
repository-content permission changes. Remote publication and the future
automatic issue side effect remain separate owner decisions after local
acceptance.

## Required validation

The workflow contract tests must prove the exact `notify` dependency, failure
condition, no-checkout boundary, issue-only permission, stage markers, open
issue lookup, create-or-comment behavior, and absence of raw-error/token
interpolation. Final local acceptance also requires the complete Python suite,
repository validation, rule validation, public Schema validation, a clean diff,
and an unchanged generated-data tree.
