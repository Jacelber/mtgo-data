# P10-12 — Format-dynamic Melee whitelist operations

## Scope and impact map

P10-12 changes the manual Melee workflow's source-format boundary. Its
consumers are the workflow, the strict whitelist registry, workflow-contract
tests, operational documentation, architecture, decisions, roadmap, and
status. The registry already validates event identity, supported format,
enabled state, and verified review state, so this task reuses it rather than
adding a second configuration parser.

No whitelist entry, source collector, schema, generator, statistics formula,
generated data, public path, or front-end file changes.

## Contract

1. The operator supplies only an event ID through the existing manual dispatch.
2. Before a candidate baseline, retained-snapshot lookup, or source request,
   the workflow resolves that ID through `require_fetchable`.
3. The derived configured format becomes the only later `FORMAT` value.
4. A malformed, unknown, disabled, unverified, unsupported, or ruleless entry
   fails before source access and has no fallback to Modern.
5. The existing review branch remains the only possible remote write; the
   workflow does not push `master`, create a pull request, or merge.

## Required validation

Run the focused workflow and whitelist tests, YAML parsing, full Python suite,
repository validation, rule validation, public Schema validation, and a scope
check proving that no whitelist, raw, generated, or front-end path changed.

## Stop point

P10-12 stops after local validation for owner acceptance. Commit, push, pull
request, merge, whitelist modification, event activation, live source access,
and manual workflow dispatch remain separately owner-controlled.
