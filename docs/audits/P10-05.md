## GitHub platform constraints

GitHub's current sensitive-data-removal guidance states that force-pushing a
rewritten repository does not remove copies in other clones or forks, cached
views, or pull-request refs. GitHub marks `refs/pull/*` read-only. Removing
those refs and cached views requires a GitHub Support request after all other
reachable refs and forks have been cleaned, and Support decides whether the
material qualifies for that process.

The same guidance warns that a rewrite can break closed PR diffs, invalidate
review context, remove commit and tag signatures, conflict with branch
protection, and allow one unclean clone merge to reintroduce the old history.
The authoritative external procedure is:

`https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository`

## Compatibility and sequencing consequence

A history-only rewrite would not reduce current exposure while the same files
remain in master and Pages. Removing them from the current tree would change
bytes frozen by the P10-02 event `434455` compatibility manifest and requires
a separately approved compatibility migration. It also requires a selected
replacement for the current raw-archive location.

Therefore P10-05 preparation must not execute a rewrite. The preferred order
is:

1. prove an independent backup and restoration now;
2. record the owner decision to defer, reject, or later execute a rewrite;
3. complete the P10-06 storage/deployment selection and any separately
   authorized P10-07 migration;
4. reassess whether a history rewrite has meaningful benefit after the active
   public path and compatibility contract have an approved successor.
