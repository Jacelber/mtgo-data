# P10-03 audit — Future-event privacy snapshot v3

## Purpose and boundary

P10-03 changes only the complete-event collection and retention path used by
future approved Melee snapshots. A source response is held in bounded memory,
parsed, reduced to a resource allowlist, and only then written as canonical
JSON. The retained mixed-event snapshot for event `434455` remains manifest
`2.0.0` and is not fetched, regenerated, rewritten, or modified.

The owner authorized local implementation on 2026-08-01 and selected these
policies:

- keep the source-published tournament `DisplayName` for future events;
- remove unused account, profile, preference, duplicated identity, and deck
  metadata fields before persistence;
- replace raw participant IDs with event-scoped HMAC-SHA256 references;
- do not provision a real key, change a workflow, run a live fetch, retain new
  production data, or publish within P10-03.

After the documented local checks passed, the owner accepted P10-03 and
separately authorized commit, push, pull request creation, and merge on
2026-08-01. Production dispatch and secret provisioning remain unauthorized.

## Persistence allowlists

The minimized resource document version is `1.0.0`. Unknown or additional
source fields are discarded because persistence is constructed only from the
following parsed values.

| Resource | Persisted source content |
| --- | --- |
| Tournament | event ID, source-published event name, available source dates, completed round IDs, labels, and numbers |
| Standings | page total; standing ID; event-scoped participant reference; `DisplayName`; rank; match points; record and status text; decklist ID, owner reference, and approved source URL |
| Matches | page total; match and round IDs; event-scoped competitor references; result/status text; outcome and match points; table number |
| Decklist | decklist ID; event-scoped owner reference; format text; card name, quantity, and normalized source section |

The conversion does not persist source player IDs, duplicate team IDs,
`DisplayNameLastFirst`, `Username`, `ScreenName`, `PronounsDescription`,
`LanguageDescription`, `ProfileImageVersion`, duplicated match player names,
`DecklistName`, `LinkToCards`, duplicate `Components`, or unused card set,
collector, language, and treatment metadata.

Manifest `3.0.0` retains only reviewed request and integrity context. Each row
records the request identity, resource/page/path, selected response headers,
status and attempt count, request-body digest where applicable, round or
decklist context, optional HMAC participant reference, and both:

- `source_sha256` / `source_bytes` for the transient source response; and
- `sha256` / `bytes` for the minimized JSON actually persisted.

The source response itself is never written by the v3 complete collector.
Incomplete checkpoints use the same response-row allowlist and contain no raw
participant ID or key material.

## Participant reference contract

The identity scheme is `hmac-sha256-event-v1`. For a reviewed secret key, the
digest input is:

```text
melee\0v3\0<event_id>\0participant\0<source_participant_id>
```

The persisted value is `melee-v3-` followed by the lowercase 64-character
HMAC-SHA256 digest. This makes one participant stable and joinable within one
event while changing the value across events. It also prevents enumeration of
small numeric source IDs by anyone who does not hold the secret.

The secret must contain at least 32 bytes. It is supplied to the command as
base64 through `MELEE_PARTICIPANT_HMAC_KEY_BASE64`; the non-secret rotation
label is supplied through `MELEE_PARTICIPANT_HMAC_KEY_ID`. The manifest and
checkpoint record only the key ID. A missing, malformed, or short key fails
before transport or archive side effects. A checkpoint created under another
key ID also fails before resume. Operators must never reuse one key ID for
different key material.

P10-03 defines the interface but does not create, store, upload, rotate, or
authorize a production secret. Workflow secret provisioning remains a
separate owner-gated operation.

## Compatibility and downstream behavior

The parser and retention path accept immutable v2 and v3 complete snapshots;
fixture-only v1 parsing remains supported. v3 source-level records carry the
HMAC reference in the existing join positions, and normalized participant
`id` and `source_id` use that reference. Names and all statistical semantics
remain unchanged.

The P10-02 compatibility test continues to verify the exact event `434455`
snapshot closure, normalized input, derived inputs, five public documents, and
selected catalog projections. P10-03 changes no production data, statistic,
public path, front end, whitelist, or workflow.

## Deliberate limitations and next gate

Keeping `DisplayName` means participant names remain public and can still be
recognized independently of the HMAC reference. This is the explicit owner
policy for the current product, not an anonymity claim.

P10-04 remains responsible for promoting resource Schemas to the primary
production-data gate, adding scoped prohibited-field scans as supplemental
defense, and updating the public notice, contact, and removal procedure. No
P10-04 work, live collection, key provisioning, remote publication, or history
rewrite is authorized by P10-03 local completion.
