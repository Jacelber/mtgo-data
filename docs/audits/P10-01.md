# P10-01 audit — Data classification and privacy boundary

## Purpose

P10-01 inventories the identity, account, preference, provenance, and public
event-name fields retained for the canonical Tabletop reference event. It
classifies the current data by resource and traces the fields that reach
normalized, derived, and public outputs.

This is a documentation-only audit. It does not define a future persistence
allowlist, change the existing public-name contract, migrate the legacy
snapshot, rewrite history, select storage, or alter production behavior.

## Classification vocabulary

| Class | Meaning in this audit |
| --- | --- |
| Public event metadata | Public tournament identity, dates, format, round labels, or source URL used to identify and present the event. |
| Current public participant identity | A source-published tournament name that the current statistics specification and `decks.json` intentionally expose. This describes current compatibility, not approval for future events. |
| Source linkage ID | A source event, standing, participant, team, round, match, or decklist identifier used to join or reconcile records. It may still be personal data when it links back to a person. |
| Statistical event content | Standings, results, deck cards, phases, formats, and other tournament facts used by the approved product. |
| Provenance and checkpoint data | Request identity, URL, page, digest, byte count, status, timing, and local path used for integrity, reproducibility, retry, or deduplication. |
| Platform account field | A Melee account or profile handle that is distinct from the tournament display name. |
| Profile or preference field | A profile image version, pronoun, language, or similar user preference supplied by the platform response. |
| User-supplied deck metadata | A decklist title, link, or other deck metadata that is not a participant account field and is not required to represent the card list itself. |
| Authentication or secret data | Cookies, authorization tokens, credentials, private request headers, or browser-session state. None is recorded by the manifest contract or observed in the scoped retained responses. |
| Owner decision required | A current behavior or future policy that P10-01 must describe but cannot approve or change. |

Public source availability is not the same as necessity, privacy minimization,
or permission for indefinite republication.

## Participant pseudonym threat assessment

The assembler derives IDs as:

```text
kind + "-" + SHA256("melee\0" + event_id + "\0" + kind + "\0" + source_id)
```

For participants, `kind` is `participant`. The event ID, kind, algorithm, and
implementation are public, and no secret or random salt is involved. A party
that knows or guesses a source participant ID can recompute the corresponding
normalized and public participant ID. The current manifest also publishes the
source participant ID for all 362 decklist responses.

The derived ID therefore provides deterministic pseudonymous linkage and
namespace separation. It does not provide irreversible anonymization or
resistance to enumeration. P10-03 must use an owner-approved secret or mapping
management contract for future events; selecting that contract is outside this
audit.

## Findings

1. The retained public responses contain substantially more platform account,
   profile, preference, and duplicate identity data than the current parser or
   statistical product consumes.
2. Match pagination is the main source of duplication: 4,578 of the 4,940
   occurrences of each reviewed player-object field are in match responses.
3. The current public-name contract is distinct from the unused account and
   profile fields. A privacy change must not silently remove the former while
   trying to eliminate the latter.
4. Source IDs are needed by the current join and provenance model, but their
   direct publication and deterministic unsalted derivative make participant
   records linkable.
5. The raw archive is currently both repository-public and Pages-public. A
   future persistence allowlist alone will not remove the legacy snapshot from
   existing publication or history.
6. Event `434455` remains the v2 compatibility baseline. Applying a future v3
   minimizer and recomputing hashes would change its reproducibility chain and
   is prohibited without a separately approved version migration.
7. A repository-wide prohibited-field zero-result cannot be the privacy gate:
   documentation, Schemas, and rejection fixtures must be allowed to name
   prohibited fields. P10-04 must use resource-specific Schemas and allowlists
   for production paths, with scoped scans only as supplemental evidence.
8. No cookie, credential, authorization token, private request header, or
   browser-session field is recorded by the manifest contract or observed in
   the scoped retained responses. This is a snapshot-scoped finding, not a
   guarantee about every repository file or future source response.

## Validation method

The inventory was generated read-only from the manifest-declared snapshot,
not from an unrestricted repository grep:

- verified exact manifest/file coverage and 483 declared responses;
- counted generalized JSON field paths separately for standings, matches, and
  decklists without printing values;
- inspected only parser and assembler consumers needed to trace the fields;
- counted identity fields in normalized, classification, opportunity, and
  public event documents without printing values;
- compared the handoff hash list with current master;
- used anonymous `HEAD` requests for two exact raw Pages paths;
- confirmed the task changes no data, Schema, code, workflow, or public file.

## Conclusion

P10-01 establishes the current classification and exposure boundary without
changing it. The repository has a reproducible and well-linked Tabletop event
chain, but its retained and directly served raw responses include unused
account, identity-variant, profile, and preference fields. The current
participant hash is deterministic pseudonymization, and the public-name
contract remains a separate owner-controlled compatibility decision.

Implementation must stop here. P10-02, privacy filtering, legacy migration,
storage changes, history rewriting, and production dispatch remain separately
controlled.
