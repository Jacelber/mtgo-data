# P9-07 audit — Bounded real-source pilots

## Purpose

P9-07 tests whether the existing Melee source contract can recognize one
owner-approved Standard event for each supported event structure before any
event is admitted to production.

The task also measures the request scale that a complete immutable archive
would require. It does not implement the subsequent large-event collector.

## Authorization and boundary

The owner authorized P9-07 on 2026-07-30 and selected:

- `415628` for `mixed`;
- `425324` for `constructed_single_stage`;
- `419742` for `constructed_day2`.

The probe used anonymous public `melee.gg` requests with the repository's
existing request headers. It read:

- one tournament page per event;
- all pages of the final completed Swiss standings;
- the first result page for each completed round, solely to read
  `recordsTotal`.

It did not:

- reuse cookies, credentials, or a browser session;
- fetch any complete decklist body;
- retain source HTML or JSON;
- record player names or source player IDs;
- add an event to `configs/melee_events.yaml`;
- write under `data_raw/`, `data/`, `stats/`, or `reports/`;
- dispatch a workflow or publish production data.

Only aggregate counts printed to the task terminal are recorded below.

## Large-event finding

The current collector defines:

```text
MAX_EVENT_DECKLISTS = 500
MAX_ARCHIVE_RESPONSES = 500
```

Events `415628` and `425324` remain under both limits. Event `419742` exposes
893 decklists and needs an estimated 1,085 successful responses, so raising
only one constant would not solve the problem.

Future events may exceed 2,000 players. Treating that as a Phase 11 concern
would be incorrect: Phase 11 combines already valid event-level raw counts,
whereas this is a prerequisite for producing one complete event archive.
