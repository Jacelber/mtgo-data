## Current platform constraints

The following official documentation was checked on 2026-08-01:

- GitHub supports custom Pages workflows that upload a selected static
  artifact and deploy it in a separate job. The deploy job needs only
  `pages: write` and `id-token: write`, while checkout can remain
  `contents: read`:
  `https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages`.
- A published Pages site may not exceed 1 GB, and a Pages source repository
  has a recommended 1 GB limit:
  `https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits`.
- Normal GitHub Actions artifacts are temporary transport. Public-repository
  artifact retention is one to 90 days and defaults to 90 days, so they are
  not a durable raw archive:
  `https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization`.
- GitHub Actions OIDC can exchange workflow identity for short-lived cloud
  credentials without storing long-lived cloud access keys:
  `https://docs.github.com/en/actions/concepts/security/openid-connect`.
- A versioned object store can retain prior object versions after overwrite or
  deletion. Amazon S3 documents this reference behavior at
  `https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html`.
- Object Lock is an optional write-once-read-many control that requires
  versioning and can protect selected versions from overwrite or deletion:
  `https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html`.

These references establish capability categories, not an approved vendor,
account, price, region, retention period, or credential configuration.

## Options considered

| Option | Archive | Pages/public delivery | Strengths | Weaknesses | Disposition |
| --- | --- | --- | --- | --- | --- |
| A. Keep the current branch-root design | Public Git history | Managed branch-root Pages build | No migration or new service | Every repository-root path remains an implicit Pages candidate; storage and deployment permissions stay mixed | Do not retain unchanged |
| A+. Keep public Git storage and add a Pages artifact boundary | Current public Git repository and history | Custom allowlisted Pages artifact | No provider, account, fee, cloud credential, or data migration; compatible with the current static product and j6e evidence | Data remains public, Git history continues to grow, and the current combined production job remains until P10-09 | **Selected by the owner** |
| B. Owner-local archive only | ACL-controlled local files | Custom Pages artifact | Low external exposure and already proven for backup | Cannot support unattended production, shared recovery, or runner access; one machine is not the production archive | Retain only as independent backup |
| C. Private sibling Git repository | Private Git history | Custom Pages artifact | Familiar review and recovery model; lower initial implementation novelty | Git remains the data store, every update grows history, cross-repository write credentials are required, and generated-data publication still needs a separate mechanism | Acceptable only as an explicitly temporary bridge |
| D. Private versioned object storage | Private immutable objects and manifests | Custom allowlisted Pages artifact | Independent retention, lifecycle controls, and no Git data growth | Adds a provider, account, fee, credentials, recovery procedures, and migration without a demonstrated current need | Deferred unless measured evidence later justifies it |

GitHub Actions artifacts are deliberately absent as a primary archive option.
They are suitable for immutable transfer between fetch, build, and deploy jobs,
but their bounded retention makes them insufficient as the authoritative raw
archive. Public GitHub Releases are also not a privacy boundary for a public
repository.

## Selected A+ target architecture

P10-06 records option A+ as the owner-selected target:

```text
approved sources + reviewed code commit
                 |
                 v
       fetch / minimize / validate
                 |
                 v
     current public Git repository
       as the durable data record
                 |
                 v
          build and validate
                 |
                 v
    fresh allowlisted Pages artifact
                 |
                 v
       protected Pages deployment
```

The current public repository remains authoritative for code, tests, Schemas,
reviewed configuration, governance documents, retained source evidence,
normalized inputs, and generated data. Future Melee v3 responses continue to
be minimized through the accepted per-resource allowlists before persistence.
No storage provider, private archive, cloud account, cloud fee, object-store
credential, or storage migration is introduced.

The Pages artifact is assembled into a fresh empty directory from an explicit
allowlist. Its initial compatibility closure must include every approved
user-facing and compatibility path required by the current products, including
the protected event `434455` closure. Existing `data/**`, `reports/**`, and
`data_raw/**` files enter the artifact only when explicitly selected. Absence
from the allowlist is a deletion and must fail validation unless the owner
approved the matching compatibility migration.

## Credential and permission model

The selected design introduces no external storage credential. The future
Pages build needs repository read access, while the Pages deploy job needs
only `pages: write` and `id-token: write` plus the protected `github-pages`
environment. The current production job retains repository write access until
P10-09 separately splits fetch, build, commit, and publish responsibilities.
P10-07 must not broaden that token or give the Pages deploy job repository
write access.
