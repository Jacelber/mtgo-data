# P7-07 audit — Public packaging and manual Melee workflow

Date: 2026-07-25

Status: local implementation completed; owner acceptance and remote
publication are pending.

## Purpose

Turn the completed Modern reference-event statistics into a discoverable,
Schema-governed Tabletop Major Events backend and provide a source-separated,
review-branch-only production workflow for later P7-08 execution.

## Frozen boundaries

P7-07:

- rebuilds and byte-compares the existing overview, decks, matchup, and
  quality documents before packaging;
- generates deterministic event metadata and one Modern Melee catalog;
- adds all six event/catalog documents to the public Schema manifest;
- validates that a production candidate cannot delete data, mutate retained
  raw evidence, cross an event or format, or write MTGO paths;
- adds a manual-only workflow that may push only
  `data/melee-<event_id>` for review.

P7-07 does not change a statistic, taxonomy rule, retained event, MTGO output,
MTGO workflow, or front end. It performs no live source request, workflow
dispatch, push, PR, merge, phase closeout, or tag.

## Public contract

The manifest profile is now `public-generated-json`, covering both MTGO and
Tabletop Major Events. It validates 52 documents: the previous 46 plus the
four event payloads, event metadata, and Modern Melee catalog. Two new
versioned Schemas govern metadata and catalog shape.

The catalog contains exactly enabled, verified event `434455`, uses
`all_constructed` as its default scope, and points to all five event files.
No wall-clock, branch, checkout-depth, or Git-history value enters either
generated document.

## Candidate and workflow safety

`validate_melee_candidate.py` permits only:

- new immutable raw evidence under the selected event;
- that event's normalized event, classification overlay, and opportunity
  ledger;
- its overview, decks, matchup, quality, and metadata;
- the selected format's Melee catalog.

The workflow:

- has only `workflow_dispatch`;
- requires an event ID and relies on the existing enabled/verified whitelist
  gate;
- reuses the immutable snapshot recorded by an existing canonical event and
  fetches only when canonical input does not exist;
- uses event-specific concurrency and `contents: write`;
- runs clean-checkout tests before any fetch;
- runs the full source-to-publication sequence;
- validates candidate scope, repository, rules, and Schemas before staging;
- stages only selected Melee paths;
- may push only `data/melee-<event_id>`;
- cannot push `master`, create a PR, merge, or run on a schedule.
