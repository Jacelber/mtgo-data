## Problem

P13-01 can aggregate compatible in-memory event documents, but its reference
result has no Schema, per-input path or digest provenance, or proof that every
selected event appears in the active catalog. The current catalog Schema
`1.0.0` supports single-event discovery and cannot safely authorize a
multi-event consumer.

## Solution

Add a version `1.0.0` in-memory result Schema and a small wrapper around the
unchanged P13-01 core. The wrapper requires catalog Schema `1.1.0`, active
membership for every selected ID, and a versioned compatibility block whose
source, product, format, scope, matchup Schema/hash, taxonomy Schema/hash, and
quality state reconcile with the validated input documents.

Active JSON Schema validation of the loaded catalog, metadata, and matchup
documents remains the caller's first gate. The wrapper owns the semantic
cross-document reconciliation that JSON Schema cannot express by itself.

Advance only the future catalog producer to `1.1.0`. The event catalog Schema
continues to accept legacy `1.0.0` catalogs without the new block, preserving
the current production file for single-event use. Every `1.1.0` entry requires
the block. No public JSON is regenerated or edited in this task.

The in-memory result is not mapped in `schemas/manifest.json`: there is no
generated file to discover or validate. Schema discovery still validates the
new Schema itself. A later task that persists combined results must separately
define the public path and manifest behavior.

## Stable contract failures

`MultiEventContractError.code` is restricted to:

- `catalog_compatibility_mismatch`;
- `catalog_event_missing`;
- `catalog_identity_mismatch`;
- `duplicate_catalog_event`;
- `invalid_contract_input`;
- `missing_catalog_compatibility`;
- `provenance_mismatch`; and
- `unsupported_catalog_schema`.

P13-01's accepted aggregation errors remain unchanged and propagate when the
raw input subject itself is invalid.

## Synthetic acceptance subjects

`tests/test_melee_multi_event_contract.py` proves:

1. two admitted synthetic events produce a sorted, versioned result that
   validates against the new Schema;
2. the raw-count aggregate still differs from averaging event rates;
3. catalog `1.0.0` remains Schema-valid for single-event discovery but is
   rejected by the multi-event wrapper;
4. catalog `1.1.0` requires compatibility evidence;
5. source, product, format, scope, matchup Schema/hash, taxonomy Schema/hash,
   and quality mismatches fail closed;
6. the maintained publisher derives the minimum compatibility block and
   rejects malformed provenance; and
7. missing result provenance fails Schema validation.
