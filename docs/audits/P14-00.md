## Problem

The existing Phase 14 roadmap identifies the required Pauper MTGO and
Paupergeddon outcomes, but it does not yet prove which Standard and Modern
components are already reusable for a third complete MTGO format. It also does
not separate material shared-framework work from the first use of Pauper data.
Starting classification or generation from that plan could hide a broad
generalization inside a format task, copy an existing implementation, expose a
partial public format, or let the disposable real-event trial cross a public
boundary.

P14-00 therefore freezes a reuse-first contract. It changes no code,
configuration, Schema, workflow, classifier, data, generated output, catalog,
front end, public path, or production behavior.

## Authoritative boundaries

The frozen plan preserves the following existing decisions and specifications:

- `DEC-002`: MTGO and Melee share format-specific archetype identities and
  reusable classification logic, while ingestion and statistics stay separate;
- `DEC-005`: only an approved Paupergeddon main event is in the supported
  tabletop event category;
- `DEC-006`: the event strategy is explicit, and a qualifying Paupergeddon is
  expected to use `constructed_day2` rather than inferred structure;
- `DEC-033`: MTGO archival permission is separate from complete product-format
  execution;
- `DEC-034`: Modern is the completed post-Standard reference path and Pauper is
  the next format target, not a new reference architecture;
- `DEC-132`: future multi-event Tabletop admission requires the current active
  taxonomy, not merely equal stale event projections;
- `docs/PROJECT_SCOPE.md`: a future public MTGO format requires Landing,
  statistics, matchups, and weekly Top 8 together; and
- `docs/DATA_ARCHITECTURE.md`: Landing review sources stay private, catalog
  availability is generated, and MTGO and Tabletop data flows never merge.

## Owner-approved reuse principle

Phase 14 extends the established product rather than building a Pauper-specific
copy. Every implementation task must first identify the existing producer,
contract, validator, and consumer that own its behavior.

An implementation may add Pauper-specific rules, data, and reviewed content.
It may not add a parallel Pauper statistics engine, Landing renderer, page,
catalog, workflow, or source-specific archetype taxonomy merely to avoid a
shared contract. A small parameter or closed-enum extension may remain in the
directly affected task. A material shared-framework gap requires a separate
Owner-authorized subtask before Pauper input enters that layer.

Every proposed new code path must answer:

1. which current shared module was inspected;
2. why that module cannot accept Pauper through its maintained format contract;
3. whether the gap is a small extension or a material shared-framework change;
4. which existing consumers and Schemas are invalidated; and
5. which single named risk proves the repair.

## Validation routing

One risk is proven once. P14 tasks use the current
`docs/TEST_TRIGGER_MATRIX.md` and these phase-specific boundaries:

- rule changes: Pauper rules plus only directly affected shared-validator
  regressions;
- a Schema, manifest, or Schema validator change: complete declared Schema
  validation once on the final tree;
- ordinary Pauper generated JSON changes: changed-scope Schema validation;
- shared MTGO code: synthetic third-format contract plus the smallest named
  existing-format regression;
- Landing review/generalization: synthetic third-format carrier before real
  Pauper review, then exact immutable Pauper subject checks;
- UI changes: focused syntax/model checks and one final local Owner review at
  desktop, 390px, and 412px;
- workflow changes: focused workflow/governance tests and no production
  dispatch during local implementation;
- real-event trial: one collection, reused snapshot, exact quality harness, and
  complete temporary cleanup; and
- final publication: candidate tests occur before packaging; downstream checks
  only bind the publication SHA and verify the required public resources.

No task runs full pytest, unrelated format suites, generic browser suites, or
already-passed immutable checks merely because Pauper is a new format.
