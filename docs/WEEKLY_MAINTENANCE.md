# 周维护的业务审阅

本文件说明周维护需要哪些业务输入与判断。任务计划、授权和验收依
[GOVERNANCE](GOVERNANCE.md)，验证依 [QUALITY](QUALITY.md)，交付和续作依
[DELIVERY](DELIVERY.md)。下面是结果依赖，不是逐步骤启动审批。

## 介质与执行方式

本文件集中定义周维护的协作流程，包括修复任务涉及周内容时的处理。
默认使用固定模板的只读 Web 查阅、对话中选稿和写稿、实际 Landing 页面验收。
Excel 是按需导出／批量修改的替代介质，不要求将同一决定或正文再填一次。
已有表格接收能力保留；选择一种内容输入路径，不双重确认。

1. Codex 批量准备各赛制当前阶段的完整材料，一个入口按周次和赛制导航。各赛制可以
   处在不同阶段或处理不同待审周。缺失材料明确说明，不阻止其它赛制审阅。
   程序输出全量供 Owner 查看。模型可先读摘要定位问题，但提出分类判断前必须读取
   对应完整主备牌并提供下述审阅材料；模型读取策略不能缩减 Owner 的判断依据。
2. Owner 在对话中说明当前赛制，先审阅 Unknown 和完整分类。Codex 落实分类决定、
   完成受影响验证并更新派生结果后，才准备 Feature 供 Owner 选择。机器只给机械候选与
   事实理由，不默认选牌表、展示牌、类别或代写中文；只有 Owner 明确要求时才建议。
   只读页保持材料快照，不同步选稿状态，不增加实时更新或审批控件。
3. Owner 起草中文。“第一条／第二条”或编号列表各对应一个 bullet；明确要求
   同条换行时保留换行，输入中的普通换行不擅自拆条。牌表位置可以自然语言指定。
   多份牌表时 Codex 可给 F1/F2 短编号，Owner 可选用【F1】；编号在当前周次、
   赛制内稳定，删掉某份不复用编号。跨赛制引用带赛制名，歧义只澄清相关位置。
4. Codex 只整理新选择和修改，核对数字并准备英文。明确单卡名称通过共用程序
   转为链接与卡图交互，不要求 Owner 写 URL 或内部标记；简称、重名和英文普通词
   不盲目链接，只处理具体歧义。正文语气和结论由 Owner 决定。
5. 英文和显示按约定提交验收；先由 Codex 验证实际入口、资源与默认链接样式。
   预览更新使资源版本可区分，不能只在新开的浏览器里验证后让 Owner 排查缓存。
   已确认内容不因介质、赛制切换或无关修复而重复询问。

每个赛制独立接纳内容和完成。未决定、明确不选 Feature、明确不写正文分别处理；
不得由缺值推断省略。未完成赛制继续保留旧的已验收 Landing。多个赛制可合并技术
交付，但不捆绑人工决定，不以一份赛制的确认扩大其它赛制范围。
赛制增长复用同一模板和处理工具；维护频率与人工审阅范围的变化由 Owner 决定。

只读入口生成命令（scope 可重复，不要求所有赛制同周）：

```text
python tools/build_weekly_review_web.py --scope standard=2026-W37 --scope modern=2026-W37 --scope pauper=2026-W37 --output <private-directory> --localization <cards.json>
```

默认只生成分类阶段材料。完成下述分类与统计依赖后，对相应赛制使用
`--include-feature` 重新生成；这只是 Codex 的技术操作，不增加一次 Owner 授权。
工具核对既有 `data_admissions` 中当前赛制、周次、赛事和分类摘要的实际接纳依据，
并通过现有消费者核对机械候选的统计摘要；缺失或过期时不提供 Feature 材料。
机器能生成候选、Unknown 数量少或某场赛事单独审过，都不代表本周完整分类已验收。

正文整理时使用 `tools/prepare_landing_copy.py --input <copy.json> --card-catalog
<cards.json> --output <private-copy.json>`。Codex 将对话正文整理为 `items`（order、
text.zh/en），可选 `feature_aliases` 仅包含当前赛制当前周的已选牌表。
工具不会设置验收或写入正式周内容。识别依赖共享双语牌名目录；未收录的新牌由
Codex 按原有本地化查询补齐后再生成，不要求 Owner 找链接。英文普通单词等歧义
返回待判断项；同一句已确认的明确牌名可转换为内部标记，避免重复询问。
已接纳内容按既有私有周文档结构导入并校验，部署仍依 DELIVERY；入口网页和诊断
材料不进入公开包。验收记录来自实际对话，不由工具成功或默认值推定。

### 从 W38 起绑定实际提交材料

`2026-W38` 起使用[提交与续作入口](operations/WEEKLY_REVIEW_SUBMISSIONS.md)。
W37 及更早已接纳分类、名称、Landing 和完成记录沿用原合同，不批量迁移或重新验收。

完整分类、中文、英文、Feature 选择、视觉资料和最终页面分别保留确认范围。
新增或修改名称分别处理两种语言；既有名称表中有效的批准继续复用。视觉材料展示
高占比套牌的指示色及两张代表牌、每个 Feature 的指示色及四张牌；明确无色允许空颜色，
但缺颜色不能当作无色。仅绑定本次实际使用的条目，无关类别变更不使已确认内容失效。

导入对话内容或 Excel 时核对实际提交的快照，不能把旧决定重新绑定到当前内容。
内容确认不代替最终页面验收；完成记录还须对应已确认发布的产品包。工具只核对
对象一致性，不能证明人已看过材料，也不能自行生成 Owner 的决定。

续作分别列出分类、数据发布、Feature、正文、视觉、最终预览和完成状态。
这些维度可独立推进或保留旧成果，不压成一个会跳过步骤的线性进度值。

## 数据输入

默认周审范围由 `configs/mtgo_weekly_review_completions.yaml` 的
`weekly_maintenance` 明确选择；本次从 `2026-W37` 推进三个赛制，
Pauper 从该周加入。已结束的 W36 不重新打开人工审阅。
`start_week` 只限定常规待审队列，不接纳此前排除的赛事，不补造完成记录，
也不改变公开数据范围。未加入的私有赛制继续使用显式 `--review-scope`。

现有 MTGO 采集仍按每日 09:00 UTC 运行；不因周维护新增定时任务。
成功保留的赛事是已有输入，不重新抓取来证明一次审阅。每个赛制分别确定最早
待审的已结束自然周、已公开周和已接纳赛事。目录增长、日期、Issue 关闭或
周维护完成标记都不能代替赛事接纳。

Owner 指定的同赛制 Melee 赛事，在来源完整、分类可复现、可用牌表可审阅时可以
补充审阅，不要求已经公开。来源、赛事、统计、公开状态和完成记录均与 MTGO 分开。
缺失牌表标为 unavailable；没有规则命中的可用牌表才是 Unknown。

缺失预期赛事或异常来源需要诊断和必要修复，按当前任务范围连续处理；不因为
技术修复另开授权阶段，也不把未知来源当作已完整取得。

## 完整分类审阅

Codex 同时提供完整分类表和机器优先提示。完整 MTGO 表包含本周每场官方赛事的
全部已公布记录，最多到第 32 名；机器没有提示的行不代表分类一定正确。
Melee 补充表包含每个可用分类，Unavailable 另列。完整分类表是记录覆盖范围，
完整牌表是每份构筑的全部主牌与备牌，两者均须提供，不能相互代替。
总览主表可保持紧凑，通过对应行直接展开完整主备牌；这只是展示方式，
不是等 Owner 追问后才提供牌表的条件。

### 提交分类判断的材料

对 Unknown、疑似误分类、新类别或类别边界提出确认时，Codex 必须同时提供：

- 每份牌表的赛制、周次、赛事 ID、排名、牌手，以及完整主牌、备牌、各牌数量和
  分区总数。牌名沿用共用中文目录，保留英文以便定位；未收录名称明确显示英文。
  缺失牌表或分区数据明确标注，不补成空备牌或随机牌堆，也不据此要求确认构筑归属。
- 当前分类、拟议分类及事实理由；规则未命中原因与需要 Owner 决定的边界分开说明。
  关键牌摘要只能帮助理解，不能代替完整主备牌。
- 对话中的编号与牌表材料逐项对应。使用 Web 时，给出可直接到达该条目或分组的
  链接，条目中可直接展开主备牌；不能只给总入口、赛事 ID 或搜索词让 Owner 自行寻找。
  若当前工具尚不能提供这种定位，先补齐材料；也可在对话中直接附上完整牌表。

按构筑归组时，必须保留组内每份牌表及其定位，包括备牌不同或主牌相近的成员。
不得用代表牌表代替其余成员的确认依据，或把代表牌表的确认扩展为全组确认。
已有有效决定无需重审；只提供本次待判断对象及必要对照，不重新打开已结束周次。

### 续作与提出确认前的核对

Codex 在续作或切换赛制时，先从当前指令和有效记录恢复赛制、周次、当前阶段及
尚待决定的事项。提出业务确认前，自行核对本次实际提交的材料：

- 阶段依赖是否满足：分类未落实或受影响统计未更新时，不请求 Feature／正文判断。
- 所有待确认编号是否均能直接查看对应完整主备牌，分组是否覆盖全部成员。
- 实际入口是否显示本次版本，牌表可展开，理由和数量是否与该份牌表一致。

这是 Codex 提交材料前的责任，不增加 Owner 检查表、填报或技术授权。
文件存在、页面能打开、程序测试通过或模型已读过牌表，都不能单独证明本次确认
请求已满足要求。不满足时先修复材料，再提出确认；不能先要求决定、后补依据。
当 Owner 指出流程偏差时，先检查同一审阅请求的阶段和材料两项要求，修复实际入口
与相关正式说明后再续作，不能仅修正最近被指出的一句话。

### 分类决定与规则维护

Owner 决定类别、子类、名称和允许的 intentional Unknown；Codex 负责查明牌表和
实现决定。`configs/mtgo_intentional_unknowns.yaml` 的既定业务含义不变：仅接受
明确记录的 random_card_pile，不以陈旧、单例、证据少或缺规则作为豁免原因。

规则维护优先简化已有条件。确需新父类或替代分支时，说明现有身份或单个分支为何
不能表达已确认构筑；数量条件取能成立的较低阈值。要求四张而非较低数量时，须有
低阈值导致身份迁移、冲突或分类丢失的具体证据。

类别内容变化按 QUALITY 的 R3 比较同一批完整同赛制 MTGO／Melee 保留牌表，
核对全部已批准迁移及未解释的分类、子类、匹配、冲突和状态变化。有效结果复用；
纯名称变化只检查名称和消费者，不机械重跑分类器。

每个待审赛制依次满足以下依赖：

- 先明确 Unknown 的归属或符合既定含义的 intentional Unknown，同时核对完整分类，
  不能仅清零 Unknown 就推定全表正确。
- 落实已确认规则和名称，完成相应影响验证；重新生成受影响分类材料，向 Owner
  说明实际变化并取得完整分类验收。已确认且未变化的决定复用，不重复逐条询问。
- 按既有机制记录实际分类接纳，更新受影响统计和机械候选，核对当前版本与范围后，
  再进入 Feature、展示牌及正文审阅。分类再次变化时暂停受影响的 Feature 判断，
  修复和重新生成对应材料；不能沿用旧占比、差异理由或候选排序。

批量准备是多个赛制各自当前阶段的批量，不是把待定分类和下游选稿同时交给 Owner。
续作先核对当前阶段及已有有效结论；已结束周次不因入口修复而重开。

```text
python tools/compare_classifier_impact.py --format <format> --accepted-rules <accepted.yaml> --candidate-rules <candidate.yaml> --expected-changes <accepted-changes.json>
python tools/export_weekly_classification_review.py mtgo --week <week> --format <format> --output <review.json>
python tools/export_weekly_classification_review.py melee --format <format> --event-id <event> --output <review.json>
```

这些命令生成或比较当前审阅对象，不能代替业务判断。私有诊断、首次名称建议和
含未接纳赛事的审阅材料留在批准的私有位置，不进入公开产品或公共 Actions 附件。
日常工作流的周审交接只上传加密附件，可读材料按 DELIVERY 单独存入现有私有归档；
Codex 从该运行摘要定位并取用，不要求 Owner 手工下载、解密或维护新的记录。
表格导入须核对完整行与实际用户选择；不能把缺值、过期表格或建议值当作验收。

## 数据、Landing 和完成是三个不同结果

完整分类验收后，`data_admissions` 记录批准的明确赛事集合，允许依当前任务发布
该赛制的数据产品。保持连续自然周与空周观察含义；后来到达但未列出的 ID 仍待接纳。
初次公开与历史公开迁移使用各自既定类型，不补造历史人工验收。

分类变化使派生结果过期时更新对应结果；不变的输入、分类结论和其他赛制成果复用。
必要时在一个候选中组合多个已确认赛制，但不能扩大其各自接纳范围。

Landing 从已确定的数据筛选。只有新增、缺失、改变或需业务选择的代表牌、颜色和
显示元数据才交 Owner 判断；已确认结果不因技术步骤变化失效。中文原文、英文内容
及最终周内容预览按当前计划中的业务验收点处理。技术可用性由 Codex 在提交验收前
确认，不能让 Owner 代查图片缺失、控件失效或明显错误数字。

新数据公开不会自动替换旧的已验收 Landing；跨周消费者保护和独立内容接纳继续成立。
只有约定的业务内容、数据交付和内容交付实际完成后，才记录该赛制周维护完成。
旧记录保持 Top-8-only 含义，新记录使用 full_official_classification_v2，绑定已审
赛事、分类主体、完整审阅摘要和 Landing 内容，不成为每行数据库或授权令牌。

Readiness、Issue 和完成记录说明现有事实。相同诊断不重复通知；新诊断更新同一
业务对象的说明，不强制重新打开已经完成且仍有效的审阅。技术查询失败只恢复查询，
不能使全部产品证明失效。当前任务结束不产生永久维护、自动监控或新赛事处理权限。
