## 两项责任澄清

1. **完整分类确认的主体是用户。** 机器负责落实修改和提供影响结果；不能把“用户只提出几条修改意见”自动解释为接受其余全部内容。用户已经确认的部分继续复用，不要求重审。
2. **数据必需信息与编辑展示选择分开。** 类别身份、颜色身份等数据依赖应在数据上线前齐备；环境栏／Feature 的代表牌等展示选择归内容阶段。某个名称或配色如果也是数据公开的必要条件，就提前处理，后面不重复确认。

## 八步主流程

| 步骤 | 做什么 | 进入下一步应达到的结果 |
| --- | --- | --- |
| **1．开启或继续维护** | 用户宣言开启或继续周维护；机器确定周次、赛制范围、本次终点和已有有效进度。 | 清楚本次处理什么，以及从哪里接续。 |
| **2．提交完整分类材料** | 机器提供明确数据范围内、当前分类器下的完整分类，列明覆盖赛事、牌表及已知缺失或来源限制。 | 用户知道自己审查的具体对象，能够按赛制判断。 |
| **3．逐赛制确定最终分类** | 用户审查并提出意见；机器落实规则和数据公开必需的配套信息，展示修改及影响结果；用户完成完整分类确认。 | 预期变更生效，非预期漂移得到处理，公开必需信息齐备；未变化的有效决定继续复用。 |
| **4．统一交付全赛制数据** | 本次已确认赛事完成接纳，新分类及对应统计实际公开，Landing 保持不变。 | 本次数据确实进入公开产品；不能只完成分类器合并，也不能只重算此前已公开的旧数据。 |
| **5．提交内容与视觉待定项** | 机器按新分类与统计提供 Feature 候选事实、环境栏资料，以及当前全部未决项目；首次说明有无从未展示的新类型。 | 用户一次获得完整选择依据；已展示且沿用的环境栏配置默认接受，其他已有有效决定复用，仅实际未决项提交选择。 |
| **6．逐赛制确定内容** | 用户提供 Feature 有无；有 Feature 时提供对象、类别、四张展示牌及逐条中文说明；Landing 中文正文必交。环境代表牌仅条件需要时提交。机器完成机械处理、英文及实际页面展示，用户确认实际未决部分。 | 必交及条件适用内容齐备；用户已明确的选择和中文定稿不重复询问；页面确认供第 7 步复用。 |
| **7．完成整体 Landing 候选与验收** | 机器复用或组合整体 Landing 候选，完成必要技术检查；默认复用第 6 步已确认的实际页面，仅将确需新判断的部分提交补充确认。 | 得到确定、可交付且已有适用确认的版本；无额外待确认项时直接进入第 8 步，不安排第二轮整页重审。纯文字确认不扩大为未展示页面的确认。 |
| **8．交付 Landing 并完成维护** | 机器发布已确认版本，确认实际发布结果，保存对应范围和对象的必要完成事实。 | 本次约定范围真正完成，可供后续续作和下一周判断使用。 |

## 贯穿八步的共同约束

### 1．审查范围不能被悄悄替换

提交并确认的赛事与牌表范围保持明确。后续收到新赛事时，作为增量按约定处理：既不偷偷并入已审对象，也不自动推翻整周结果。

沿用有效输入、核对范围完整性、重新采集是三个不同动作；前两者不自动触发第三者。

### 2．分类确认既不能缩水，也不能重复

用户对完整材料的明确确认与指定修改，共同界定最终分类。机器提供修改和影响结果，复用未变化的有效决定：

- 不能用“指定的几副牌改好了”代替完整分类确认。
- 不能在每次落实修改后，要求用户重新逐条审查整张表。

### 3．两次统一交付是结果节点，不是强制部署次数

已有结果确实覆盖本次范围且仍有效时，可以复用，不为走流程制造发布。

但“没有改分类规则”不意味着跳过数据交付：仍须确认本周赛事是否已经接纳并公开。

### 4．默认统一交付，各赛制进度分别保留

某赛制阻塞时，保留其他赛制成果，继续不依赖阻塞的授权准备。机器不得自行改为分批发布；需要改变范围或批次时，由用户决定。

### 5．内容阶段明确包含环境栏

Feature、环境栏、Landing 正文都在范围内。明确不选 Feature，只跳过本周 Feature 相关动作，不跳过环境栏或已经确定的 Landing 正文。

待定项同时检查：

- 没有配置；
- 有配置但没有适用确认；
- 已有内容实际发生变化。

已获有效确认且未变化的项目直接复用。环境栏已经展示且本次沿用的现有配置依用户默认规则视为已确认，不因缺历史验收记录列为待定；只有配置但尚未展示的对象不适用此默认规则。

### 6．机器检查与用户接受各有责任

- **机器负责**：页面加载、图片实际显示、链接与相关交互可用，以及确定的内容正确落入页面。
- **用户负责**：是否接受实际页面的内容与展示体验。
- **机器继续负责**：用户确认后，按既定范围发布并确认结果。

整体页面确认不构成重审已确认正文、英文和未变化展示项的理由。

### 7．正常执行不增加重复授权，失败不重置全部进度

在约定范围内，分类确认后的数据接纳与交付、页面确认后的发布与完成记录，按既定授权执行，不另加“是否允许上线”的审批点。

失败从受影响环节续作。PR 合并、工作流结束或会话结束，都不能单独充当周维护完成依据。

### 一、机器应该做什么

| 编号 | 预期行为 |
| --- | --- |
| **1.1 识别指令** | 区分开启维护、继续维护与查询／讨论。查询或讨论不自动启动执行。 |
| **1.2 确定周次** | 优先采用用户明确指定的周次；未指定时，从当前上下文和已有维护记录确定。无法唯一确定且影响下一动作时，才询问。 |
| **1.3 区分整批范围与当前对象** | 开启一批尚未确定范围的维护时，采用用户明确指定的整批赛制范围；未指定时采用已经明确建立的默认范围。两者均不存在时，将范围作为必要缺口询问，不自行推断。继续维护时继承已确定的整批赛制范围。用户指定先处理某个赛制，只改变当前处理对象，不自动缩小整批范围或改变统一交付安排。用户明确变更范围时按新指令处理；只有影响下一动作的歧义才询问。 |
| **1.4 继承终点与限制** | 开启完整维护时，按已确认的完整流程推进；有“只准备分类材料”等明确限制时，以该限制为终点。继续维护继承原终点及仍有效的限制，除非用户明确变更。业务决定仍在对应节点取得。 |
| **1.5 恢复已记录进度** | 从已有交接信息和可定位记录恢复相关进度及材料位置，仅补查确定接续位置所必需的缺口。不在本步骤逐项重验分类、数据、内容、预览和发布成果。 |
| **1.6 识别维护类型** | 区分新一周维护、未完成维护的续作、已完成周的新增补充。不将三者一律处理为从头开始。 |
| **1.7 确定下一动作** | 根据已确认的阶段依赖、整批交付安排和实际缺口确定下一动作。不能凭某个赛制的局部进度，宣布整批交付节点完成。 |
| **1.8 简短告知并继续** | 简短说明本次范围、当前处理对象、接续位置及必要阻塞项。条件明确时直接继续，不再请求启动许可。 |

**与后续步骤的分工：**

第 1 步确定周次、整批范围、当前对象、终点和接续位置，并保留已有赛事范围约定。

具体赛事与牌表覆盖属于第 2 步；完整内容／视觉待定项清点属于第 5 步；实际赛制页面的准备及提交前技术检查属于第 6 步；整体候选组合、确认复用及剩余检查属于第 7 步；实际发布确认属于第 4 或第 8 步。**第 1 步不提前替这些步骤执行一遍。**

### 三、如何处理缺口

| 缺口类型 | 预期行为 |
| --- | --- |
| **可以从现有来源自行查明** | 针对具体缺口读取必要材料，不提问，不扩展为全历史搜索。 |
| **确实需要用户选择，或只有用户能提供必要信息** | 提交具体问题；多个已知且必要的问题合并提出。不要求重新确认整份计划或重新验收已有结果。 |
| **必要事实暂时因技术原因无法核实** | 保留未知，说明具体阻塞，针对该读取或查询故障处理。不以重新生成、重新验收或猜测替代缺失证据；没有新依据时不重复盲试。 |

共同原则：

- 只阻止依赖该缺口的动作。
- 继续已授权且不依赖该缺口的工作。
- 不重置其他进度，不自行改变统一交付安排。
- 后续阶段的证据暂不可用，但不影响当前动作时，不提前排查。
- 技术故障处理不自动扩大为工具开发或流程优化。

多个问题合并提出，仅指已知且同时阻止下一动作的必要问题；不因此提前调查所有后续步骤缺项。

### 四、本步骤的三种结果

**A．可以接续**

周次、整批范围、当前对象和终点明确，已有事实足以确定下一项符合阶段依赖的动作。

→ 简短告知后直接执行，不再请求启动许可。

**B．必要缺口阻塞**

存在影响下一动作的业务歧义、必要信息缺失或技术待查事项。

→ 说明阻塞并暂停依赖动作。**提出问题不等于前提已经满足，也不等于第 1 步已经完成。** 独立的授权工作仍可继续。

**C．本次范围已完成**

已有足够事实表明，本次约定范围已经完成。

→ 告知并结束，不自动开始下一周或追加事项。

这三种只是本步骤的结果，不新增维护阶段或状态系统。

### 五、验收情境

| 情境 | 合格表现 |
| --- | --- |
| 用户只查询维护进度 | 报告所需事实，不启动维护执行。 |
| 整批范围为四赛制，用户说“继续 W39 Pioneer” | 保留四赛制整批范围和统一交付安排，当前处理对象设为 Pioneer。 |
| 原终点是“只准备分类材料”，换会话后用户说“继续” | 继承原终点，不扩大到规则修改或发布。 |
| 用户说“开启周维护”，范围明确且没有可接续成果 | 简短说明后进入分类材料准备，不另问是否允许启动。 |
| 用户说“开启 W39”，但已有部分成果 | 从实际缺口接续，不因“开启”二字清空进度。 |
| 整批分类确认与数据交付已完成，内容尚未齐备 | 接续内容／视觉实际未决项，不重跑分类或数据发布，不直接假定只剩英文。 |
| 验收记录位置明确，但文件暂时无法读取 | 标为技术待查，不宣布原验收失效，也不请求重新验收来替代取证。 |
| 两个周次均合理，无法确定对象 | 只询问必要歧义；答案到达前，不擅选其中一个周生成材料。 |
| 后续预览证据暂不可用，当前动作是处理未完成的分类材料 | 继续不依赖预览证据的分类工作，不提前排查整套预览证据。 |
| 找到代表牌配置，但没有适用验收依据 | 不冒充已接受；若不影响当前动作，留待对应内容步骤处理。 |
| 本次约定范围已有充分完成事实 | 告知完成并结束，不自动开启下一周。 |

**验收重点是：读取是否必要、已知答案是否重复查询、范围和限制是否正确继承、是否提前执行后续工作。工具调用次数和耗时可以观察，不设固定次数门槛。**

## 实体赛事合流补充基准（已采纳）

确认依据：用户确认合流方案合理、可保留八步主干，并要求补清交接状态、范围分离、批次执行、来源与组合、完成记录五项边界；无需重新开启整份基准确认。

本补充扩展本批审查和数据交付对象，不增加维护阶段或审批。当前仅确认行为定义，不启动实际采集、周维护或 Skill 开发。

### 一、合流关系及八步中的归属

实体赛事独立取得输入，进入对应赛制的分类阶段后，与 MTGO 共同审查完整分类及 Unknown、落实同一套分类规则，并在第一次数据交付中统一公开。指定实体赛事由“可补充审阅材料”成为本批必须完成审阅及数据交付的对象。

| 步骤 | 合流后的要求 |
| --- | --- |
| 1．开启或继续维护 | 整批范围包含明确纳入的实体赛事清单。恢复赛事身份、赛制、材料位置、已有交接状态和已知阻塞，不重新审查全部资格或输入。 |
| 2．提交完整分类材料 | 按赛制提供 MTGO 与本批实体赛事的完整分类、Unknown、不可用牌表、具体覆盖及缺失；各来源与实际对象分别可定位。实体赛事不套用 MTGO 最多第 32 名的材料覆盖口径，提供该赛事全部可用分类牌表。 |
| 3．逐赛制确定最终分类 | 集中处理两类来源的分类意见，落实共享规则，核对完整同赛制保留语料的影响及必要产品同步范围，保留来源明确的完整分类确认。 |
| 4．统一交付数据 | 本批 MTGO 与指定实体赛事共同完成数据交付，分别满足接纳、统计、产品和实际发布要求；Landing 保持不变。 |
| 5—7．内容与 Landing | 继续原有 MTGO Feature、环境栏和 Landing 来源口径；实体赛事参与联合分类及数据交付，不自动进入这些内容的候选或统计。 |
| 8．完成维护 | 关联 MTGO、实体赛事和 Landing 各自的完成事实；不能只因 MTGO 完成就宣布整批完成。 |

实体赛事日期可以早于本次维护周。纳入当前批次时保留真实日期和身份，不改成当前周 MTGO 赛事，不重新打开已经完成的 MTGO 周记录。已有适用的公开结果继续复用。

本次现有实体路径限定为 Melee。其他平台不因同属实体赛事而被视为已有采集、规范化和交付能力支持。

### 二、交接状态：可审分类与可交付数据分别说明

独立采集向联合维护交接时，带入已查明的输入状态及已知发布阻塞，不能等分类审完才重新发现已有问题。

| 输入状态 | 联合维护中的处理 |
| --- | --- |
| 牌表可审、分类可复现，数据交付条件也满足 | 正常进入联合分类审查及后续交付。 |
| 牌表可审，但排名、轮次或结果存在已知交付阻塞 | 可以继续分类审查；保留并说明阻塞，不宣称整场已具备发布条件，不以 Swiss 排名替代正式最终排名。 |
| 输入不足以形成可靠分类材料 | 不伪造完整分类；处理或报告具体缺口，其他独立授权工作继续。 |

第 1 步仅恢复交接事实，第 2 步展示具体覆盖和缺失，必要修复只针对确定缺口。独立采集不绝对禁止补采：来源确有更新或输入缺失时，按已有授权补齐对应范围，不为进入周维护重新全量采集。

### 三、三个范围分别确定

| 范围 | 回答的问题 |
| --- | --- |
| 本批人工审查范围 | 用户本次确认哪些 MTGO 赛事及指定实体赛事？ |
| 完整语料影响检查范围 | 共享规则修改影响同赛制哪些保留牌表？ |
| 必要产品同步范围 | 哪些已公开统计、名称、目录或赛事组合必须随实际变化更新？ |

历史语料参与影响检查，不自动扩大人工审查范围；实际产品影响也不能忽略。仍有效的业务决定和产品结果复用，必要技术同步按既定授权处理。出现新的业务迁移或受保护产品边界时，只提交相关差异，不重开全部历史审阅。

共用同一套规则，不等于所有历史公开产物必须无条件换成当前摘要。按产品既有版本与兼容约定处理，不为追求摘要一致改写受保护历史产品。

### 四、批次执行覆盖实际手动与自动发布

实体采集任务只完成其已授权的输入交付，不因成功采集就提前公开本批待审结果。统一交付约束同时覆盖手动和自动发布入口；不得通过提前暴露部分规则、待审数据或接纳配置，让后台任务先发布半批结果。

这不要求暂停正常每日采集，也不在行为基准阶段规定发布锁等实现方式。正常采集与本批尚未统一交付的结果切换保持各自边界。

已审输入后来发生新增或更新时，明确说明增量和影响，复用不受影响的确认，不悄悄替换已审对象。

本批某赛事阻塞时，保留其他成果并继续独立授权准备；不擅自排除赛事或先单独发布 MTGO。改变范围或批次由用户决定。统一交付是结果要求，不为已有适用公开结果制造重复发布。

### 五、来源、确认与实体产品组合分别保留

联合分类不合并来源资格、缺失含义、Unknown 例外政策、统计口径或默认产品选择。可用牌表未命中规则与 unavailable 分开；不能将某来源的特殊接受方式自动复制给另一来源，也不把全部 Unknown 清零作为默认要求。

同一类别边界可以合并讨论，一次取得覆盖两类来源多份牌表的明确决定。记录中仍需分别定位来源、赛事及实际材料，不因保存两个来源的事实要求用户重复回答同一问题；类别边界确认不能自动扩大为整批完整分类验收。

按已有或本次明确确定的实体产品范围公开。不因多场赛事同批上线，就自动合并统计范围、改变默认选中项或既有产品口径。已有明确约定直接执行，不重复询问。

### 六、各来源完成事实独立，整批完成关联结果

实体赛事保持真实日期、身份以及独立的审阅、交付和完成事实。当前维护批次关联这些事实，不把实体赛事塞进 MTGO 周完成记录，不改写历史 MTGO 完成记录。

第 4 步已完成实体数据交付后，第 8 步引用并确认其仍满足本批要求，不为结束维护重新发布实体数据或重新审查分类。只有本批约定的两类来源数据交付及 Landing 交付均完成，才宣布整批维护完成。

## 第 2 步详细行为基准（按最终修订条件定稿）

确认依据：用户认可主体和其余条款，指定补清 2.4／2.5／2.10 的固定快照、2.11／结果 B 的局部确认边界、2.16 的诊断与建议区别，并增加三个验收情境，表示“修订后我认为第 2 步就可以作为正式行为基准确认”。本节按这些条件整理，不启动 Skill 开发或实际周维护。

**目标：按赛制提供本批 MTGO 与指定 Melee 赛事的完整分类依据，明确覆盖、缺失和已知交付阻塞，供用户审查。**

本步骤准备材料，不修改分类规则，也不完成数据接纳或发布。

### 一、机器应该做什么

| 编号 | 预期行为 |
| --- | --- |
| **2.1 明确本批审查对象** | 沿用第 1 步确定的整批范围，分别列明 MTGO 周次及赛事、指定 Melee 赛事及真实日期。跨周实体赛事保留自身身份，不改成当前周赛事。 |
| **2.2 承接输入交接事实** | 接收已有输入、分类可复现情况、材料位置及已知缺失，分别说明“能否审分类”和“是否存在已知数据交付阻塞”。不把分类可审视为数据可发布。 |

| **2.10 保存明确且不可覆盖的提交对象** | 每次实际提交给用户审查的材料形成可定位的固定快照，绑定实际赛事范围、来源材料和分类基准。提交后不得原地覆盖。新增赛事、补齐牌表、来源更新或分类基准变化时，生成新的修订快照，明确说明变化范围；旧快照和基于旧快照取得的决定继续保留，并仅在其实际范围仍适用时复用。 |
| **2.11 分别报告准备状态** | 按赛制和来源说明材料齐备、部分缺失或阻塞。已齐备部分可以先供审查；不得因此宣称整批齐备或改变统一交付安排。本批明确纳入但尚不可审的对象继续保留在待完成范围内，不因其他材料已经提交而从本批消失。 |

“全量”要求机器提供全部应审记录和完整牌表，不要求模型逐副人工重分类。

三个范围继续分开：本步骤明确本批人工审查范围；第 3 步处理规则修改时确定完整语料影响检查范围和必要产品同步范围；不为准备材料提前重验所有历史产品。

### 三、输入缺口与变化如何处理

| 情况 | 预期行为 |
| --- | --- |
| 输入有效，分类材料缺失或过期 | 使用已有输入生成缺失或受影响材料，不先重采；已提交对象按不可变快照规则处理。 |
| 牌表可审，但最终排名、轮次或结果存在已知交付阻塞 | 提供可审分类，同时保留具体阻塞。可以进入分类讨论，不能宣称赛事已可发布。 |
| 输入不足以形成可靠分类材料 | 明确哪些对象不可审，处理必要缺口；完整部分可以先审，不伪造缺失牌表或分类。 |
| 来源确有更新或输入确实缺失 | 在已有授权内补齐对应范围。需要改变来源或本批范围时提交具体选择，不默认扩大采集。 |
| 提交后新增赛事或输入发生变化 | 作为明确增量或修订处理，说明影响，复用不受影响的确认；不覆盖已审快照。 |
| 读取、下载或生成失败 | 处理对应故障，保留有效输入和成果。不以重新全量采集、重新验收或猜测替代故障处理。 |

已知且同时影响当前动作的必要问题合并说明。不为一次问齐，提前检查所有后续内容、图片和发布细节。

### 四、本步骤的结果

**A．材料齐备，可供审查**

本批审查对象、分类基准、实际覆盖与限制明确，全部应审材料可直接查看。

→ 提交材料，进入第 3 步的分类审查，不另设启动许可。已知数据交付阻塞继续保留。

**B．部分材料齐备**

明确可审对象、不可审对象及原因。

→ 可以先审不受影响部分，继续处理授权范围内的缺口；不宣布整批材料齐备，不改变统一交付安排。

对部分材料取得的决定只覆盖实际展示和确认的对象。只要本批该赛制仍存在未完成的应审对象，就不得把局部决定记录或解释为该赛制本批的完整分类确认。后续材料补齐时，只提交新增或实际变化部分作为新增待定；已有局部决定继续在适用范围内复用。新修订快照仍明确展示完整本批范围。

**C．已有适用材料或决定**

→ 复用并定位实际未决部分，不为经过第 2 步而重复生成或要求重新确认。

### 五、验收情境

| 情境 | 合格表现 |

| 提交后工作区分类器变化 | 已提交 Web 保持原基准，不静默刷新；变化需要参与本批审查时，生成新可定位快照并说明差异。 |
| Melee B 暂不可审，其他对象已完成审查 | B 继续保留为本批未完成对象，不能因当前可审材料均已确认就宣布该赛制完整分类完成。 |

核心：把本次用户实际审查的固定材料完整、准确、可追溯地提交；不替用户分类，不覆盖已提交材料，不提前解决下游问题。

### 一、接收决定并明确作用范围

| 编号 | 预期行为 |
| --- | --- |
| **3.1 定位用户意见** | 将意见对应到实际提交快照、来源、赛事、牌表或类别边界。明确的直接处理；只有影响执行的歧义才询问。 |
| **3.2 区分决定作用域** | 区分类别边界、指定牌表、局部确认与完整分类确认。已确认边界可以覆盖其明确逻辑作用范围；机器用独立牌表材料证明其他对象属于该范围，不逐副重复询问，也不扩展到无法由该边界推出的对象。 |
| **3.3 明确最终业务含义** | 简明说明落实后的类别、子类、名称及边界。已表达清楚的决定不重复请求批准；不能用技术写法偷偷加入新业务取舍。 |

预期变化的来源只能是：

- 用户明确指定的对象及处理结果；
- 根据用户已确认边界和独立输入，可以明确推导出的对象及处理结果。

候选产生的实际差异可以用于发现问题，不能直接复制成“预期变化”来证明自己正确。

### 二、分类器的修改方法

#### 3.4 优先复用现有分支，以最简必要条件表达决定

固定采用以下顺序：

1. **先检查现有分支能否表达。** 确认目标套牌为什么未命中或误命中，不先新增分支。
2. **优先调整现有分支的必要条件。** 在已确认业务边界内，修正不必要的限制、过高数量门槛、重复或不准确条件，使其覆盖目标构筑，同时保留区分相邻类别所需的条件。
3. **避免按样本堆叠规则。** 不因几副目标牌表略有差异，就分别复制分支、增加长串例外或列举全部具体构筑。
4. **现有分支确实无法清楚表达时，才增加必要分支。** 说明现有分支为何不能表达，以及强行合并会产生什么误分类、冲突或业务含义变化。新增父类、子类或改变业务边界仍须有对应用户决定。
5. **检查本次改动是否引入冗余。** 保留必要的识别和区分条件。只消除本次修改直接造成、且不承担独立业务边界的冗余；既有独立分支即使看起来相似，也不因本次任务顺手合并。简化限定于本次受影响规则，不扩展为全分类器重构。

“最简”以业务含义清楚、条件必要、目标覆盖正确、无未解释漂移为标准，不以代码行数最少为标准，也不要求穷举所有可能写法。

#### 数量门槛的约束

- 使用能够维持已确认类别边界的较低门槛。
- 不因眼前样本恰好带四张，就直接要求四张。
- 采用更高门槛时，应有较低门槛造成身份迁移、冲突或分类丢失的具体依据。
- 不为覆盖目标而无依据地放宽条件，也不靠不断收紧条件将规则变成单副牌表指纹。

#### 指定牌表不授权特殊绕过

用户指定“这副应归为 A”，确定的是业务归属。

机器通过现有分类规则或已批准例外机制表达；不得新建未经批准的牌表 ID 特判、手改历史分类结果，或绕开分类器。

如果无法在已有边界内表达，提交具体冲突及真正需要决定的边界问题。

### 三、固定检查顺序与范围

| 编号 | 预期行为 |
| --- | --- |
| **3.5 补齐公开必需配套信息** | 业务含义及候选身份稳定后，集中核对数据消费者所需的类别身份、名称、颜色身份等信息。现有规则、已确认分类或既有映射能够唯一确定的，机器直接补齐；只有真实业务或展示选择才提交用户。已知缺口不故意拖延到完整检查后才提出。 |
| **3.6 分开三个范围** | 本批人工审查范围、同赛制完整保留语料影响检查范围、必要产品同步范围分别确定。历史语料参与检查不自动扩大人工审查；发现实际产品影响也不能忽略。 |
| **3.7 固定正式比较** | 规则内容变化时，以本批开始时为该赛制固定的已接受分类器为基准，以本批累计修改后的最终候选为比较对象，对相同的适用完整 MTGO／Melee 保留输入进行比较。正式比较复用当前有效的 retained corpus；“相同输入”指比较两套规则作用于同一固定输入，不要求重新抓取来建立所谓新基准。续作不把中间候选滚动替换为正式基准。核对独立确定的预期变化，以及其他分类、子类、命中、冲突和状态变化。 |
| **3.8 处理差异** | 已确认边界能够独立解释的迁移，作为该决定的预期作用结果展示，无需逐副重新询问。实现偏差在原边界内修正；超出边界、存在新歧义或需要新业务取舍时，只提交相关差异。不得把未解释副作用补记为预期。 |
| **3.9 确定必要产品同步** | 稳定候选及影响结果明确后，依据既有产品依赖确定需要同步的统计、名称、目录和赛事产品，交给第 4 步落实。不为保险扫描并重做所有历史产品；受保护产品按既有版本与兼容约定处理。 |

中间候选之间的比较可以辅助诊断，但不能替代本批原已接受基准到本批最终候选的累计影响证明。

仅规则编号或命中证据变化，也需解释其技术原因和业务结果；不能忽略，更不能仅因发生变化就要求用户重新判断类别。

### 四、按变化类型执行，保留快速路径

| 实际变化 | 需要做什么 |
| --- | --- |
| 没有规则变化，也没有使既有分类证明失效的其他变化 | 复用第 2 步分类基准和材料，记录实际确认；不制造规则候选，不重跑完整影响比较。 |
| 只有展示名称变化 | 检查名称和实际使用位置，不自动运行分类漂移。 |
| 规则内容变化 | 完成适用的同输入、全语料累计影响比较。 |
| 分类执行机制确实变化 | 才触发相应机制检查；普通规则修改不因此扩大为引擎开发。 |

规则是否变化以实际改动为准，不能仅凭工具状态名称判断。

正常执行顺序：用户决定明确 → 最简规则表达与必要局部诊断 → 候选稳定 → 必需配套信息检查 → 完整累计影响比较 → 确定产品同步范围 → 处理异常 → 提交最终分类结果。

不在每个临时写法上重复完整检查。修复或新增决定使已有证明失效时，补足对应证明，不重做无关部分。配套信息检查不意味着提前生成全部公开产品。

### 五、提交结果与形成确认

| 编号 | 预期行为 |
| --- | --- |
| **3.10 提交修改结果** | 展示最终业务含义、规则采用的表达方式、预期变化是否实现、其他差异如何处理及剩余问题。只解释足以判断业务边界是否被正确落实的规则表达，不默认展示完整 YAML、所有条件或实现细节；用户要求时再展开。材料变化时生成新的固定快照，保留原快照和决定。 |
| **3.11 核对完整确认范围** | 当前最终快照中的本批应审义务，须被实际用户决定、仍适用的既有决定及符合政策的处理结果覆盖。局部确认不能冒充完整确认；新增待定项只包括新增或真实变化部分。 |
| **3.12 保留批次与交付阻塞** | 分别保存各赛制分类成果、影响证明和剩余问题。最终排名、轮次等数据交付阻塞继续保留，不因分类完成而消失，也不触发单赛制提前公开。 |

### 六、严格禁止的行为

- 不从候选实际差异反向制造预期答案。
- 不用最后两版候选之间的比较，代替原基准至最终候选的累计证明。
- 不为覆盖当前样本无必要地新增分支、提高门槛、堆叠例外或编写 ID 特判。
- 不默认提出新的类别、拆分、命名或边界建议；真实冲突需要决定或用户要求时除外。
- 不以 Unknown 全清零、不可用牌表全补齐作为统一完成条件；来源政策和合法例外分别保留。
- 不只检查点名样本，也不默认运行整个分类引擎测试套件。
- 不重新采集来进行影响比较，不因 SHA、工作区或无关变化重复有效检查。
- 不重开全部历史人工审阅，不强行更新受保护历史产品以追求摘要一致。
- 不覆盖已提交快照，不丢弃本批未完成对象。
- 不让部分规则或接纳状态提前被手动或自动生产使用；不擅自暂停正常每日采集。
- 不在本步骤选择 Feature、制作正文、更新 Landing，或宣称数据已经公开。

### 八、重点验收情境

| 情境 | 合格表现 |
| --- | --- |
| 用户接受当前完整分类，没有修改 | 复用材料和证明，不创建无意义候选或运行完整漂移。 |
| 现有分支仅因不必要的数量限制漏掉目标 | 优先修正该限制并检查影响，不先复制一个新分支。 |
| 目标样本都带四张核心牌，但较低数量已能正确区分类别 | 不无依据地要求四张；更高门槛必须说明必要性。 |
| 单个现有分支无法清楚表达已确认构筑 | 展示具体原因，采用必要新分支，不强行压成难以理解的条件串。 |
| 用户确认所有符合 X 的牌表归 A，历史语料另有明确符合 X 的牌表 | 独立证明其符合边界，展示预期迁移，不逐副重复询问。 |
| 第一项修改形成候选 B，第二项形成 C | 最终比较原已接受基准 A → C，不只比较 B → C。 |
| 候选额外迁移了未获决定支持的牌表 | 查明原因，不把实际迁移直接写入预期清单。 |
| 指定牌表无法在现有边界内正确表达 | 不加 ID 特判，提交具体边界冲突。 |
| 颜色身份可由既有规则唯一确定 | 机器直接补齐，不询问“是否需要设置颜色”。 |
| MTGO 和 Melee A 已确认，Melee B 仍有未完成应审义务 | 保留已有决定，不宣布该赛制完整分类完成。 |
| 分类全部完成，但实体最终排名仍缺失 | 分类阶段可以完成，数据发布阻塞继续保留。 |

无规则变化的快速路径列为后续 Skill 实现验收的高优先级性能情境，不为此增加独立阶段或检查门槛。

### 一、机器应该做什么

| 编号 | 预期行为 |

| **4.11 确认实际公开结果** | 分别确认平台操作与产品结果：对象正确，本批赛事及数据实际可用，来源和组合范围正确，受影响入口及资源可用，旧 Landing 产品得到保留。 |
| **4.12 保存数据交付事实** | 保存赛制、赛事范围、分类对象、交付版本及实际结果的必要引用，MTGO／Melee 分别可定位。本步骤不宣布整批周维护完成；第 8 步按既有机制补齐必要完成事实，再由这些事实得出本批完成结论，不另建批次真值台账。 |

### 二、必要检查的明确范围

根据本次实际变化，核对以下适用事项：

- 赛事范围：批准纳入和排除的对象正确，本批新赛事没有遗漏。
- 分类绑定：需要更新的产品使用第 3 步最终分类版本；保留产品符合各自既定绑定。
- 统计结果：独立计数和必要代表性复算成立，合法缺失与例外保持原含义。
- 来源与消费者：来源身份、目录、字段及实际使用位置正确。
- 产品入口：实际受影响入口和必要资源可用。
- 旧 Landing：原已接受内容与实际依赖组合仍适用。
- 公开边界：私有审查材料、未获准数据等没有混入公开包。

这些是按变化选择的结果检查，不要求每次重新检查全部统计、全部页面或所有历史恢复路径。

### 三、生成、候选和复用的顺序

正常路径：承接确定对象及已知阻塞 → 定位已有成果和发布续作位置 → 解决必要交付缺口 → 在隔离候选内落实接纳范围 → 按已确定范围复用或生成 → 检查受影响结果，形成固定完整候选 → 对该候选打包、归档并统一发布 → 确认实际结果，保存数据交付事实。

固定约束：

1. 先明确输出，再生成。不通过重建整站后观察差异，反过来猜测影响范围。
2. 正常路径读取同一候选。检查、打包、归档和发布不得各自重新生成一份内容。
3. 候选变化必须显式形成新版本。输入变化、影响输出的实现修复或线上组合变化，需要新候选时，保留原候选并说明变化。
4. 执行故障不自动改变候选。归档、上传、查询或发布失败，原候选内容不因此重建。
5. 新组合不改写旧记录。因其他交付需要采用新基线时，形成新的组合及对应准备记录；不能给旧归档包或未结束操作偷偷换基线。

新输入改变已审对象时，按第 2—3 步增量和证明复用规则处理，不直接混入发布候选。

### 四、Landing 保持不变的执行边界

优先保留并核对实际已经接受的产品及其绑定。旧 Landing 对应旧周环境、特定 Feature 牌表和分类主体时，不能拿相同文案配上新分类器重新查出的牌表，声称页面没有变化。

维持同一已接受产品需要保留版本化资源或必要兼容处理时：

- 机器处理技术问题；
- 只补受影响组合的证明；
- 不将其转化为新的正文、Feature 或视觉选择；
- 不伪造绑定或改写验收记录来通过检查。

只有确实必须改变已接受业务内容时，才提交具体差异，不重开全部历史审阅。

### 五、统一交付与复用

- 有本批必要对象尚未满足条件：保留其他成果并继续独立准备，不擅自排除对象或先发 MTGO。
- 部分结果已经有效公开：复用事实，交付尚未完成的变化，不为形式重复生成或写入全部文件。
- 全部数据结果已有效公开：核对覆盖本批要求，引用已有事实，直接完成本步骤，不额外部署。
- 规则未变但有新赛事：仍须接纳并交付新赛事及对应统计，不能跳过本步骤。
- 工具暂不支持统一交付：明确能力缺口并保全成果，不因工具只能分开执行就自行拆批，不把 Skill 指令当成已有工具能力。

统一交付同时约束手动与自动发布入口。

### 六、机器严格不做什么

- 不只合并分类器或重算旧赛事，就遗漏本批新赛事。
- 不提前让部分接纳配置、规则或公开选择在生产生效。
- 不为输入够新重采，不为普通数据交付重跑完整分类比较或机制测试套件。
- 不重新分析已确定的全部产品影响，不为保险生成整个站点。
- 不改变来源统计口径、实体聚合范围、默认选择或受保护历史产品。
- 不以新数据静默重新解析旧 Landing，不借兼容问题重新要求业务验收。
- 不覆盖固定候选，不在发布阶段暗中生成另一份内容。
- 不覆盖其他任务后来交付的有效成果，不静默修改发布基线。
- 不把 PR 合并、配置写入、平台绿色状态视为产品已确认。
- 不因失败退回完整采集、分类或生成流程，不擅自回滚。
- 不为后续 Feature／环境栏选稿提前开展候选筛选、本地化或内容 Web 审阅准备。本次数据交付及保留既有 Landing 实际需要的资源缺口，按 4.6／4.7 处理；只补对应缺项，不扩成全部图片重建。生成器附带产生的内部中间文件可以保留，但不为此额外准备、检查或提交内容材料。
- 不生成表示整批周维护完成的记录。

### 七、失败与未知状态的续作

| 情况 | 预期行为 |
| --- | --- |
| 输出已生成，路径登记或检查入口失败 | 保留输出，修复具体问题；生成依据未变时不重建。 |
| 候选已归档，后续发布失败 | 复用原包，从失败处继续。 |
| 发布请求超时或查询失败 | 查询原操作，保留未知；不直接发起第二次写入。 |
| 已部署但产品确认失败 | 分别记录部署事实和产品问题，继续必要诊断；不宣布完成，不自动回滚。 |
| 期间出现其他有效交付 | 保留新成果，必要时形成新组合候选；复用本批未受影响数据与证明，只补组合相关验证。 |
| 某实体赛事仍有交付阻塞 | 保留整批成果，继续独立准备；改变范围或拆批由用户决定。 |

### 八、本步骤的结果

**A．本批数据交付完成**

本批 MTGO 与指定 Melee 数据实际公开正确，必要产品同步完成，旧 Landing 产品得到保留，实际结果已确认。

→ 保存数据交付事实，进入第 5 步，不新增内容材料准备许可。

**B．尚未满足统一发布条件**

→ 明确剩余阻塞，保留准备成果及既有线上产品，不发布半批结果。

**C．发布已发生，但结果未知或存在失败**

→ 记录真实状态，从相应环节续作，不重发、不归零、不宣告完成。

### 九、验收情境

| 情境 | 合格表现 |
| --- | --- |
| 规则未变，本周新赛事尚未公开 | 完成新赛事接纳与数据交付，不跳过本步骤。 |
| 分类器已合并，本批赛事仍未公开 | 明确交付未完成，不宣告上线。 |
| 某实体赛事最终排名未齐 | 保留分类成果与阻塞，不用 Swiss 排名冒充，不先发半批。 |
| 输出已生成，仅登记路径遗漏 | 修复登记并核对，复用适用输出。 |
| 某些结果已有效公开 | 复用事实，不为同批交付重采或重复生成。 |
| 发布请求超时 | 查询原操作，不立即重发或重建。 |
| 平台成功，但线上缺少本批赛事 | 处理产品问题，不以绿色工作流结案。 |
| 数据已完成交付，Landing 尚未更新 | 完成第 4 步，不写整批周维护完成记录。 |
| 固定候选形成后，其他任务更新线上无关文件 | 保留该更新，形成必要新组合候选及准备基线，不重生成本批数据，只补组合证明。 |
| 新分类器重新解析旧 Landing 会得到不同牌表，但原绑定资源仍可提供 | 保留原绑定与资源，不静默重新解析，不要求重新确认旧 Landing。 |

## 第 5 步详细行为基准（已确认）

确认依据：用户确认第 5 步，并要求补入稳定 Feature 候选引用、已有有效批准名称不因 name dimension 存在而重新开放选择两项边界。本节完整纳入；仅确认行为定义，不启动实际维护或 Skill 开发。

**目标：按既定规则确定候选、展示对象及实际待定项，提供足够的选择依据，及时交给用户决定。机器不自行选稿、选代表牌或撰写观点。**

本步骤准备材料；实际选择、中文输入和英文确认属于第 6 步。

### 一、机器应该做什么

| 编号 | 预期行为 |
| --- | --- |
| **5.1 承接数据交付结果** | 使用第 4 步已确认的数据、分类与统计对象，核对材料与赛制、周次及版本一致。复用已有交付证明，不重新跑分类、统计或发布检查。 |
| **5.2 保持既定来源与窗口** | 按现有规则确定 Feature 候选范围、统计窗口和环境栏对象。Melee 参与联合分类和数据交付，不自动进入 MTGO 内容候选、占比或胜率计算。 |
| **5.3 按绑定生成或复用候选** | 按既定筛选规则提供 Feature 候选及事实依据。已有候选的赛事范围、分类基准、筛选策略和依赖机器事实，须经既定绑定与比较判定仍适用，才能复用；不能由文件日期、名称、存在与否或模型印象代替。缺失或实际失效时，只重建受影响机器候选，不重新采集。 |
| **5.4 提供完整 Feature 选择依据** | 候选明确对应牌表、赛事、日期、排名、分类，以及筛选所用统计和事实理由，并可直接查看完整主备牌。不以候选名称、关键牌摘要或模型评价替代实际构筑。提交给用户的候选使用当前周次、赛制内稳定且可定位的引用编号；修订材料时，实际未变化的候选保持原引用，删除编号不在同一范围内复用于其他候选。事实变化形成新对象时使用新引用，不将旧用户决定静默绑定到新对象。短编号仅为对话引用，实际对象仍由赛事、牌表身份／完整内容及分类依据等事实确定。 |
| **5.5 提供环境栏及代表牌选择依据** | 第一次提供材料时，明确说明本周环境栏是否出现从未展示过的新类型；有则列清具体类型及需要补充的展示资料，无则明确说明本周无需新增环境代表牌选择。已经展示且本次沿用的现有配置默认已确认，不要求额外确认。新类型需要选择代表牌时，提供对应实际牌表／代表构筑直接入口和完整主备牌；已有确定性牌频、共同牌或候选规则时展示相应机械事实，不由模型主观筛选。 |
| **5.6 清点实际未决项目** | 对当前确定需要使用的对象，按既有内容维度清点名称适用状态、视觉组合、代表牌、Feature 选择及展示类别、正文状态等。环境栏已展示的现有配置按用户默认确认规则复用，不因缺少历史验收记录重新列为待定；仅有配置但从未展示不能据此视为已展示。其他对象继续按各自确认合同处理。第 3 步已确定并具有有效批准、且当前显示值未变化的名称直接作为既定事实复用，不重新开放名称选择；只有实际显示对象缺少适用名称决定或名称确实变化时，才进入待定清单。维度存在本身不等于用户必须重新决定。 |
| **5.7 复用适用决定** | 已接受且实际未变的名称、视觉决定按既定范围复用。跨周可复用完全相同的名称与视觉决定，不自动继承旧周正文、Feature 选择或最终页面确认。 |
| **5.8 标明选择依赖** | Feature 尚未选择时，明确哪些展示项目要等选择后才能确定，不标成已完成，也不要求提前决定全部候选的展示资料。 |
| **5.9 提交固定材料** | 按赛制组织只读 Web 材料，候选与待定项可直接定位。实际提交后保持固定快照；相关事实变化时形成新修订，保留原材料和仍适用决定。 |
| **5.10 检查实际审阅入口** | 核对版本、候选范围、必要数字、完整牌表可达性及待定项对应关系。只取得支持当前选择所需的证明，不提前执行最终 Landing 页面验收。 |
| **5.11 材料齐备即提交** | 当前选择依据和已知必要待定项齐备后立即提交，不等待英文、完整图片缓存、页面组装或发布准备。 |

候选有效性与人工决定有效性分别处理。机器候选需要更新，不等于所有已有业务决定失效。既定比较允许等价复用时，按该结果执行；不能仅因技术身份变化重开全部确认。

### 二、数据颜色身份与视觉指示色

- 数据颜色身份：第 3 步已经确定的类别身份事实。
- 视觉指示色：具体展示对象按身份和显示规则呈现的颜色。

视觉指示色能由既有规则唯一确定时，机器直接带入，不询问“你想选什么颜色”，也不自行改色。视觉指示色由身份规则确定，不代表整个视觉组合已经被用户接受。

视觉组合尚未接受时，按实际展示对象提交确认；已确定颜色作为事实呈现。只有确实存在独立视觉配色选择、且没有适用决定时，才提交该选择。

环境栏两张代表牌、已选 Feature 四张展示牌及相关视觉组合，分别识别适用决定。第 3 步已解决的数据身份和名称不重复询问。

### 三、待定清单与一次列齐

| 状态 | 机器行为 |
| --- | --- |
| 已有有效决定且未变化 | 标明沿用，不再次要求选择。 |
| 环境栏已有展示且沿用现有配置 | 按用户默认确认规则直接复用，不追问历史验收记录。 |
| 已有配置，但尚未展示且无适用确认 | 展示现值与待确认事实，不把配置存在当成已经展示，也不包装成推荐。 |
| 缺失或实际变化 | 提供具体待定字段及足够的选择依据。 |
| 技术证据暂缺 | 处理具体证据缺口，不要求重新接受来替代取证。 |
| 依赖尚未作出的选择 | 明确依赖关系，待对象确定后处理，不对全部可能对象提前展开。 |

一次列齐指：当前已知且能确定的必要项目一次查齐，同时说明尚待选择才能确定的依赖。

- 环境栏类别已确定：一次查齐这些实际类别的名称、指示色、代表牌和确认状态。
- Feature 尚未选择：提供候选与后续要求，不提前给每个候选四张牌、下载图片或制作完整视觉材料。
- Feature 选定后：第 6 步只补已选对象的实际缺项，使用相同的事实材料支持选择原则。

后续选择产生的新项目可以增量提出；原本已经可知却漏查的项目，不得称为后续新增。

### 四、机器严格不做什么

| 编号 | 禁止行为 |
| --- | --- |
| **5.12** | 不默认推荐 Feature、展示类别或代表牌；不自行改变确定性指示色，也不将其重新开放为颜色选择。用户明确要求建议时，仅针对所问对象提供。 |
| **5.13** | 不把机械排序、标签或统计事实改写成模型背书，不额外主观筛选来缩减候选。 |
| **5.14** | 不默认撰写中文、提出环境观点、润色已有文字或提前制作英文草稿。 |
| **5.15** | 不遗漏从未展示的新类型；不把环境栏已展示且沿用的现有配置重新提交确认。仅有配置但未展示的对象，不冒充已有展示。 |
| **5.16** | 不因机器候选过期重开实际未变业务决定，不覆盖旧快照或将旧决定改绑到变化对象。 |
| **5.17** | 不混同未选择、未填写和明确不选 Feature。Landing 中文正文为默认必交项，不把“本周不写”列为常规选项；仅用户后续明确改变要求时按相应例外处理。 |
| **5.18** | 不为全部候选提前准备代表牌、完整图片缓存或最终 Landing。当前选择确实需要的材料除外。 |
| **5.19** | 不重新采集、修改分类、扩大统计来源、重新发布数据或开展无关检查。 |
| **5.20** | 不把候选展示、材料生成或用户未回复当成确认；没有待定项时不制造空审阅请求。 |

机器既不能替用户选代表牌，也不能只说“缺两张牌，请提供”，把寻找选择依据的工作转交给用户。

### 五、空结果、复用与变化

- 有效候选为空：如实说明，不擅自放宽筛选规则；不能据此记录用户明确不选 Feature。
- 用户已明确不选 Feature：跳过本周 Feature 相关动作，继续环境栏及需要处理的正文。
- 已有本周决定：复用适用部分，仅处理实际剩余项。
- 相关上游事实变化：按绑定确定影响，必要时生成新修订材料，只提出实际变化项；不自动重启完整维护。
- 某赛制材料阻塞：明确缺口，其他齐备材料仍可进入内容讨论；统一 Landing 交付安排不变。

### 六、本步骤的结果

**A．选择材料齐备**

候选事实、环境栏资料、当前待定项和选择依赖明确，必要牌表可直接查看。

→ 提交用户，进入第 6 步。

**B．仍有材料缺口**

→ 处理对应缺口，保留有效材料与决定；不要求用户在缺乏依据时猜测，不阻止独立内容工作。

**C．已有适用材料和决定**

→ 只接续剩余项。不存在实际需要用户决定的项目时，不生成空审阅页面，不要求确认“没有待定项”。尚有中文／英文工作则接续第 6 步；第 6 步也已完成时，直接进入第 7 步。

### 七、验收情境

| 情境 | 合格表现 |
| --- | --- |
| 旧候选文件存在，但分类基准或依赖事实变化 | 按绑定判断，不凭存在直接复用；只重建实际失效部分。 |
| 数据与候选绑定仍适用 | 直接复用，不重采或重跑分类。 |

| 名称和视觉跨周完全相同且原决定适用 | 沿用；Feature 选择和正文不随之自动继承。 |
| Feature 尚未选择 | 不为全部候选提前准备展示牌及图片。 |
| 用户明确不选 Feature | 跳过 Feature，仍处理环境栏和必要正文。 |
| 有效机械候选为空 | 不自动记录用户明确不选。 |
| 当前选择材料已齐备，下游页面尚未准备 | 立即提交，不等待下游工作。 |
| 所有决定适用且无实际待定项 | 不制造空确认，直接接续实际下一阶段。 |
| F1／F2／F3 已提交，修订只移除 F1，F2／F3 未变 | 保留 F2／F3 原引用，不重新编号；移除编号不复用于新候选，旧决定不指向其他牌表。 |
| 新类别名称在第 3 步已确定且有效批准，第 5 步仍存在 name 维度 | 作为既定名称复用，不再询问；维度存在本身不等于新业务选择。 |

八步是结果依赖，不是八次必须发生的对话。

## 用户后续修订：环境栏默认确认与第 6 步提交内容

用户明确要求：Feature 有无、展示类别、展示牌、Landing 正文中文是需要提交的内容；有 Feature 时，每条 Feature 的中文说明也必须由用户提供，不能由 Landing 正文替代。环境栏代表牌不是每次必交项。

### 环境栏已确认规则

- 第一次提供材料就说明本周是否有从未展示过的新类型；有则列清，没有则明确告知无需新增环境代表牌选择。
- 已经展示且本次沿用的现有环境栏配置，依本次用户规则默认已确认；缺少历史验收记录不构成重新提问理由。
- 沿用依据是本次用户给出的默认确认规则，不伪造或补写过去曾经逐项验收的历史事实。
- 仅有配置但从未展示，不等于已经展示。新类型或用户明确要求改变的项目，按实际变化处理。
- 此项修订适用于环境栏现有展示配置，不自动接受本周新的 Feature 选择、正文或最终页面。
- 本项优先于先前通用条款中将环境栏已配置但缺历史验收记录一律列为待定的做法。

### 第 6 步提交要求的确认来源

- 本次 Feature 有无必须明确；有 Feature 时，具体对象、每条的展示类别（新套牌／新科技）、四张不同展示牌及各自中文说明均必须由用户明确提供。明确无 Feature 时，这些单条字段不适用。
- Landing 中文正文按用户本次要求列为必交项；不再默认将“本周不写”列为同等常规选项，后续明确例外按实际指令处理。
- 环境栏代表牌只在新类型或实际改动需要时提交，不要求每次重填或确认已有展示配置。
- 上述要求及其他实际应由用户提供的内容，缺失时机器只提醒具体缺项；没有明确指令时不建议、不代填、不代写，不以机器推断代替用户提供。
- 已知且当前必要的缺项一次列齐；用户部分补充后保留已有内容，后续只提醒仍缺的部分，不要求重发完整内容。
- 缺项持续保留，直至用户实际提供或明确改变对应要求；沉默、遗漏、等待时间或机器候选为空均不构成省略、默认选择或确认。
- 存在适用必交项缺失时，不把对应内容标记为齐备，不越过依赖该项的验收或交付；不依赖缺项的既定机器工作可以继续。确定性身份、链接、英文草稿及其他机器职责仍由机器处理，不能作为用户缺项提出。
- 用户明确要求建议或代拟时，仅在其明确委托的对象和范围内处理；生成建议／草稿本身不等于用户已确认。
- 以下第 6 步完整条款整合这些要求及后续页面复用约定；不启动 Skill 开发或实际周维护。

### 用户确认补充：实际展示与第 6／7 步确认复用

- “视觉组合”具体指实际展示项的类别名称、颜色标识、牌图及排列顺序：Feature 为四张展示牌，环境栏为两张代表牌。已确定名称、确定性颜色和用户明确指定的牌张／顺序不重新开放选择。
- 第 6 步在内容审阅 Web 中展示真实页面呈现，包括实际图片与排列；不能只用牌名、颜色代码或无关示意图替代。机器先核对图片显示、牌张对应与顺序，不把技术错误交给用户发现。
- 用户在当前对话中确认实际展示及英文等待定内容，可以一次覆盖多个已展示项目；记录其真实确认范围。机器落实与用户原指令不符时，修正落实错误，不要求用户重新选择。
- 本批约定赛制在第 6 步展示并确认的页面内容，第 7 步默认直接复用。第 7 步不设置必经的第二轮整页人工确认，不因进入新阶段、重新组合或记录位置变化而要求重审。
- 第 7 步仅对确实需要新判断的部分提交补充确认：新增内容、影响已确认内容或展示体验的实际变化，以及此前未展示且尚无适用确认的整体组合部分。提交时指出具体对象、差异与需要补充确认的原因，不重开未变化部分。
- 必要的组合与技术检查由机器负责，复用已有适用检查；没有实际变化或确认缺口时，第 7 步沿用第 6 步确认完成验收，按既定流程进入第 8 步，不制造“请再次确认整页”或“确认没有待定项”的人工节点。
- 复用只覆盖实际已展示和确认的范围，不能把局部内容确认扩大为未展示部分的确认；既有环境栏默认确认政策继续有效。
- 本补充优先于此前将第 6 步与第 7 步理解为必须分别取得两次页面确认的表述。当前仅确认行为基准，不启动 Skill 开发或实际周维护。

## 第 6 步详细行为基准（按对话约定整合）

本节把用户明确的必交内容、缺项处理、对话提交方式与实际页面确认约定整合为连续步骤，不增加新的用户选择或审批。当前工具能否完全表达这些行为，在后续实现时核对；不能把预期能力写成当前已经具备，也不能因工具不支持而转嫁重复确认。

### 一、用户提交什么、如何提交

默认使用只读 Web 查看事实及页面，在当前对话提供选择、中文和确认。可以逐赛制提交，也可以一次提交多个赛制；多轮消息累计保存，不要求反复重填整份表格。自然语言能明确定位即可，不强制 JSON、文件、URL、内部标记或固定口令。

| 用户输入 | 适用条件 | 可直接采用的提交方式 |
| --- | --- | --- |
| Feature 有无 | 每个本批赛制必须明确 | “Modern 本周无 Feature”或“Modern 选 F2、F5”。候选为空不等于明确不选。 |
| Feature 实际对象 | 选择 Feature 时 | 使用第 5 步稳定编号；若从提供的完整 Top8 材料另选，可用赛事和名次等明确定位，由机器绑定对象并赋稳定引用。 |
| 每条 Feature 展示类别 | 每条已选 Feature | 明确“新套牌”或“新科技”；不由机器根据候选标签推断。 |
| 每条 Feature 展示牌 | 每条已选 Feature | 按所需顺序给出四张不同牌，须来自该实际牌表的主牌或备牌。 |
| 每条 Feature 中文说明 | 每条已选 Feature | 按对应编号分别提供中文；Landing 正文不自动代替单条说明。 |
| Landing 中文正文 | 每个本批赛制默认必交 | 直接提交文字或编号分条；明确的同条换行保留，不自行把普通换行拆成多个 bullet。 |
| 环境栏两张代表牌及顺序 | 第 5 步列出的新类型或实际改动确有需要时 | 指明类型及两张牌；已展示且沿用的配置默认接受，不要求每周提交。 |

示例仅表达提交格式，不提供内容建议：

```text
Modern
Feature：选 F2
F2 类别：新科技
F2 展示牌（依次）：牌 A、牌 B、牌 C、牌 D
F2 中文说明：〔用户正文〕
Landing 中文正文：
1. 〔用户第一条〕
2. 〔用户第二条〕
新环境类型 X 代表牌（依次）：牌 E、牌 F
```

环境栏一行仅在实际需要时出现。明确无 Feature 时跳过单条 Feature 输入，Landing 中文仍需提供。不新增独立标题、字数、条数或重复表格要求；已有确定名称直接复用。英文、链接、确定性颜色及其他机器职责不能列为用户缺项。

### 二、机器动作

| 编号 | 预期行为 |
| --- | --- |
| **6.1 接续第 5 步材料** | 接续已提交的稳定候选、事实与实际待定清单，不重新筛选候选或重新开放既有名称及环境配置。 |
| **6.2 接收并绑定输入** | 将用户选择和文字绑定周次、赛制及实际对象。F 编号映射到真实赛事、牌表身份和材料，不绑定会变化的列表位置；只澄清具体歧义。 |
| **6.3 累计输入并提醒缺项** | 一次列清当前已知且必要的缺项，部分回复后仅提醒仍缺内容。用户未明确委托时不建议、不代选、不代写、不默认省略；缺项保留直至提供或明确改变要求。 |
| **6.4 只展开已选对象** | 对已选择 Feature 补实际依赖及展示材料，不为所有候选提前准备四张展示牌、翻译或图片。环境栏沿用第 5 步未决项，既有展示配置不因缺历史记录重新列入。 |
| **6.5 保留用户中文** | 保留原意、语气、分条、明确换行和对象归属，不默认润色或改写。将自然语言转换成必要结构时保持可见结果；发现明确数字矛盾只指出具体位置，不擅改结论或扩大为环境研究。 |
| **6.6 机械核对展示牌** | 解析规范牌张身份，验证 Feature 恰为四张不同牌、每张属于实际牌表主牌或备牌，并保留顺序。中英文同一牌不算不同牌。错误只报告具体项并请求修正，保留其余输入，不自行替换或推荐。 |
| **6.7 处理链接与资源** | 用既有共享牌名和资源机制处理明确名称、链接及牌图；只有真实歧义才问用户，不要求提供机器能定位的 URL。复用适用资源，只补本次实际对象缺口。 |
| **6.8 提供英文草稿** | 根据用户中文生成对应英文，不新增观点或建议；已有适用英文确认复用。中文变化仅处理实际受影响英文，不重翻全部内容。 |
| **6.9 展示实际赛制页面** | 展示本赛制实际 Landing 页面，包括原中文、英文、Feature 名称／颜色／四张牌图顺序和环境栏。图片、交互与实际排列须可审，不用无关示意图代替。准备好实际待定内容即提交，不等待其他赛制或下游发布准备。 |
| **6.10 先做必要技术核对** | 提交前验证实际入口、必要图片显示、牌张对应、顺序及相关链接，并处理版本／缓存问题。复用已有适用检查，不把技术可用性检查转交用户。 |
| **6.11 取得真正未决的确认** | 用户在对话确认机器英文和实际新增／改变的展示；可一次覆盖多个已展示项目。已明确提交的选择与中文定稿直接作为决定，不因后来生成材料而重问。纯文字确认不扩大为尚未展示页面的确认。 |
| **6.12 保存对象与接续位置** | 保存真实输入来源、材料对象和确认范围；第 6 步实际页面及依赖可机械对应到第 7 步候选。材料修订保留旧快照，只处理真实受影响部分，其余成果与决定复用。 |

### 三、哪些内容不用重复确认

- 用户明确给出的 Feature 对象、类别、展示牌和顺序、环境代表牌选择，以及作为最终输入提交的中文，属于用户决定；不要求再回复一次相同内容。明确标为草稿或讨论中的内容不冒充定稿，也不强制使用“定稿”口令。
- 机器证明结构化结果忠实保留可见文字、对象归属、牌张身份与顺序、分条和明确换行；记录原始对话来源，不能伪称用户看过后来生成的材料。
- 实际改变可见文字、含义、归属或顺序，需要按实际变化取得决定；技术转换保持原结果时不增加审批。
- 用户选了哪些牌与用户是否接受实际展示是不同事实，但不能借展示确认重开选牌。机器先修正不符合原指令的落实错误。
- 颜色标识由既定身份规则唯一确定时直接呈现，名称已确定则复用；已展示且沿用的环境栏配置默认接受。
- 用户只确认英文，不推定同时确认尚未接受的新增展示。用户针对实际已展示内容作整体确认时，可以一次覆盖相关维度，不拆成固定多轮问答。
- 第 7 步默认复用本步骤实际页面确认；没有新增差异或实际缺口时，不再安排本批约定赛制整页重审。

### 四、缺口、禁止事项与结束条件

必交输入缺失时只提醒，不推断或代填；不把“没有回复”当作“无 Feature”。不要求重新提交已收到内容，不因技术记录缺失要求用户重复业务决定。具体技术缺口由机器处理，无法核实的状态保留未知，不越过依赖该状态的动作。

不默认建议选牌、类别、环境观点或中文写法；用户明确要求建议／代拟时仅处理授权范围，生成草稿本身不等于接受。不重新采集、修改分类、扩展内容来源、发布或标记周维护完成。

**A．本赛制内容与页面齐备**：必交及条件适用输入齐备，必要技术检查成立，英文与实际展示有适用确认。保留成果，处理其他赛制；整批齐备后接续第 7 步。

**B．存在缺口**：明确所缺输入、确认或技术事实，只暂停依赖动作，其他独立工作继续；不自行分批发布。

**C．已有适用完整结果**：直接复用并接续，不生成空确认。

| 情境 | 合格表现 |

| 有 Feature 且有 Landing 中文，但缺 Feature 单条中文 | 只提醒缺少哪条说明，不从 Landing 自动抽取或代写。 |

| 用户分三条消息补充内容 | 累计保存，仅提醒剩余项，不要求重发整表。 |
| 四张展示牌中一张不在实际主备牌 | 指出具体错误项，其余输入保留；无授权不推荐替代。 |
| 用户按稳定编号选择，材料后来排序变化 | 仍指向原实际对象，不改绑到新的显示位置。 |
| 用户已明确中文定稿及牌张选择 | 保留真实输入来源，不要求为新材料重复确认同一决定；机器英文与实际未决展示仍正常提交。 |
| 第 6 步四赛制实际页面均已确认 | 第 7 步证明对应后复用，不强制第二轮整页验收。 |

## 第 7 步详细行为基准（已确认）

确认依据：用户认可第 7 步结构，并要求补入确认复用由机器证明、无法绑定是技术缺口、技术变化不自动触发人工确认、组合故障优先保留第 6 步成果四项收紧。本节仅记录预期行为，不授权执行维护或开发 Skill。

### 一、职责与机器动作

把第 6 步已确认的各赛制页面复用或组合成固定交付候选，证明已有确认适用于最终组合，并补足剩余技术检查；只对原确认未覆盖且确实需要用户判断的实际内容或展示／交互变化提交补充确认。

| 编号 | 预期行为 |
| --- | --- |
| **7.1 接续已确认结果** | 使用第 6 步确定的正文、英文、Feature、环境栏配置及实际页面确认。上游必需内容缺失时保留缺口，不补写或推断接受。 |
| **7.2 优先复用现成页面** | 第 6 步页面已能组成最终交付版本时直接复用，只补必要组合或依赖；不因进入第 7 步重新生成本批约定赛制页面。 |
| **7.3 保留交付边界** | 整体候选覆盖本批约定赛制，保留第 4 步已交付数据及应保留的其他产品。不重新采集、重分类、重算统计或自行拆分 Landing 发布批次。 |
| **7.4 核对实际落地结果** | 机械核对赛制、周次、正文分条与换行、英文、Feature 对象与类别、牌图顺序、环境栏配置及链接目标符合已确定输入。不重新判断观点或选牌好坏。 |
| **7.5 复用技术证明** | 对象及相关依赖未变的适用检查直接复用；只补缺少的或因实际变化失效的证明。候选编号、日期、SHA 等本身不触发重跑。 |
| **7.6 固定实际页面对象** | 最终页面及实际依赖形成可定位的确定版本。第 6 步确认须能机械对应到候选中的实际赛制页面，不能只绑定内容数据。无法证明对应关系时处理技术证据缺口，不自动要求用户重新确认。新修订保留旧对象及仍适用确认，不覆盖已审材料。 |

### 二、技术检查范围与顺序

以下是应成立的结果，不是每次必须重跑的清单：

| 对象 | 必要结果 |
| --- | --- |
| 内容落地 | 中文、英文、分条、换行、Feature 归属符合已确定输入，没有遗漏、重复或串赛制。 |
| 图片与资源 | 图片能实际显示，牌张和顺序正确；文件存在或 HTTP 成功不能单独证明。 |

| 页面组合 | 组合没有引入资源冲突、错误绑定或影响使用的展示问题。 |
| 预览版本 | 用户入口显示本次确定版本；机器处理版本和缓存问题，不让用户排查。 |

顺序：先核对内容与依赖，复用已有证明，再补查实际缺口，必要时提交用户补充确认。本批约定赛制各自内容完整性均须覆盖；相同模板和未变化交互不机械重复测试，不同受影响分支补对应检查。

审计中的工具间剩余时间包含 agent gap 及其他未解释时间，不能全称为模型纯推理，也不能承诺全部消除。模型服务延迟、真实来源采集、依赖下载及远端发布等待可能仍存在；减少无谓触发和重复执行，不隐去外部等待或以其解释全部耗时。

### 二、六项执行约束

#### P1．正常路径不重新探索工具用法

适用于八步中已支持的正常执行路径：使用既定入口和稳定参数约定，不逐次读取源码、探查 JSON 结构或试命令参数来完成相同操作。只有出现具体不兼容或未知故障时，才针对问题调查；调查不扩成全项目认知重建。

- 已有入口足够时直接复用；多个确定性操作仍需模型反复串联时，才补必要薄封装。
- 工具结果提供可定位输出、实际缺项、复用情况和具体故障，避免模型通过多次试读猜下一动作。
- 批量处理可以机械确定的独立事项；不跨过用户业务决定、技术依赖或八步阶段边界。
- 工具能力不足应作为实现缺口，不假定文档指令已使该能力存在，不以用户重复操作来补工具缺陷。
- 不为本目标新建庞大流程引擎、独立授权对象或另一套批次状态系统。

#### P2．短主入口，按当前步骤加载

完整行为基准用于设计及验收，不作为每轮必须通读的执行清单。Skill 主入口只保留阶段定位、关键约束和必要引用，详细说明按当前步骤及实际问题加载。

- 模型默认读取当前范围、材料位置、变化、缺项与下一动作所需的事实摘要；具体对象仅在业务判断、规则表达或排错需要时展开。
- 已知且仍适用的信息不重复查询；不为了恢复下一动作而读取全部历史、其他赛制草稿或无关代码。
- 已有程序能够唯一确定的缺项、资源位置、输入绑定和检查适用性由程序处理；业务判断、必要规则表达、英文翻译和真实异常仍可由模型完成。
- 不以固定工具调用次数、读文件数量或固定文档篇幅作为验收门槛；判断每次读取和模型介入是否必要。

#### P3．固定第 6 步资源准备与页面检查顺序

补充 6.7—6.10，并由第 7—8 步复用适用结果：

确定本次实际页面及中英文资源选择路径 → 核对现有缓存适用性 → 只补实际缺项 → 验证目标文件及目录层级 → 通过既定 HTTP 入口检查实际页面。

- 不尝试已知不适用于该页面的 file:// 路径；候选预览使用既定 HTTP 入口。
- 中文优先资源与英文回退资源在同一次准备中确定，不把英文缓存完整当成中文资源齐备。
- 按实际消费者选择结果核对资源；文件检查先发现缺失或层级错误，浏览器再核对实际选中资源能否加载、解码及显示，并检查有关失败请求或错误。两层检查各自覆盖不同问题，不用文件存在代替实际显示。
- 只处理本次已选对象、页面实际依赖及受影响展示分支，不扩大到所有候选、全部历史图片或无关视口组合。
- 第 6 步已有适用检查不在第 7 步重做；第 8 步仅补发布环境实际可能改变的部分。
- 云端准备前先验证本地最终卡名／图片缓存对最终组合的适用性；成立则复用既有打包和归档路径，不先启动云端重新查询。云端容错步骤成功不证明缓存命中，以实际复用／补取统计或日志为依据。

#### P4．保留输入与失败处续作必须是可执行能力

补充第 3—4 步和第 6—8 步的工具验收：本批必要输入已有效保留时，规则修改、名称／颜色补齐、构建修复和发布续作，不得因所选入口默认行为而重新触发来源抓取。

- 先验证现有保留输入、阶段生成及交付入口能否完成既定路径；只补实际能力缺口，不预设必须另造发布体系。
- 确有输入缺失或来源更新时，只补明确范围；变化按原快照及增量处理规则进入审查，不静默替换已审对象。
- 输出已生成而登记、检查、归档或发布失败时，保留输出，仅续作故障环节；只有实际生成依据变化才使对应生成证明失效。
- 选定输出位置发生明确权限错误时，及时返回具体阻塞并保留已有成果；不得无依据持续重试或让权限失败表现为长期计算。
- 权限处理属于相关操作自身，不新增每次启动全环境巡检；替代路径仍须遵守项目及平台权限边界。
- 不把现有已修复问题再次列作待开发功能；先确认当前行为是否已满足要求。

#### P5．实际复用可观察

声称复用时，从既有操作结果或必要的轻量记录能够定位：哪些输入、页面、资源、证明或发布准备被复用，哪些实际重做。重新生成后结果相同不算复用。

同时观察“复用了什么”和“为了判定可复用实际做了什么及其耗时”。读取既有结果、核对相关输入身份或资源等必要轻量检查可以保留；不能每次重新执行与原生成或验证近乎相同的整套工作，再以结果相同宣称节省工作。复用已有适用依据，不另造每周全面比较。

至少在适用操作中可区分：

- 原页面复用与重新生成；
- 缓存复用与新查询／下载；
- 影响比较使用的固定输入；
- 已有检查证明复用与本次重新检查；
- 查询／续作原发布操作与创建新操作。

正常报告给必要摘要即可，不新增人工台账、完整审计报告或另一套完成状态。观察数据服务于排错和验收，不成为新增业务审批。

#### P6．端到端耗时验收

行为符合性与端到端耗时分别验证。沿用现有日志，必要时补轻量时间戳、阶段和等待原因；不以增加长期监控或独立日志平台为前提。

共同计时边界：从对应用户请求，或使该项任务可继续的最后一项必要用户输入实际到达时开始，不能等模型完成上下文整理、资源检查或预处理后才开始。结束于用户真正获得完整可审材料，或目标结果实际完成，不以中间文件生成作为结束。区间中新增的用户等待与技术等待如实列明，不移动起止点来排除开销。

| 区间 | 起止与需要说明的条件 |
| --- | --- |
| 决策材料准备 | 收到对应请求至完整且可读的实际待定材料提交；不能在缺已知维度时提前停止计时。 |
| 页面制作 | 用户所需决定及中文齐备至实际可审页面提交；区分缓存适用、需要补取资源和真实技术故障。 |
| 数据交付 | 最后一个分类决定至本批数据实际公开；列明适用赛事规模、来源和数据交付前提是否齐备，不能只计分类器合并或旧数据重算。 |
| 发布及记录续作 | 从具体失败或继续请求至对应结果恢复；观察是否无故重复生成、发布或人工确认。 |

区分本地执行、外部等待、用户等待及工具间剩余时间。外层工具包含的子步骤按需要计时，调用数量仅为诊断信息。异步重叠按实际区间处理，不重复相加；未能归因的保留为剩余时间，不能标成纯推理或 Python 计算。

已发出用户问题但机器仍执行独立任务时，不能把整个区间扣为纯人工等待；只单列能够辨认的等待，重叠工作保留在相应活动中，墙钟总时间保持完整。

比较时记录可观察的模型及推理档位、执行环境、是否刚恢复会话、缓存及资源预热状态，以及已有要求中的赛事规模、来源、输入状态和外部等待。无法取得的信息标为未知，不另收集复杂遥测；不要求严格复现旧模型当时的服务状态。条件不可完全比较时，分别报告确定消除的工作和观察到的耗时变化，不把全部时间差归因于 Skill。

墙钟总耗时与各类等待同时报告；工具内部计时不能单独证明模型往返或用户等待减少。若只测局部工具，不宣称整条 agent 路径已提速。

### 四、性能样本与观察目标

| 样本 | 行为验收重点 | 耗时观察目标 |
| --- | --- | --- |
| Pioneer，无 Feature，环境栏有实际未决项 | 已展示配置默认复用，新类型及实际未决项一次列齐，材料齐备立即提交，不插入下游草稿 | 2—3 分钟提交完整待定材料 |
| Pauper，用户决定及中文齐备、缓存适用 | 固定入口、中英文资源一次准备，无正常路径参数探索或无关页面重生 | 5—10 分钟至实际可审页面 |
| 连续小修改：已有本赛制实际页面及适用决定，用户只修改一张 Feature 展示牌；新牌属于该牌表且资源已缓存 | 保留其余输入和决定，只更新相关视觉对象及实际受影响内容；不重译无关英文、不重新筛选候选、不处理其他赛制、不做整份上下文恢复；同一会话随后收到“该区域确认”时直接接续，不重做相同核对 | 从修改消息到更新后的可审区域提交，分别记录工具时间与工具间剩余时间；后续确认轮单独观察，不另设任意硬时限 |
| 分类修改，本批输入及交付条件齐备 | 必需信息提前补齐、累计比较、保留输入生成、整批数据交付 | 最后分类决定至公开约 10—15 分钟观察 |
| 已归档后发布失败，或完成记录写入失败 | 分别只续作发布或补记录，不重新采集、生成或验收 | 记录实际耗时，不另设任意固定时限 |

这些是比较与定位问题的观察目标，不是省略必要验证、突破用户边界或绕过产品要求的理由，也不是新增生产门禁。未达到时说明关键耗时及原因，不宣称性能目标已达到。

重放沿用实际保留材料，但按本次新规则判断预期行为：Pioneer 当时因缺历史验收记录追加的两组已展示配置应直接复用，不能为了复现旧流程再向用户提问。记录赛事规模、MTGO／Melee 来源、输入状态、缓存状态及真实外部等待，避免不同工作量硬比；不从一个样本外推所有维护耗时。

### 五、验证方式与实施边界

1. 后续获准实现后，在隔离环境重放保留输入，验证材料准备、页面及资源路径、复用和具体故障续作。使用固定的历史用户决定作为重放输入，在对应交互节点提供，不伪造新的业务确认；隔离生成不修改已提交材料、完成记录或生产产品，不触发远端发布。
2. 在下一次已授权的实际维护中验证完整数据与 Landing 交付时间。隔离重放不能证明真实网络、队列及生产发布耗时，不为性能测试另发一次生产版本。
3. 实现清单按“现有能力可直接复用／需要薄封装／确需修复”逐项确定，既有正确能力不重写。行为样本必须实际执行，不能以文档或 Skill 结构校验代替。
4. 当前仅留档本补充。后续先形成上述能力对应清单及具体设计，再按用户授权进入实现；不因本节包含验收方法而立即运行重放、工具开发或维护。

代表性行为重放的最低范围：Pioneer 决策材料、Pauper 页面制作及上述连续小修改样本，各至少执行一次真实 Codex／Skill 路径。模型从正常任务入口、必要已有状态及相应用户输入开始，按 Skill 自行执行；不由测试人员逐条喂底层命令代替模型调度，不将未来回复、最终文件和下一步命令提前全部提供。连续小修改样本保留其合理已有页面与决定，与随后区域确认组成同一会话中的连续操作。

记录工具执行及工具间剩余时间，覆盖上下文读取、工具选择和结果提交。纯脚本重放验证机械能力，不能代替真实模型路径；无需新测试平台或为满足形式大量重复运行。该要求属于实现后的代表性验收，不是每次周维护的额外检查。
