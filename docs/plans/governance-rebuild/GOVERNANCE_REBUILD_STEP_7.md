## 一、实施要交付什么

交付一套可以独立使用的新治理：短入口、按任务需要读取的规范、按实际影响选择的必要检查、能复用候选的交付入口，以及 GitHub 内的完整产品归档与恢复。旧治理的文字、调用关系和强制断言一起退出，不以新文档覆盖旧文件后仍让旧工具执法。

本步把“可以完整复用”落实为严格条件：实现本身符合新要求、没有夹带旧授权或固定断言、必要调用能独立成立，才可以留下。没有这个条件就按新需求重写或删除，不先修完旧测试，也不逐项召开保留评审。

### 3.2 业务约束怎样迁移而不保留旧流程

准备阶段只对受替换的混合文件做一份有限迁移对应：**原位置及具体含义 → 新位置 → 相关生产调用是否仍满足**。用原章节标题与冻结提交定位，不只依赖可能重复使用的 DEC 编号。它是一次迁移审阅材料，不成为每个任务必填台账。

必须覆盖现行产品分离、Constructed/Draft、Missing 与零、无牌表与 Unknown、批准赛事与公开输入、统计分母、分类稳定标识、隐私和既有公共路径等有效含义。旧文档中尚未落实的未来方案不能迁成当前要求；发现实质冲突则按 Owner 决策边界说明具体差异，不自行选一个旧版本。

特别区分两类“验收”：分类/名称/输入的业务判断及其有效记录可能仍是产品所需输入，应保留正确含义；为 PR、Gate、阶段启动而设置的授权标记、固定口令和证明链不迁移。不能为了删 Gate 顺带让未批准数据公开，也不能用业务审阅记录恢复逐动作批准。

## 四、检查和运行入口的具体落地

### 4.1 一个薄入口，不建设新的治理平台

建议统一命令入口为 tools/project.py，内部按检查、候选和交付职责拆成少量模块。以下为拟实现接口，不是当前可执行命令：

| 操作 | 输入和效果 | 副作用边界 |
| --- | --- | --- |
| env | 报告当前任务所需运行时和依赖，使用仓库支持的环境 | 不为读文档安装整套依赖；确需安装时按已授权任务和锁定依赖执行 |
| prepare | 按明确目标和批准输入形成/更新候选，复用有效输入与中间结果 | 是否包含外部采集由任务范围决定；不因 prepare 命令自动取得采集权 |
| check | 列出本次必要问题，运行缺少有效证明的相关检查，返回实际结论 | 无需执行、复用、通过、产品失败、执行失败分开表达 |
| deliver | 在既有授权和约定验收下连续提交、PR、合并及适用发布；文档任务止于其真实终点 | 不把自动命令当作扩大授权的入口；发布只提交确定候选 |
| status / resume | 查询已有操作；从未完成处继续 | 查询不重跑产品检查；有副作用的续作先查实际结果与当前范围 |
| restore | 按 Step 6 选择并恢复指定归档，确认恢复结果 | 不重新生成，不自动试退多个旧版 |

这是日常支持入口，不要求每个操作单独新建脚本或 CI，也不要求 Owner 输入这些命令。Codex 使用它们连续执行已授权计划。必要的底层工具可保留，但不能成为绕过相同发布/恢复控制的第二条受支持路径。

依赖仍以现有 pyproject.toml、requirements.txt、requirements-dev.txt、package.json/锁文件为依据，按实际任务使用 Python、Node 或浏览器依赖；不顺带全面升级。Python 当前要求 3.12 及以上。环境不可用时先解决所缺模块，不能把模块加载失败计为产品验证失败，也不因换解释器废弃与环境无关的有效结论。

### 4.2 新检查集从 Step 4 建立

执行映射放在入口的检查模块内，与调用相邻维护；QUALITY 只定义人能理解的资格和风险，不再维护第二份完整命令矩阵。选择依据是实际改动、相关消费者和任务结果，文件路径只是定位信息。必要语义审阅或浏览器操作可以成为结果证明，不强迫全部包装成 pytest。

| 新要求 | 现有实现的处理方向 | 首次实现时要回答的问题 |
| --- | --- | --- |
| R1 页面真实使用 | 按本次受影响页面使用真实候选；仅复用符合要求的浏览器/JS 工具 | 数据是否真正绑定、图片是否解码、颜色是否区分缺失/无色、操作是否有反馈；不把已有 P14 缺陷全修完作为本任务条件 |
| R2/R3 输入和分类结果 | compare_classifier_impact、已确认输入和迁移可以复用；规则内容不触发 K2 全套 | 新输入和必要派生变化是否解释充分，原有漂移结论何时仍有效 |
| K1/K2 计算和引擎 | 从必要业务反例建立小测试，按真实调用选择；旧 fixture 不天然有保留权 | 手算/独立事实正确例成立，错误分母、缺失或优先级错误被发现，合法变化不误报 |
| K3 数据与公开边界 | 可复用明确的 schema、来源筛选、公开打包和安全读写实现；脱离旧全量调度 | 批准对象能使用，应排除对象不能进入真实公开包，合法空状态及消费者成立 |
| K4 交付恢复 | 新候选归档与单一部署器的聚焦验证 | 包可取用，指定包实际提供服务，失败续作不换对象，旧请求不覆盖恢复 |
| R4/G2 文档与入口 | 聚焦语义审阅和直接必要链接/命令检查 | 规则可执行，入口可找到；不检查固定英文句子、标题顺序或全仓链接 |
| G3 选择、复用和续作 | 重写旧 admission 的相关职责 | 必须运行的真的执行，必要失败不放行；合法零项、有效复用成立；查询失败不重测产品 |

validate_repository.py 当前混合文件检查、历史目录和测试登记等要求，整体调度退出。validate_schemas.py、validate_output_invariants.py、validate_production_candidate.py、validate_melee_candidate.py 等按需要拆出符合新设计的调用；不能把旧 --full 或 --full-candidate 包装成新的默认 check。

tests/test_ci_master_admission.py、test_ci_workflow.py、test_github_publication_preflight.py、test_validate_repository_modes.py、test_documentation_history.py 作为旧控制的实现依赖一起退出或按新职责重写。其它测试也从新清单选择最小实现；删除不再承担必要职责的文件、无调用 fixture 和选择入口，不把它们搬入 legacy_tests 继续随时运行。

不维护固定测试总数。触发后严格取得必要结论；检查本身错了按独立预期修正，不能通过更新 golden 或删断言消除未解释差异。选不到适用检查时先聚焦确定风险，不能自动全量或假装通过。

### 4.3 G1 状态体积的最终建议

采用 Step 4 的 **120 个非空行、6,000 个字符**作为整理提醒预算，**不把超限直接设为阻断**。必要当前信息合法增长时，即使整理后仍超限，也不能删事实或要求 Owner 例外。

实施时用正常单任务、多个必要阻断/恢复信息、历史流水误塞入 STATUS 三种小样核对：正常与必要增长不被阻断，历史膨胀能被提示并引导迁出。是否遗漏真实当前状态由本次 R4 审阅判断。这个选择保留低成本防膨胀作用，同时避免数字本身再次取得错误阻断权。

### 4.4 复用记录的最小范围

使用候选说明和已有检查输出保存：回答了哪个问题、实际对象/相关输入与实现、结论及其来源。能从现有产物或操作记录得到的事实不重复抄写。没有影响的提交号、工作区或 PR 变化不使结果失效；真正相关的代码、输入、依赖和组合变化才补对应证明。

自动化无法判断某个结论是否适用时，由 Codex 聚焦核对并给出事实依据；不建立 Owner 签署摘要或精确父提交认证链。供部署读取的候选说明须来自可信的已授权准备过程，不能任意上传一个自称通过的文件就取得发布资格。来源可信和产品预期正确是两件事，两者均按实际需要确认。

## 五、仅使用 GitHub 的归档与发布方案

### 5.1 推荐：专用私有仓库的 Release 附件

建议归档仓库命名为 **Jacelber/mtgo-data-releases**，只存完整候选/恢复包、必要清单和很小的运行状态。不把二进制包提交到产品 Git 历史，不采用 Git LFS，不引入外部存储。具体仓库名可因重名调整，不改变设计。

- 每个确定候选一个不可混淆的标识；上传完整包与 manifest，完整上传并核对后才登记归档完整、可取用。归档成功不等于质量通过或获准发布。相同标识下不覆盖包内容；有变化就形成新候选。
- 未验收候选、失败候选和内部说明不出现在公开仓库的 Release、PR Actions 附件或日志中。私有归档中的产品包也只含相应部署需要的内容，不能借私有存储夹带源响应或凭据。
- 正式版本和未发布候选按 Step 6 的固定保留、30 天、结束后 7 天策略处理；不设一个会误删当前版/适用前版的全局到期规则。
- 恢复读 Release 附件，不依赖当初运行仍存在。Actions artifact 只作本次传递给 Pages 的临时载体，过期后可以从归档重传。
- GitHub 自带的 source code zip 不是产品恢复包。包只包含实际部署文件，不执行旧版仓库脚本。

GitHub 官方资料明确 Release 附件单文件须小于 2 GiB，每个 Release 最多 1,000 个附件，未规定 Release 总大小或下载带宽上限。这满足本方案的存储形态，但不构成永久服务或无限滥用承诺；实施时仍核对真实完整包体积和保留数量。[Release 附件限制](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)

成本设计不购买新服务、不启用付费存储或更大 runner。归档仓库不运行定时计算；生产 Actions 继续使用当前公开仓库的标准 runner。公共仓库标准 runner 与私有仓库运行的计费边界不同，临时 Actions 产物也不同于 Release；不把账户未核实的额度说成已经够用。[Actions 计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

本轮可见最新 Pages 附件约 57.1 MB；仅作量级估算，若正式包近似且每天一个版本，30 天约 1.7 GB，另有固定保留版本和必要候选。该数值是 API 中传输附件大小，尚未下载核对新归档格式、解包大小或长期发布频率，不能当作最终容量结论。

实施 U4 前核对实际包尺寸、预计 30 天版本数量和账户适用限制；无须人为生成一批历史版本测成本。若真实限制要求付费、换平台或缩短恢复承诺，给出具体变化供 Owner 决定，不静默降级。

### 5.2 访问权限

产品仓库的 GITHUB_TOKEN 默认只访问本仓库，不能假定能读取新的私有归档仓库。[GITHUB_TOKEN 范围](https://docs.github.com/en/actions/concepts/security/github_token)

建议使用仅选中归档仓库、具有必要 Contents 读写权限的细粒度令牌，不扩大现有个人凭据到所有仓库，不要求用户把密钥贴入聊天。云端凭据放入产品仓库仅允许 master 分支的归档 environment secret，由可信归档/交付作业使用，不新增人工 reviewer。持有凭据的作业不检出或执行候选代码；PR 验证、生成、测试和预览环境不取得归档写入凭据。环境限制与作业隔离须实际落实，不能仅以“受控 secret”命名代替。只读使用与写入步骤按需要限制可见范围；凭据有效期和续期方法明确记在运行说明，失效时只处理该能力。[GitHub 环境与凭据规则](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

未合并的私有候选采用以下交接路径：

1. 在不持有归档写入凭据的隔离环境中，使用本次准备分支生成并检查候选，固定候选包、manifest 和相关结论。
2. 将固定候选作为数据交给在独立凭据环境中运行的可信上传器。上传器核对交接对象和完整性，只上传、不执行包内脚本，也不重新生成产品；生成/测试环境不能访问其归档凭据。
3. 完整上传并核对后登记该候选可取用；入库不替代必要质量证明，也不赋予发布资格。
4. **本地审阅不以第 2—3 项上传完成为前提。** Owner 可在符合批准可见范围、且不持有归档写入凭据的本地环境中，审阅同一确定候选。需要跨环境取用、验证归档取回能力或本地副本不可用时，再从私有归档获取；不将上传和重新下载设为所有本地验收的必经步骤。正式发布前仍须完成 Step 6 要求的完整云端归档及恢复准备。后续发布继续定位该候选；必要内容变化按 Step 5 形成新候选，只补受影响结论。

首次实施时，可信上传器可采用已完成聚焦验证的固定准备版本，在独立环境中运行，不要求为了取得上传能力提前合并治理改造。正式云端作业启用后遵循上面的主分支 environment 限制；本地可信工具与云端作业均不能让待验收代码取得上传凭据。U4 负责证明候选交接、受控审阅及权限隔离实际成立，不用 master 重新生成另一份候选解决交接问题。

创建私有仓库、配置该凭据及下面的云端设置属于将来实施计划的具体资源范围，本轮不执行。Owner 接受本方案并明确启动含这些事项的实施后，不再逐个业务动作索取同样授权；实际凭据创建或安全策略需要人操作时，只交代那个不可替代动作。

### 5.3 最小状态与包标识

归档仓库保留一个很小的控制文件，建议 state/pages.json：当前已知部署操作、实际包、产品确认结论、适用前版引用，以及尚未结束/已失效的相关写入和待处理恢复意图。每次写入使用现有版本的条件更新防止覆盖并发修改；不把整个 PR 证据、任务历史和所有测试结果塞进去。

控制文件是协调记录，部署事实仍须由平台和实际服务核对。更新失败不抹去已经发生的部署；续作先恢复真实状态。每个候选 manifest 记录文件清单和完整性信息；实际服务需要一个不含私有信息的版本标识，不能用当前 master SHA 强行要求旧包恢复与新代码来源相同。

包标识、部署操作标识和“已确认可用”分开。B 已上线但产品确认失败时，记录 B 的实际部署，保持 A 的适用恢复引用；不能等 B 变绿才承认版本改变。

恢复意图由 Owner 指令触发，关联指令对应的线上操作、恢复目标及当前处理状态。恢复完成、Owner 撤销或执行范围已失效时更新意图，不能留下过期恢复请求阻挡单次任务发布。另以 `automatic_publication_pause` 保存回滚附带的自动发布暂停；意图结束不解除该暂停，解除仅依 Step 6 的明确指令或提前授权。作业取消、被队列替换或超时不构成撤销恢复决定的依据，意图结束也不等于未知远端写入已停止。

### 5.4 所有生产写入只走同一部署器

重建 .github/workflows/pages.yml 为部署入口：只接受确定的归档候选/恢复目标，下载、核对、传给 Pages、查询和确认；不抓取、不分类、不计算、不生成图片缓存。正常发布和恢复共用目标级并发组，保留 master 环境限制与最小 Pages 权限。

内容生成移至候选准备，授权发布由 Codex/已授权入口调用。单纯合并治理文档不触发站点生成部署。受批准的定期数据工作仍可连续执行，但必须形成对应候选并使用同一发布入口；原业务审阅条件不因自动流程失效。

并发控制覆盖“核对有效范围 → 实际写入 → 远端副作用可判定”。后续运行开始时先处理上次未结束操作；不能因 runner 退出、锁释放或超时就认为远端不再写入。恢复使冲突的待执行操作失效；操作是否有效既看当前授权，也看部署操作基准，A→B→A 不会让旧请求重新生效。

不能依赖 Actions 天然按先来后到或恢复优先执行。默认并发组可能用新 pending 运行替换旧 pending；因此被取消/替换的任务保留可续作事实，不能报告已经发布，也不为排队被替换重新跑产品验证。[并发组行为](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

可信入口先可靠登记符合既定条件的恢复意图及其对冲突发布的失效作用，再提交恢复部署请求，不能等恢复作业取得执行机会才登记。登记与普通发布取得写入权之间须正确协调：普通发布在取得写入机会时识别仍有效的恢复决定，不能越过它继续写入；已经发出的远端操作仍按实际状态处理。

恢复运行被平台取消或替换时，已登记意图仍保留，由当前有效任务的 resume 从未完成处继续处理，不要求 Owner 再批准同一恢复，不静默丢弃请求，也不创建永久后台监控。U5 验证“恢复仍在等待时普通发布到达”的情境：意图不丢失，普通发布不能越过，当前有效任务能够续作；同时验证恢复完成、撤销或失效后不会遗留永久阻断。

平台上具有相应权限的操作者仍可能绕过受支持入口；历史工作流重跑并不只限于管理员，具有仓库写权限的人员也可发起。新方案保证受支持入口一致，保留权限边界并检测实际状态变化，不宣称消除了所有账户外部写入可能；不为治理重建额外授予更大权限。历史重跑的具体退出边界见第六节。

### 5.5 部署失败和部分更新：核实结论与实施判定

已核实 Pages 动作部署先前上传的完整 artifact，并提供状态/取消能力；当前仓库没有自己逐文件向生产主机覆盖的脚本。但这不足以证明平台所有故障及缓存传播情况下始终原子切换。本轮未对生产制造故障，也未把未证实的原子性当作保障。[deploy-pages](https://github.com/actions/deploy-pages)、[Pages 状态与取消 API](https://docs.github.com/en/rest/pages/pages)

实施 U5 必须覆盖以下分支：

| 实际情况 | 处置 |
| --- | --- |
| 写入前失败且实际仍是原版本 | 从归档/传输失败处修复，原线上不动 |
| B 已实际部署，必要产品确认失败 | 记录 B 的事实，在授权范围内诊断修复；仅在 Owner 下达回滚指令后恢复 A，并暂停自动发布 |
| 操作还在执行、查询超时或传播中 | 保留未确认状态，继续有依据的查询；不发冲突写入，不仅凭暂时读到旧内容认定未执行 |
| 确认出现部分更新或混合服务 | 明确记录实际受损范围和对应操作，先处理未结束写入；不伪造完整版本事实，不自行决定回滚；已有 Owner 指令则核对对象和冲突后执行 |
| 无法确认操作归属、当前对象或排除其它写入 | 不能自动扩大回滚；继续范围内诊断，确需改变恢复范围时提交具体决定 |

部分更新情境先在隔离目标/模拟平台边界中验证识别、停止冲突写入和续作行为，再核对实际 Pages API/产物传递。U5 需要落实 Owner 指令下的恢复执行路径；无法识别对象或排除冲突时明确障碍，不能伪造完整版本事实，也不能用一次成功部署证明所有失败都原子。按 2026-09-12 Owner 修订，工具不作是否值得回滚的判断；解除自动发布暂停也须依据明确指令或提前授权。

机制验证不主动损坏生产。若需要 GitHub 平台上的端到端验证，限用合成公开样例的专用 GitHub 验证目标；在 U1 明确其精确资源名称和清理范围，纳入实施说明，不使用真实私有产品作公开预览。验证需要新增资源或费用超出已确认实施范围时才提出那个具体变化。

## 六、旧内容退出的有限清单

| 旧入口 | 统一切换时的处理 |
| --- | --- |
| AGENTS、CLAUDE、Copilot 指令 | 全文替换为新布局；不保留旧规则作为后半篇说明 |
| DEVELOPMENT_WORKFLOW、TEST_TRIGGER_MATRIX、GOVERNANCE_REMEDIATION | 新文档/入口接替职责后删除旧文件和默认链接 |
| DECISIONS、旧 MELEE_EVENT_ADMISSION_RUNBOOK | 有效业务含义迁入第三节对应位置后删除旧混合文件；不另存一份可引用的旧治理备份 |
| PR 模板、README、ROADMAP、STATUS 及其它实际入口 | 去掉声明令牌、按阶段重新授权、STOP point、精确父链等旧控制；只保留对应职责的当前信息 |
| ci_master_admission、旧 publication_preflight、validate_repository 全量调度 | 删除或重写职责及所有调用；真实凭据/仓库权限诊断可独立复用，不携带旧 PR 声明审查 |
| 四个工作流、npm 支持命令、相关测试选择 | 同一版本接入新入口；不留下旧 workflow_dispatch、schedule 或过期后续作入口继续执行旧逻辑 |
| 切换前生产写入工作流的历史重跑 | 受支持的 resume、自动续作和操作说明不再重跑这些旧写入工作流；历史事实和有效产物由当前可信入口读取、判断和续作 |
| 旧治理审计/历史文件 | 从工作树删除纯旧治理记录，如 CI-MASTER-ADMISSION、GOV-06/07/08 审计、GOVERNANCE-EFFICIENCY 历史及其链接；只用 Git 历史保留，不迁入另一活动目录 |
| 混合历史、PROJECT_NOTES、业务审阅材料 | 只处理实际承载或被引用的旧治理内容；必要业务事实先迁移。不能用“历史”二字批量删除独立业务证据、原始数据或分类产物 |
| 项目专用 skills、保存的提示和自动加载规则 | 有限定位本项目实际使用的入口并移除旧 Gate 影响；不是全电脑、全账号清理 |

补查以引用和调用为边界：文档链接、工作流命令、脚本导入、测试选择、项目工具的自动加载。发现新入口就纳入对应删除单元，不另开一轮全仓历史审计。

一次性切换核对须区分“切换时已在途的旧运行”和“切换后重新发起的历史运行”。GitHub 重跑沿用原事件的 GITHUB_SHA、GITHUB_REF 和最初触发者权限，不能因为当前工作流文件已更新就认定历史重跑会采用新逻辑。需要历史成果时，由当前入口读取仍有效的候选和结论，再按新机制执行；不恢复旧写入代码、旧生成流程或旧授权判断。[GitHub 重跑规则](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)

这不是“同一失败 head 禁止重跑”的旧规则：当前机制的安全重试和单步续作仍然允许。无需删除历史运行、改写历史失败，也不为每个普通任务增加历史审计。平台界面仍允许相应权限人员发起的旧重跑能力须如实列为受支持入口之外的写入能力，不能宣称更新 YAML 后已从技术上彻底消除。

当前会话已实际出现旧阶段授权的项目说明和记忆提示，说明仓库外入口也有风险。实施时列清来源：仓库映射内容随新入口更新；项目专用外部配置在明确范围内更新；记忆修改及全局设置必须按其独立能力和明确授权处理。本方案不把删仓库文件冒充已清理这些来源，不修改其它项目或擅自编辑记忆系统。若外部内容仍会被默认注入并实质控制本项目，整体切换不能宣称完整退出；应给出最小具体变更供 Owner 决定。

已打开任务中读过的历史事实不要求抹去，但其旧授权和停止规则不再有权威。切换后用重新加载当前项目入口的实际检查确认没有旧文档/提示继续指挥执行，而不是要求每个新任务手工声明“我不遵守旧 Gate”。

以下 U1—U7 是同一已授权整改内部的工作分解，不是七次启动审批。准备提交可以分开，正式生效只在 U7。文件确需扩展时说明实际依赖并登记；改变业务或制度取舍才返回 Owner 决定。

| 单元 | 范围与交付物 | 依赖 | 当场完成的验证与结束条件 |

| U3 检查入口与环境 | tools/project.py 及少量模块；QUALITY 调用映射；运行依赖入口；合格的最小测试与 fixture；ci.yml 和旧控制脚本的替换 | U1；沿用 U2 的新职责 | 对实际新增/修改的检查证明正确例、错误例、合法变化；G3 选择和有效/失效复用成立；文档任务不装浏览器或跑核心套件 |

生成器、业务筛选和页面代码不是任意重构范围。为了候选/发布解耦所必需的接口改造可在 U4/U5 进行；纯业务算法、分类规则、赛事接纳、P14 图片/颜色修复不纳入本次。必要兼容调整须说明为什么是新入口实际运行所需，不能把所有关联产品改动吞进治理。

U2—U5 可以在依赖已满足时交错推进，不要求等所有文档或所有代码写完才验证。验证过且未受影响的结果到 U6/U7 继续复用；不在最后再安排一次全量测试“保险”。各单元必要验证失败时停止受影响完成/交付，范围内有依据的诊断和修复继续。

真实部署产物的首次保存不等到 U7：U1 获实施授权后尽早保全，U4 纳入受控云端归档，U7 再确认最终适用性。U4 未就绪时可先受控本地保存完整包及来源，但这只是临时保全，不等于云端持久恢复能力已经成立。提前保存不让新治理提前生效，也不使旧包永久保持“当前版本”身份；取不到完整包时按 Step 6 处理首次恢复限制，不重新生成冒充历史产物。

## 八、统一切换的实际顺序

Git 提交可以将仓库文件一并切换，但 GitHub 设置、运行中任务和归档不是一个原子事务。因此采用一个短、明确的生产写入切换窗口，期间站点继续服务已有版本；不建立长期 staging 门禁或每次发布的人工窗口。

1. **先准备完整可审阅版本。**U6 提供新入口、业务迁移、删除清单、有效验证、外部资源与首次基线方案，明确尚未解决项。缺少必要实现或质量结论时先修复，不能请 Owner 批准空白后再补。
2. **完成实施验收后连续收尾。**按第九节约定验收；验收后提交、PR、范围内修复、合并、必要设置与发布确认在原授权内连续完成，不重新逐动作申请许可。
3. **暂时停止相关生产写入。**只暂停可能按旧机制写入的 Pages 和相应自动写入入口；识别旧 workflow run 的提交版本、排队和远端部署状态，必要时取消并确认。已发请求仍可能写入时不进入竞跑式切换。同时核对切换后的受支持续作路径不会发起历史旧写入重跑，并如实列明平台仍存在的外部操作能力。普通设计及其它独立准备可以继续。
4. **确认切换时最终真实基线。**在 U1 保全、U4 归档的基础上，核对当时实际线上对象、覆盖范围和已知限制；必要时补取并归档最新真实已部署产物。不能只凭提前保存就将旧包视为当前基线，也不能从 master 重新生成后冒充旧线上。若旧包确实不可取用，先形成明确的首次恢复限制和失败方案；不得带着未处理缺口覆盖线上。
5. **应用同一套新入口。**合并一致的切换版本，正式文档、CI、候选、发布、恢复和旧内容删除一起生效。保持历史防删除/非快进规则和 Pages 的 master 限制；不增加 Owner reviewer，不凭当前没有 required checks 推断日后也没有。只有复核发现实际阻碍已确认新设计的旧设置时才按批准范围调整。
6. **落实仓库外已确认入口。**同时替换本项目实际默认加载的旧提示/专用规则；不能先恢复普通工作，再让每个任务碰到旧要求后解释例外。超出明确权限的具体缺口如实报告，完成不受影响工作。
7. **确认真实新流程。**新部署器优先使用已保存的当前产品包验证传递和服务对象，不重新抓取、分类或修 P14。需要加入版本识别文件时先形成明确的新候选，确认这项新增差异，再按计划交付；不声称改过内容仍是字节相同的旧包。只做适用产品确认，复用原有效计算和分类结论。
8. **恢复受支持任务入口并收尾。**确认切换时在途旧写入已得到处理，受支持入口不会重新执行历史旧写入工作流，新发布/恢复入口和状态引用成立，再恢复原有获准自动工作的运行安排；不意外新增采集或发布权。平台外部操作能力按第六节如实说明。记录哪些机制已落地、哪些实际效果仍待 Step 8 观察。

切换窗口的开始与结束由 Codex 按已授权方案报告并执行，不成为新的授权关口。技术中断不靠“最多两次”停工；没有有依据的下一步时按 Step 2 如实报告事实和未知。

若新治理激活后发现执行缺陷，修复新机制，必要时保持受影响生产写入暂停；站点问题按适用完整产品包恢复。**不回退整个切换提交，不重新启用旧治理脚本、旧文档或旧门禁。**其它不依赖故障入口的工作仍可继续。U7 的旧治理退出和必要运行能力未成立时，不宣称整体整改完成。

## 九、人工验收点与任务结束

设计阶段：本步先交 Owner 审阅、必要小修与验收；随后完成 Step 8 设计，再决定开始整体实施。已确认的第一至六步不因第七步细化重新逐项验收。

建议未来整体实施只设置一个切换前人工验收点：**U6 的完整准备成果**。届时 Owner 判断新制度是否符合已确认方向、业务含义是否完整、资源和恢复取舍是否符合计划；Codex 在提交验收前负责技术验证。若 U1 发现会改变既定方向/范围/权限/恢复承诺的具体问题，依原有限决策边界提前提问，不拖到最终验收，也不把每个技术发现升为审批。

U6 验收后按原范围连续完成 U7 并报告真实交付结果。新差异只对影响 Owner 判断的部分重新提交，不因合并、工作区变化或一次基础设施失败重新整体验收。待验收对象及其判断依据保持稳定，与之无关且不依赖其结论的工作才可继续。

U6 的完整准备成果包含 U4 的实际候选交接和已保全产物归档结果，以及 U5 的恢复排队/结束情境结论；U7 对最终基线和实际入口的核对仍按第八节进行。这些是原实施验收对象的具体内容，不新增 U1/U4/U5 人工审批。

实施完成须同时满足：正式入口独立可用、有限检查正确触发且支持复用、实际候选/归档/发布/恢复能力成立、必要业务含义未丢失、旧治理不再被默认加载或执行、云端写入和首次恢复边界没有未处理缺口。不能只按删了多少文件或 CI 绿色宣称成功。

效果是否改善由 Step 8 在获准真实开发中观察，实施验收不伪造长期效果。第八步设计应明确观察取样、成本/误报/漏检和汇报方式，不增加填报门禁、定时审计平台或 P14 清零任务。
