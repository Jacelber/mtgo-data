## 一、一页新治理原则

### 1. 以交付效果衡量治理

治理服务于持续交付可用、含义正确的产品，并降低用户协调和故障恢复成本。检查数量、绿灯数量、记录完整度不能代替这个目标。评价时同时看实际交付效率、真实错误发现、误报、重复劳动、用户技术介入、恢复效果和治理总维护成本。

### 2. 采用 C 模式，按实际风险检查

检查分为本次交付结果、受修改影响的核心机制，以及少量保障开发效率的治理检查。只有明确的触发条件和具体风险才产生验证要求；未受影响的内容不因项目规模或陌生路径而自动全量重测。必要检查没有通过，不能交付；没有执行成功，也不能声称通过。

### 3. 按已确认计划连续完成

详细计划确认并获授权后，Codex 推进至约定验收点；验收后继续完成同一交付的技术步骤。模糊目标先明确计划，除非 Owner 明确完全放权。普通故障和范围内修复不撤销任务授权，不以固定失败次数或技术阶段产生重复请示。

### 4. 由合适的人承担判断

Owner 决定业务含义、目标范围和体验是否接受；Codex 负责实现、技术验证及已授权范围内的故障处理。只有涉及新的业务或范围决定、需要新增或扩大授权、改变已确认的治理原则／质量底线／恢复策略，或缺少无法自行查明的必要信息时，才向 Owner 提交具体问题。按已确认标准修正错误测试或删除不合格检查属于执行；改变该标准本身属于制度取舍。真实平台限制如实说明，不伪装成项目自行设置的审批。

### 5. 新治理完整替换旧治理

旧 Gate、授权阶段、停止条件、模板和执行要求不自动继承，也不补充解释新规则。迁移有效业务含义时不携带旧流程。旧治理从活动入口、文档和执行机制中退出，不设恢复开关或活动副本；Git 历史只保存过去事实。

### 6. 围绕相关对象复用成果

复用仍有效的输入、候选和验证结果；仅相关代码、输入、环境或组合风险变化时重新验证受影响部分。故障从失败处处理，不默认重新抓取、生成和全套测试。保持过程与结果如实可查，不为证明复用而建立更昂贵的重复台账。

### 7. 恢复产品，不恢复旧制度

保存能够恢复的完整可部署产品版本；产品恢复不依赖重新抓取、分类和生成，并防止旧发布覆盖恢复结果。新治理故障按新原则处理，必要交付条件无法满足时暂停受影响交付；不恢复整套旧治理。

### 8. 让规则保持简短、独立和可执行

一个明确的治理入口，按当前任务读取必要规范。整体设计后分块实现与验证，再统一切换；正常开发中的效果观察持续校正设计。步骤、文档和实施单元本身不形成额外审批。新规则缺口不能转而引用旧制度填补。

## 二、重建范围与业务边界

### 2.1 重建治理所包含的内容

后续在获授权的对应步骤处理以下内容，本步不实际修改：

| 内容 | 重建设计的对象 |
| --- | --- |
| 人与代理的协作 | 计划、授权、验收、技术责任、续作和停止条件 |
| 质量保障 | 检查目的、触发、独立预期、阻断资格、验证复用 |
| 任务运行 | 工作环境、工具入口、失败重试、成果保存与并发处理 |
| 发布与恢复 | 候选到发布的关系、可恢复产品版本、恢复中的并发控制 |
| 规则载体 | 主入口、其他代理适配、手册、模板、状态记录及历史引用 |
| 可执行治理 | 脚本、CI、发布依赖、治理测试和相关 GitHub 设置 |

范围按内容的作用判断，不按文件所在目录判断。产品规范中夹带的“每阶段另行授权”等规定同样属于治理替换对象。实现代码中具有同类作用的判断，也不能因不在文档里而自动保留。

### 2.2 不借治理重建改变的业务含义

本次治理重建不授权新增产品、重定义统计、改分类结论、接纳新数据或修复 P14 产品。以下是需继续保护的业务含义示例，不是新增测试清单：

| 业务含义 | 与应退出旧流程的区别 |
| --- | --- |
| MTGO 与 Tabletop 的数据和统计保持来源分离 | 不因此要求两个产品任何变更都绑定验证和审批 |
| 只处理已批准来源与赛事范围 | 来源范围的批准不等于每个技术阶段都需要重新批准 |
| Constructed 统计排除不适用的 Draft 结果，未知轮次不冒充已确认结果 | 保留统计含义，不自动继承所有旧校验和步骤 |
| 缺失不等于零，不可用牌表不等于 Unknown 分类 | 保护含义；由后续设计决定最小有效检查 |
| 已确认的分类语义、稳定标识和已验收迁移不得被治理修改悄悄改变 | 不冻结每个实现文件、摘要算法或旧验收载体 |
| 已批准的公开范围、数据保留和隐私边界继续有效 | 不把某份旧运行手册整体提升为新治理权威 |
| 用户已经使用的产品入口和兼容性要求不因治理重建无意破坏 | 若确需改变产品约定，作为明确的新范围决定处理 |

提取业务约束时，只将当前有效且执行所需的含义整理进对应新规范。不能把同一文件中的历史阶段描述、过去状态或旧审批一起迁入。名称叫“统计规范”“架构规范”也不构成整份保留理由。

### 2.3 当前第 1 步的实际写入范围

- 新建本设计文档。
- 更新总计划的当前授权、步骤状态和本成果链接。
- 不修改项目的 AGENTS、STATUS、ROADMAP、规范、工作流、脚本、测试和产品文件。
- 不启动测试、抓取、生成、提交、PR、合并、部署、定时任务或记忆更新。

这一区分来自用户“授权第一步”的具体范围，不是旧 Gate 的额外审批要求。

## 三、权威按职责分工，不再形成历史规则叠加链

以下是新体系的设计目标，实际入口和文件布局在后续整体设计中确定。

| 信息 | 负责回答的问题 | 不得承担的作用 |
| --- | --- | --- |
| Owner 当前明确指令及已确认计划 | 当前目标、授权范围、验收点和具体选择是什么 | 不将只授权第一步解释为授权整项实施 |
| 新治理规范 | 如何计划、验证、执行、处理故障和完成交付 | 不悄悄改变业务含义，也不引用旧治理补缺 |
| 新体系中的有效业务规范 | 产品、数据和统计应该表达什么 | 不夹带平行的审批、Gate 或自动停止体系 |
| 当前状态记录 | 已知项目状态、未解决决定和当前工作是什么 | 不创造、否定或重复登记用户已经给出的授权 |
| Git、运行记录及实际产物 | 哪个版本、动作、结果实际存在 | 不将事实记录视为新增工作授权或产品正确性证明 |
| 旧提交、历史 PR、旧对话摘要和记忆 | 帮助定位事实与旧问题 | 不恢复旧制度权威，不覆盖当前用户决定 |

具体指令对范围有明确限制时遵守限制；授权措辞看实际含义，不要求固定口令或同意后再同意一次。已确认计划的修订在原有计划中记录，不让多份摘要分别产生不同流程。

若发现矛盾，先区分事实过期、治理残留与需要作出的新决定：过期事实核实更新，旧治理残留按替换范围处理，其余情况依据原则 4 的统一决策边界判断是否向 Owner 提问。不得把所有矛盾统一转成审批，也不得将涉及该决策边界的变化擅自当作纯技术修复。

## 四、过渡约定：实施不被被替代制度循环阻断

### 4.1 当前设计阶段

只输出设计材料；已授权第 1 步无需先建立 PR、修改 STATUS 或完成旧 Gate 才能开展。草案不自动成为全项目操作规则。当前明确范围优先于总计划里历史记录的阶段状态。

### 4.2 将来的实施准备阶段

完整设计确认并获得对应实施授权后，计划内明确要替换的旧治理要求不能再作为“必须先遵守它，才能删除它”的前置条件。Codex 按批准设计准备新文档、工具、检查及退出内容，分块实现并及时验证。

旧脚本或 CI 若仍强制要求旧声明、旧测试或逐阶段授权，应作为已纳入替换范围的实现依赖处理。不能凭口头说明将失败标绿，也不应为了获得旧制度许可而新建一串无产品意义的补锅任务。实际的替换方法、路径及 GitHub 设置顺序在第 7 步明确。

上述过渡仅覆盖已授权治理重建任务，不自动授权无关产品工作或修改所有系统设置。真实平台权限、凭据要求与用户信息保护不因新规则设计而消失；能在既有授权和工具能力内解决的技术问题自行处理，确实需用户操作时报告准确原因。

统一切换前，与本次治理重建无关的普通项目工作，仍按当时正式生效、且未被 Owner 明确取消或覆盖的规则执行。局部新治理不提前生效。本过渡约定仅处理已授权治理重建与待替换规则的冲突，不重新激活已废止要求，也不赋予旧治理在切换后继续生效的权威。统一切换前后的权威关系必须明确，不能将一半新规则与一半旧 Gate 拼成长期混合制度。

### 4.3 统一切换及之后

入口、规范、模板、执行脚本、工作流和对应检查按已批准顺序成组切换。旧规则清除是切换内容，不能推迟为“以后再清理”。实际 GitHub 设置如需多个动作完成，应在切换设计中明确单一有效规则与操作顺序，而不是假定天然具有原子性。

切换后只保留新治理权威；不设旧制度恢复方案。旧规则只存在于 Git 历史，不通过默认读取、活动副本、模板或脚本继续影响执行。必要业务含义已经迁入新规范，不需要再依赖旧治理文档。

### 4.4 新规则尚未定义的情况

技术细节能依据已确认目标、范围和原则确定时，由 Codex 处理并如实记录必要结果。需要向 Owner 提问的情况统一依据原则 4，一次只提出一个具体问题。不默认运行全套测试，不要求固定次数重试后再授权，也不回到旧 Gate 寻找答案。

## 五、情境推演：只检查设计自洽，不是项目测试结果

| 情境 | 本原则导出的行为 | 检查的矛盾 |
| --- | --- | --- |
| 用户只授权八步中的第一步 | 完成本步材料并提交验收，不自动开始第二步或仓库实施 | 整项授权原则不能扩大明确限定的当前范围 |
| 本地验收后，GitHub 查询临时 500 | 在同一任务内处理查询故障并复用有效结果；真实未知不能说成通过 | 技术故障不能撤销任务授权 |
| 新文档删除旧 Gate，旧措辞测试因此失败 | 按已批准替换范围处理旧测试和调用链，不要求新文档恢复旧措辞 | 旧测试不能反向取得新规则设计权 |
| 必要交付检查发现统计含义错误 | 阻止本次交付，范围内修复；若修复需要改变业务含义，提出新决定 | 连续执行不等于失败也上线 |
| 产品规范中同时写来源分离和逐阶段审批 | 迁移来源分离的有效含义，逐阶段审批随旧治理退出 | 业务文档不能成为旧审批的隐藏入口 |
| 主分支新增无关文档，但候选相关输入未变 | 按实际影响处理并复用结果，不自动重新生成和全面测试 | Git 身份变化不能等同全部成果失效 |
| 新治理切换后发现运行入口缺陷 | 按新原则修复；必要条件未满足时暂停受影响动作，不恢复旧制度 | 恢复能力不能成为保留旧治理的理由 |
| 平台拒绝某项写入，现有授权内存在可行替代 | 采用授权内替代；若确需用户操作则说明真实来源与动作 | 项目规则无法取消实际平台限制，也不能借此重复请示无关步骤 |

推演结论：上述原则能够区分范围限制、质量失败、技术故障、业务决定和平台约束；没有“未规定事项沿用旧制度”的分支。实际脚本及代理行为尚未实施或验证，不将本表称为已通过的工程测试。
