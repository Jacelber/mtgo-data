## 一、基本模型：必要结果不让步，证明方法可替换

依 Step 3 先确定本次应交付的结果，再选择最小有效证明。检查分为交付结果检查、核心机制测试和治理小检查。普通开发不默认运行核心回归套件；本次实际改变的结果仍须有适用证明，不能将“默认不跑测试套件”理解为“不确认交付是否成立”。

一次检查只有同时具有资格、被本次实际影响触发、且缺少仍有效的证明时，才需要执行。已有证明适用时复用；没有触发时无需执行；两者都不记作“本次运行通过”。触发后必须取得必要结论，不能用上线后容易修复、Owner 已验收或其它绿灯替代。

必须保护的结果与检查工具分开：工具错误可以修复或替换，不等于允许不正确的产品交付。检查退出后，若其所指的必要风险尚未得到有效覆盖，仍须采用适当方法回答该问题。反之，不能因一个旧检查存在，就假定它保护的断言是必要条件。

## 二、一项检查怎样取得阻断资格

### 2.1 五个问题

拟保留或新增的阻断检查应能简短回答以下问题。采用现有设计或变更说明即可，不建立每个 PR 必填的证明表，也不对每次复用重新评审资格。

| 问题 | 合格答案应表达什么 | 不足以取得资格的理由 |
| --- | --- | --- |
| 发现什么错误，有什么损失 | 一个具体不正确结果，以及用户使用、业务含义、公开边界、恢复能力或持续开发效率受到的影响 | 已经存在、以前一直跑、文件属于核心目录 |
| 正确答案从哪里来 | 已确认业务规则、独立可核实输入、人工可算小例子、已确认的具体结果或真实行为要求 | 当前生成结果、另一次调用同一算法、仅有旧快照 |
| 怎样区分正常变化 | 批准输入、时间窗口、业务变化、空值及首次状态、显示容差等如何合法变化 | 任何变化都算回归、任何自动生成都算正确 |
| 何时触发、实际覆盖什么 | 哪种变化使哪个结论需要重新证明，及其真实读取或调用对象 | 所有提交、陌生文件、所有依赖者都无条件重跑 |
| 这种方法是否值得 | 能否用更短的检查、一次真实操作、现有漂移结果或有效证据回答同一问题；连同维护、环境和 Owner 介入成本是否划算 | 运行很快，所以任何断言都有阻断权；覆盖率越高越好 |

资格不以曾在生产发生事故为前提：混入未批准数据、恢复错误版本等低频但损失明确的错误，可以用最小具体反例说明价值。也不要求证明这个检查能发现所有错误。

### 2.2 赋予、修正和撤销资格

检查的实际实现和处置须属于已授权任务，并符合既定过渡与切换安排。在这些前提及已确认标准内，Codex 可自行选择、实现、修正或删除检查，不逐项申请授权。本步设计验收本身不启动实施。真正改变治理原则、质量底线或恢复策略，依 Step 1 原则 4；不得将“这个测试不合格”当作降低必要结果要求的捷径。

首次实现或实质修改检查时，就近确认三件事：一个正确对象能通过、一个对应具体错误能被发现、一个相关正常变化不会误报。可用很小的样例或实际操作，不要求三份测试文件、全面变异测试、固定覆盖率或额外演练平台。这些结论未成立前，不将工具部署为可信的强制门禁；必要结果由有效替代方法确认，无法确认时仍不交付受影响对象。

确认误报时按独立依据修正；不能确认原因时如实报告未知，先诊断，不先删断言或刷新期望。出现昂贵维护或重复误报时，只重新评估该检查及受影响方法，不扩成全仓审计。没有新事故不自动等于没有价值，也不强制按日历为所有检查重新证明价值。

旧测试从新需求出发退出、重写或完整复用合格实现，不逐项论证旧库为什么必须留下，不先修好全部旧测试。退出在统一切换时覆盖相关运行入口和强制依赖；不可只删测试文件而遗留一个永远无法满足的必需状态。

## 三、有限检查清单

下面的编号仅用于本设计引用，不要求写入 PR 标记或运行日志。它们表示有限的检查目的，不是一行一个新脚本、一个 CI 作业，也不构成普通任务全跑列表。相同结果被一份有效证明覆盖时不重复执行。

### 3.1 交付结果检查

| 项目 | 触发与对象 | 独立预期和最小证明 | 阻断资格与复用 |
| --- | --- | --- | --- |
| R1 实际页面与使用路径 | UI、资源选择、页面所读数据形状改变，或新产品接入；检查受影响入口及实际依赖 | 按已确认使用要求操作真实页面，确认反馈、内容、所需资源与合法空状态；新入口实际使用交付数据，不能只加载替身页面。可用一次聚焦浏览器检查；确有重复收益才固化自动化 | 本次必要使用路径或直接受影响行为不成立，阻止该交付。相关页面、输入、资源和环境未变且证据仍适用时复用；不巡检全站所有页面和图片 |
| R2 输入范围与派生含义 | 数据更新、新接入或生成逻辑改变；检查本次批准输入、相关派生输出及消费者 | 批准输入的纳入/排除、可独立核对的计数及统计口径；确认必要字段实际被消费。对相关数字做一致性核对和有代表性的独立复算，不能仅以文件能解析证明统计正确 | 漏项、重复、未批准输入、错误分母或含义失真阻止交付。复用不变输入和已证实计算；新输出仅确认新增或受影响结论，不重复全量分类验收 |
| R3 分类内容变化 | 规则内容或分类名称改变；对象为受影响赛制已确认输入上的结果、批准迁移及实际派生展示 | 使用现有可复用的该赛制同输入全量漂移结果，或在该结论失效时重新取得；对照已批准迁移和独立牌表事实。纯显示名称变化只核对名称及实际消费者，不自动触发分类全量漂移 | 未解释的意外迁移、批准变化未落实，不能交付。相同输入与相关规则/执行机制不变则复用；不绑定全仓或其它赛制，不在本地、PR、合并重复跑 |
| R4 治理、规范与文档结果 | 治理、规范或设计内容发生实质变化；对象为本次修改及直接关联内容 | 对照已确认目标、适用业务含义和治理原则，由 Codex 聚焦进行语义审阅及必要情境推演，确认规则一致、结论可执行、未决定项如实标注；例如不能将“必要检查失败阻止交付”误写成“失败后必须重新授权” | 影响本次承诺结果的错误、矛盾或关键缺失须修正后才能完成交付；未受影响的有效审阅结论可复用。合法措辞、排版和组织变化不独立构成失败，不扩成全部治理文档审计 |

R4 不自动增加人工审批、第二位审阅者、固定措辞测试或每 PR 一致性证明表。已约定的 Owner 验收仍依 Step 2；聚焦审阅是 Codex 对本次文档结果的责任，不能以入口存在替代，也不因其属于文档而追加无关项目测试。

R1 的资源可用性既看数据绑定，也看实际展示：存在图片字段或响应成功，不能证明图片已经正常解码显示；颜色缺失与真实无色必须区分。共享组件重复展示大量同构项目时，结合低成本数据完整性核对与代表性实际渲染，不机械逐牌点击，也不能只看一个成功例子就忽略其它不同资源来源或分支。

这些属性依 Step 3 的适用范围判断，不因图片和颜色曾出错就永久追加全站检查；也不能因当前任务没有逐字段重复描述产品要求而省略应有能力。已经确认的人工验收点和有效验收复用依 Step 2，不因 R1 自动新增 Owner 审批。

### 3.2 核心机制测试：四类有限边界

核心指其实现错误会破坏业务计算、共同执行语义、数据边界或可恢复交付的机制。不是“多数文件都很重要”的标签；普通页面排版、文案、单条规则和单次赛事内容不因重要而成为核心机制修改。

| 项目 | 触发与对象 | 独立预期及具体反例 | 阻断资格与复用 |
| --- | --- | --- | --- |
| K1 统计与数据含义转换 | 改变归一化、筛选、分组、分母、缺失状态或统计计算实现，包括实质改变这些行为的配置/依赖；对象为受改机制和相关真实调用 | 使用能手算的小输入核对结果及相关异常；例如把 Draft 纳入 Constructed、把缺失记成零或用错分母，应能发现。另由 R2 确认本次真实数据链，没有必要重复相同证明 | 受改机制必要情形失败或尚未有效验证，不能交付。普通数据更新不触发整套机制测试；共享算法受影响的不同调用语义需覆盖，不能只按所改文件所属产品选择 |
| K2 分类执行机制 | 改变匹配、优先级、冲突处理、Unknown 判定、规则加载或共享同赛制执行行为；不含单纯规则内容调整 | 独立小牌表/规则情境证明选中结果、冲突和未匹配处理符合已确认约定；不从引擎当前输出生成正确答案。按实际影响结合 R3，不另造重复漂移套件 | 机制错误会系统性改变分类，具有阻断资格；只验证受影响语义及调用链。没有机制变化不重跑；纯规则内容采用 R3 |
| K3 输入与公开边界、数据契约 | 改变来源隔离、批准范围筛选、候选可见性、公开打包筛选、数据形状或关键读写契约；对象为选择机制、实际输出和消费者 | 用一个获准对象和一个应排除对象核对；例如私有对象意外进入公开产物、来源混合、字段变化令真实消费者读不到数据。合法首次/空状态应成立；字段名或历史摘要本身不是不变量 | 会扩大公开受众、混入未批准输入或破坏必要消费时阻断。目录名不作为私有证明；只改内容且契约未变不重跑全部 Schema/安全套件，但 R2 仍核对本次输入范围 |
| K4 发布与恢复机制 | 改变产物保存、选择、部署、恢复或发布并发控制；对象为完整可部署版本及受改流程 | 按第 6 步确定的恢复要求，在准备环境证明使用指定版本、拒绝缺失/损坏对象、恢复不重新生成、过期发布不能覆盖恢复等受影响行为；普通发布是否到达目标另作结果确认 | 受影响的必要发布/恢复能力未成立时阻断其交付。普通产品更新不重演恢复故障；机制未变的证明可复用。具体恢复条件和版本组成不在本步预先决定 |

关键依赖或运行环境升级若实际影响上述机制，也触发对应部分。新增能力落入这些保护含义时按实际影响处理；确有清单不能表达的新风险，先用资格标准判断并将必要设计变化说明清楚，不自动将陌生路径归为全部核心，也不以不在表内放弃已确认的质量要求。

### 3.3 治理小检查：只保留三个目的

| 项目 | 触发与对象 | 独立预期及具体反例 | 阻断资格与复用 |
| --- | --- | --- | --- |
| G1 当前状态保持精简 | 当前状态文件变化；对象是新体系的当前状态摘要 | 当前任务、实际进度、阻断和必要下一步可直接读到，历史明细以链接退出默认读取。体积预算暂建议为 120 个非空行且正文不超过 6,000 个字符；超限先区分历史、重复内容与必要当前信息，不删事实或把内容塞成长行 | 超限可触发整理，不仅凭字符数判定状态有问题。第 7 步结合新布局验证必要当前信息合法增长的情境，再决定预算是否及如何具有阻断资格；范围仅限该状态更新，不要求全仓文档缩短，也不将候选阈值用于当前仓库 |
| G2 必要工作入口能够找到 | 新治理入口、直接必读链接或支持命令被修改、移动、删除；只看相关目标 | 必要本地目标存在，命令入口可定位；例如改名后入口仍指向不存在的规范。具体句子、标题编号、文件排列及历史链接不属于正确答案 | 确实使正常工作入口不可用时阻断该改动。普通参考链接或排版建议没有同等资格；不递归爬全部文档和外网，不因远端暂不可达阻断产品交付。未受影响目标的有效结果复用 |
| G3 必要检查确实执行且能从故障处续作 | 修改检查选择、执行或结果复用机制时；对象为真实入口的选择和返回行为 | 最小情境证明：触发检查实际执行；预期有检查却选中零项时不算成功；必要失败不放行；未触发不补全量；查询重试不重跑产品验证。涉及复用机制时，还须对照确认有效结论可复用、失效结论不能误用；仅提交号等无关变化不使结论失效。正确行为来自本步与 Step 2，不复刻旧 Gate 状态 | 错误会漏检或持续阻断开发，机制修改时必须确认。每次运行只如实返回实际执行和复用等事实，不每次重跑执行器自测；没有适用检查的合法任务可明确无须执行，不能误作零项异常。失效结论按尚未证明处理并补足受影响验证；适用性不明时聚焦查明，不默认复用或全量重测 |

G1 的体积预算是本步提出、留待整体设计组合时验证的候选参数，不是已测得的最佳值或必须维护的质量底线。必要当前信息可通过清晰摘要和按需读取组织，不删事实，不把关键限制隐藏到无法发现的位置，也不能转移到另一个默认必读文件规避预算。若合理精简后仍存在必要信息造成的合法超限，而数值检查无法区分它与历史堆积，该数值只承担提醒作用；不能靠反复请求 Owner 例外维持。预算定稿本身不赋予其阻断权，也不按旧文件大小倒推放宽。

G2 的命令可定位不等于要求运行有副作用的命令。G3 验证的是少量关键行为，不为治理脚本每个分支再建一套治理测试，也不预设必须建设自动证据管理系统。复用失效取决于输入、代码、依赖、环境或组合变化是否实际影响原结论，不仅凭某个字段发生变化就重测。

“测试很快”不是充分理由。本步不增加固定英文句子、PR 文案格式、状态授权令牌、失败次数上限、代码覆盖率、全仓链接爬取等检查；不为检查这些检查再建立常驻审计系统。第 7 步的旧影响退出核对是一次切换工作，后续只有改动相关入口时才验证直接影响。

## 四、独立预期、数字与正常变化

### 4.1 独立不等于另写一套复杂实现

小型人工可算例子、来源明确的输入事实、Owner 已批准的迁移、实际用户操作要求都可作为预期。旧快照只有在其正确性和适用范围已确认时才能使用；不得因为它存在就冻结合法变化。

生产实现给出预期、再由同一生产实现判断通过，不具备独立性。大规模数据可用已确认前后结果比较迁移，并对受影响语义使用小型独立预期，不要求人工逐行复算所有数据。Schema 能说明结构，不单独证明含义、资源可用性或正确接入。

测试样本应围绕业务情境，只包含情境所需字段，避免复制整个当前产品快照或依赖无关默认分类。但检查实际接入时仍须使用真实接口和必要资源；不能为了样本简单而把真正容易漏接的部分全部替换成永远成功的替身。

### 4.2 数字检查先定义集合和口径

| 情形 | 正确判定方式 |
| --- | --- |
| 占比之和 | 先确认是否为完整、互斥的集合及同一分母。完整集合才有相应总和要求；Top N、过滤后子集或重叠指标不强制合计 1 |
| Unknown、排除和缺失 | 按既定口径明确是否进入分母、怎样展示；未知分类、不可用牌表、无比赛和零胜率不能合并为空或零 |
| 显示舍入 | 优先核对未舍入计数/比例关系，再按显示精度允许其舍入误差；不强求 33.3% 三项显示合计 100%，也不采用足以掩盖错误分母的宽泛容差 |
| 新输入或滚动窗口 | 依据批准输入、约定窗口和规则判断派生变化；不要求相关旧数字保持不变，也不以生成器产出替代解释 |
| 首次接入、无合法样本 | 按已确认空状态处理，不要求先有旧基线，不用虚构零值让断言通过 |

正确性预期变化必须有业务决定或独立事实依据。修复测试不等于修改正确答案；Owner 批准的业务变化可以更新相应预期，但不能顺带接纳其它尚未解释的差异。

## 五、触发、范围与复用如何执行

1. 从已确认目标和实际改动识别 Step 3 的相关结果，以及本步对应风险。文件路径可帮助定位，但不独立决定全部范围；共享实现、配置和依赖的影响也要考虑。
2. 查找已有相关结论。明确本次需要新增回答的问题，用最短方法补足。已有结果不适用的原因是实际内容或环境变化，不是仅提交号、工作区、PR 或日期变化。
3. 必须确认的相关行为全部取得有效结论后，才通过对应交付条件。最小范围指裁掉无关项目，不是只挑容易通过的情况；多个实际分支风险不同，就分别覆盖必要区别。
4. 陌生路径、影响不清或结果来源暂不可查时，先做聚焦调查；不默认全量，也不默认无需检查。必要风险仍无法判断时，暂停受影响交付并继续有依据的调查，按 Step 2 处理真实阻断。

| 变化或状态 | 仍可复用什么 | 需要补什么 |
| --- | --- | --- |
| 换窗口、工作区、提交或 PR，相关对象未变 | 适用于相同相关内容的技术结果与已确认业务判断 | 仅恢复已有上下文，不因载体变化重测 |
| 主分支新增无关修改 | 未受影响的结果 | 确认是否有实际相关影响；不凭主分支 SHA 不同直接废弃成果 |
| 同一输入、分类规则内容变化 | 输入资格、未受影响机制证明 | R3 的受影响分类结论；需要新派生输出时补其实际产品结论 |
| 新数据、规则与机制不变 | 机制正确性、未变规则的相关证明 | 新输入范围、新派生结果和改变的真实使用情形 |
| 页面逻辑未变，但数据形状或资源路径改变 | 未受影响的交互结论 | 受改数据/资源的真实读取与展示，不用旧页面截图替代 |
| 本地验证到真实发布环境 | 与环境无关且仍有效的输入/计算/业务判断 | 只增加路径、访问范围、资源供应等真实环境差异的确认；具体发布确认由第 5—6 步确定 |
| 环境或查询失败 | 已完成且未受故障影响的证明 | 修复后重试未完成部分。曾失败的同一提交可以必要重试，不强迫制造新提交 |
| 修正检查自身错误 | 未受错误影响的证明 | 重新取得原错误检查未能证明的结论；不要求所有检查陪跑 |

复用依据可以来自现有候选、提交差异、文件内容、日志或报告；不要求每个对象新增摘要算法、签名、父节点核对和专门台账。需要确认选中的确是原对象时使用现成标识或内容核对，不能仅凭“之前绿过”复用不同对象。

证据没有固定按天失效规则。易受外部状态影响的结论不能无限复用：历史资源可用记录不能独自证明新的发布环境现在可用，但这也不使纯计算结果一起过期。受影响检查的证据确实无法恢复时可以重做必要检查，不把“不重复”变成禁止恢复有效结论。

## 六、失败状态与交付处理

| 实际状态 | 对应处理 | 不允许的替代 |
| --- | --- | --- |
| 必要检查执行并发现实际错误 | 停止受影响交付，范围内修复，然后验证受影响部分 | Owner 已验收所以跳过；失败容易修所以先上线 |
| 必要检查未执行、环境故障或选择错误 | 状态是尚未证明；修复执行问题或采用有效替代方法 | 零项执行、无说明跳过、超时或 API 红灯直接当作产品通过/失败 |
| 检查预期或工具本身错误 | 依据独立标准纠正、替换或删除不合格断言；必要质量条件继续满足 | 把当前输出覆盖为新期望，或删掉唯一证明后宣布风险消失 |
| 本次未触发，或已有有效结论 | 如实说明不适用或复用，不安排额外运行 | 为了取得一套新绿灯重跑；把复用说成本次运行成功 |
| 非必要建议、无关既有问题 | 如实说明相关已知影响，按 Step 3 的缺陷边界处理 | 将建议提升为阻断；将本次引入的问题归入无关历史 |

历史失败事实保留，但不永久否决修复后取得的新有效结论。检查工具与流水线状态怎样恢复到可继续交付，在第 5 步定义；不能用聊天结论冒充平台状态已变，也不能把一次查询故障自动升级成 Owner 例外审批。

这些处理不重新定义授权：失败通常停止交付而不是停止诊断修复；真实权限、必要业务决定和无法继续的情形统一依 Step 2。

## 七、设计情境核对与后续衔接

以下仅为设计推演，不是已执行测试，不要求每次普通任务逐项运行：

| 情境 | 本设计应产生的行为 |
| --- | --- |
| 修改一句文案，未改统计或机制 | 确认实际文案及直接展示；不运行核心套件，也不自动增加人工验收 |
| 新赛制分类正确，代表牌全部空图、颜色遗漏 | R1/R2 发现本次完整接入不成立；分类漂移通过不能替代实际页面证明 |
| 分类内容变化已完成同输入漂移，后续仅创建 PR | 复用 R3，不因新 PR 或提交重新检查；新派生产品仍需证明实际反映变化 |
| 旧断言要求私有候选先出现在公开目录 | 断言不合格，可修正；仍需证明候选对批准受众可用且没有扩大公开范围 |
| 为统计新赛事而总量/滚动窗口变化 | 检查批准输入和合法派生含义，不冻结旧数字，不触发未改的整个统计机制套件 |
| API 500，产品检查已成功 | 保留产品证明，只恢复必要查询；不要求重跑整个 head，也不自动要求 Owner 例外 |
| 执行器本应运行相关检查却返回零项成功 | G3 要求该入口如实判为未完成，修复选择问题；合法无检查任务不误伤 |
| 复用机制修改后，原结论仍适用；另一个结论因相关计算变化已经失效 | 前者继续复用，后者不能误标为有效复用，补足受影响验证；无关提交号变化不触发重测，适用性未知时先聚焦查明 |
| 治理文档把范围内修复改成失败后必须重新授权，但体积和链接均正常 | R4 对照已确认原则发现语义冲突，修正后才完成本次文档交付；G1/G2 通过不能替代语义审阅 |
| STATUS 增加大量历史日志 | G1 只要求精简当前状态和链接历史，不重跑产品测试，不靠删当前事实通过 |
| STATUS 因必要当前依赖和阻断增多，合理精简后仍超出候选预算 | 保留必要事实，以清晰摘要和按需读取组织；无法区分合法增长的数值检查只作提醒，不删事实、不藏限制，也不新增 Owner 例外审批 |
| 检查从未发现过生产事故，但能拒绝错误恢复版本 | 有具体损失与独立反例，仍有价值；只在受影响机制变动时测试 |
| 删除错误测试后相关质量条件仍无有效证明 | 继续选用有效方法；不能把“删了红灯”当作通过 |

本步交付有限检查清单、资格标准、触发范围、独立预期、数字语义、复用和失败处理设计。尚未执行任何检查资格验证，不宣称现有测试已完成替换或本设计已证实降低成本。

第 5 步落实运行环境、选择入口、候选续作及失败状态恢复；第 6 步落实发布和恢复对象及具体情境；第 7 步确定最终文件/脚本映射和状态预算，逐块实现验证后统一切换。前三步验收结论不改写，具体文件不必逐一成为 Owner 审批对象。第 8 步用真实任务的交付耗时、误报、漏检、重跑及维护成本判断效果，不靠检查数量或绿灯数量宣称成功。
