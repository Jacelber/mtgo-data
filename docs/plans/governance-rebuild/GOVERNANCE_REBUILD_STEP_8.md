- 依据：Step 1—6 已验收版 1.1，以及按 Owner 限定修订并授权续进后完成的 [Step 7 版本 1.2](GOVERNANCE_REBUILD_STEP_7.md)。
- 版本：1.1，2026-09-12，Owner 已验收，设计及收尾完成。
- 验收记录：Owner 同意 §4.2 的截止时间澄清并明确“验收”，同时要求整体实施暂缓；本版已落实该限定修改。
- 当前授权：仅完成指定澄清及验收留档；整体实施暂缓，不启动 U1—U7、产品修复、测试、归档资源创建、权限修改或发布。

## 一、本步解决的问题

治理文件删掉、CI 变绿，不足以说明开发变顺畅；反过来，没有马上积累真实任务，也不应阻止已经完成的治理切换交付。

本步分别回答三个问题：实施成果是否达到已确认设计、真实任务中是否减少无效劳动且保持必要质量、出现偏差后如何在原原则下做有限调整。实施验收复用 U1—U7 已取得的结论，效果观察利用之后获准真实任务中的现成信息；不再造一套验收平台。

评价同时覆盖交付效率、真实错误发现、误报和重复劳动、Owner 技术介入、恢复效果与治理总维护成本。检查数、文件数、绿灯数只可描述实现，不能代替收益结论。

## 二、四种状态分别表达

| 状态 | 何时成立 | 对后续工作的影响 |
| --- | --- | --- |
| 设计已确认 | 八步设计及必要修改完成 Owner 确认 | 可以按用户指令进入实施；尚不代表实际能力存在 |
| 实施准备完成 | U2—U5 必要验证、U6 组合与退出核对完成，形成具体成果 | 到达 Step 7 约定的 U6 一次人工验收点；不重新验收全部已确认制度取舍 |
| 统一切换交付完成 | U6 验收后，U7 实际入口、生产对象、归档和旧影响退出的必要结论成立 | 本次治理实施可如实收尾，普通开发使用新体系；不等待五个任务或十四天 |
| 真实效果已有初步证据／需改进／证据不足 | 依据后文有限观察得到相应事实 | 改善结论限于观察范围；证据不足不撤销实施完成，也不阻断正常开发 |

未完成的必要实现、实际旧门禁残留、失效的恢复入口不能写成“留待效果观察”。反之，未发生真实回滚、没有核心机制改动等属于未遇到使用场景，不要求制造事故或业务改动补样本。

## 三、落地验收：复用成果，补真实衔接

### 3.1 U6 向 Owner 提供什么

提交一份简短可审阅说明，链接已完成成果，覆盖以下实际问题；不要求每项另写报告或复制所有日志。

| 验收问题 | 所用现成成果 | 不额外要求什么 |
| --- | --- | --- |
| 新规则是否独立、清楚且符合已确认方向 | 新入口及职责文档、聚焦语义审阅 | 不把 Step 1—8 全部重新审批，不用固定句子测试替代含义审阅 |
| 有效业务含义是否完整迁移，旧控制是否退出 | U1 迁移对应、U2/U6 删除和引用核对 | 不保留旧治理活动副本，不审计全部业务历史 |
| 必要检查是否能发现对应错误且允许正常变化 | U3 的正确例、错误例、合法变化和选择/复用结论 | 不重跑未受影响检查，不按覆盖率或数量验收 |
| 候选、归档、发布和恢复是否真的可用 | U4/U5 的实际交接、取回、隔离和故障续作验证 | 不把脚本存在当能力通过，也不让日常本地审阅必须云端往返 |
| 切换还有什么实际风险和限制 | U6 组合结果、已保全真实包、外部入口和精确设置清单 | 不用待实现承诺冒充完成，不把明确需要 Owner 判断的变化留到切换中隐式处理 |

Owner 判断方向、业务含义和已约定取舍；技术是否正确由 Codex 在提交前取得必要结论。正常技术修复不变成新的启动授权。U6 验收对象保持稳定，受影响变化依 Step 2 重新提交相应部分。

### 3.2 U7 完成依据

沿用 Step 7 的切换顺序，收尾时确认：当前正式入口采用新规则；受支持调用不再执行旧控制；在途旧写入已处理且历史重跑边界如实说明；最终真实基线及归档引用成立；实际发布或恢复所承诺的结果已确认。外部项目提示仍实质强制旧流程、或必要能力未完成时，不能宣称整体切换完成。

使用已完成单元的有效证据，只补切换实际引入的组合、环境和服务对象问题。诸如查询失败只续查、不重复分类、本地验收不等待归档等路径，优先引用 U3—U5 的验证；不在 U7 再逐条演示一次。

U7 的结果报告是实施交付说明，不再增加第二次人工发布批准。既定质量条件未成立时暂停受影响交付并继续有依据的修复；未到业务目标时如实报未完成。

## 四、真实观察的范围和结束时点

### 4.1 观察自然发生的任务

建议初始观察样本为**切换后最先启动的五项已授权真实任务**，按启动顺序选入，不只挑成功任务；其中失败、阻断、取消和仍在进行的任务均如实保留。观察对象是独立交付目标，同一任务拆成多个 PR、换窗口或重试不增加样本数。

任务可以是文档、UI、数据更新、分类内容或核心机制修改，不要求凑齐每个类别。沿用已批准安排自然发生的维护任务可以纳入，不为观察新开任务、抓新赛事或制造产品修改。P14 的后续修复若另行获准可以成为真实样本，但本计划不授权修复，也不要求先将其 bug 清零。

跨越切换的在途任务单独标注新旧流程分别作用的部分；可以说明恢复衔接问题，不与完全使用新体系的任务混为同类对照。只有本任务已有且有权读取的资料才用于总结；不会自动监听其它对话、向其它任务发消息或扩大读取权限。资料缺失标为未知，不向 Owner 追索完整历史。

### 4.2 一次初始总结，不长期挂起

初始观察以以下两个条件先满足者作为取样截止点：

- 首批五项任务均已有明确结局，包括成功、取消或明确暂停；
- 切换后满十四个自然日。

报告可在截止后的自然任务收尾或 Owner 查看进度时，依据现成资料整理；不因晚报告而延长取样窗口。未结束任务按截止时可知状态记录，资料不足标为未知，不将之后的进展回填为截止时已经取得的结果。观察结束不影响原任务继续执行或及时处理实际问题。

五项与十四天是本步建议的有限观察窗口，不是质量阈值、交付 Gate 或统计显著性标准。若窗口届满只有两项任务、某项尚未结束或没有任务，就报告实际数量和未知点，结束这次初始观察，不为凑数无限延长治理任务。

不创建定时任务、后台轮询或主动唤醒；没有后续交互不会自动在第十四天发报告。观察安排在未来获准实施和相关真实工作时按已确认范围执行，当前设计授权不启动它。实施完成无需保持当前会话运行等待观察结果。

## 五、观察哪些事实，以及怎样防止自我美化

### 5.1 口径

下表是一次总结的取证口径，不是每个 PR 的必填表。只使用任务对话、PR、现有作业日志和实际产品反馈；无法可靠还原的时间或数量写明未知。不同维度可关联同一事件，但不能把它们相加当成多次独立事故。

| 维度 | 要回答的问题及最小记录 | 判读边界 |
| --- | --- | --- |
| 实际交付效率 | 任务承诺结果是否完成；可取得时列授权至交付的经过时间及主要停顿原因 | 分开 Owner 正常验收等待、外部服务等待、实际工作和治理返工；日志跨度不冒称人工工时，取消不当作成功或技术失败 |
| Owner 技术介入 | 哪次需要 Owner 动作，原因是业务决定、不可替代权限/信息，还是已有授权下的机械重复请示 | 正常业务验收不算治理失误；必要权限操作仍属于真实负担，单列而不隐藏。对状态的普通询问不自动计为审批 |
| 检查带来的真实发现 | 检查首先发现了哪个不正确产品结果、独立预期是什么、发生在交付前还是后、采取何种修复 | 不能将 Owner 已发现的 bug、修复后新增的回归样例或检查自身报错计为“测试先发现产品错误” |
| 误报与执行故障 | 合法变化被拦、过期假设/fixture/选择逻辑导致失败，还是依赖/平台故障导致未执行 | 原因未查明就保留未知；执行失败不等于通过，也不全部归为误报；正确发现本次产品问题的阻断属于必要收益 |
| 重复劳动与复用 | 哪次已有有效结果却被重跑、候选被无必要重建、归档上传故障阻断独立本地审阅；哪些成果实际复用 | 相关代码、输入或组合变化后的必要补验证不算浪费；只称“复用了哪些结论”，不虚构节省的分钟数 |
| 漏检与恢复 | 已交付必要结果的真实缺陷由谁发现、此前证明漏了哪一环；如有真实恢复，记录识别至恢复确认的可知时间和结果 | 区分原有无关缺陷、本次引入或本次承诺应解决的问题；未发生恢复不记为零分钟成功，不重做故障演练制造证据 |
| 治理总维护成本 | 实际花在检查、fixture、CI、依赖环境、归档、凭据、控制文件、文档及本观察本身的排障/维护工作 | 一次重建投入与日常成本分开；测试运行快但经常修也可能不划算。新增工具的成本不能因名为“薄入口”而忽略 |

同一根因引起三个运行失败，应表达为“一次问题、影响三个运行”，而不是三个独立产品缺陷。多个独立错误也不因为同处一个 PR 就压缩成一件小事。已有日志能够说明的事实直接引用，不建立新的计时、签到或逐动作证据系统。

### 5.2 与旧体系比较

复用总计划已记录的历史样本，不再为评估收益重跑旧测试或补齐全部旧日志。该样本缺少完整本地拦截记录和人工工时，不能将未知当零，也不能拿旧失败运行数量与新产品 bug 数量直接相减。

有相似任务和可比较证据时，说明例如“同样的查询故障，以前引起人工流程例外，这次只续查后继续”“本次规则更新复用输入与已有机制证明，只补受影响漂移”。任务难度和产品范围不同则分别陈述，不宣称精确提速百分比或已证明全部测试无用。

没有故障不证明检查有价值，也不证明没有价值；没有发现 bug 不自动撤销检查。检查资格仍依据 Step 4 的具体损失、独立预期和成本判断。实际漏检或反复误报提供重新评估相关方法的依据，而不是全仓增加测试的理由。

## 六、效果判断与调整边界

| 观察结论 | 应采取的动作 | 不产生的额外制度 |
| --- | --- | --- |
| 正常任务按计划连续完成、复用成立、必要结果得到确认 | 报告在这些任务上已有改善证据及未覆盖场景 | 不把小样本结论扩大成永久成功，不为维持报告绿色重跑 |
| 重复请示、无关重测、本地验收被上传故障拖住 | 当前任务按已确认规则纠正执行；定位是代理理解、旧入口残留还是工具实现错误 | 不先向 Owner 申请同一技术续作，不增加例外登记 |
| 工具误报或维护成本偏高 | 按 Step 4 对该检查/入口修复、简化、替换或撤销不合格断言；必要结果继续由有效方法确认 | 不为把测试改绿而刷新未解释预期，不因减少测试目标而跳过正确性 |
| 必要产品结果漏检、范围/恢复控制失效 | 先按当前任务范围和 Step 2/6 处理真实影响，再定位最小遗漏；必要时修订相关证明方法 | 不等待满五项才处理，不自动加全量回归或重演所有机制 |
| 所需修订改变治理原则、业务含义、权限或恢复策略 | 提供具体变化、影响和推荐，由 Owner 决定受影响部分 | 不重新打开全部已确认设计，不因普通实现选择增加审批 |
| 证据不足、任务太少或缺少某种场景 | 标明未观察到什么，完成有限总结；正常开发继续 | 不制造演示任务，不等待长期效果才承认 U7 已完成 |

上述纠偏采用既有授权：U1—U7 尚在交付过程中且属于必要范围的治理修复可以继续；实施已经完成后，观察本身不授予永久自行修改治理或产品的权限。后续任务范围内的必要修复依 Step 2 判断，新的独立改造目标另行提出具体计划。当前有效的授权能覆盖时不重复请示，不能以旧整改名义无限续修。

一次明显违反既定规则的行为就值得纠正，不要求重复三次才承认问题；也不因一次未知失败立即删除正确检查。重复出现或成本明显偏高时聚焦相关机制调查。故障数量不是撤销授权或强制更换方案的自动触发器。

少跑测试、少提问但真实必要结果经常漏检，不能判为改善；验证更充分但不断制造无关维护和技术请示，也不能判为达到目标。没有统一加权总分，按真实收益、成本和仍存在的问题分别说明。

## 七、交付记录与用户负担

实施时复用 Step 7 已安排的收尾记录，建议唯一位置为 docs/plans/governance-rebuild/RESULTS.md，分为“实施交付事实”和“初始真实效果”两部分。不在日常默认入口塞入完整观察表，不另建效果数据库、专用工作流或长期审计台账。

U6 审阅和 U7 收尾沿用同一说明及证据链接；不复制完整日志。初始总结由 Codex 在既有范围内整理现成资料，通常用一页内的正文说明以下内容，篇幅是沟通目标而非检查阈值：

- 观察了哪些真实任务、结果及资料缺口。
- 哪些旧问题确实减少，哪些仍发生；用具体事件支持。
- 真实缺陷发现和漏检，及新增归档/工具带来的维护成本。
- 已按范围纠正什么、哪些需要新决定、哪些尚无效果证据。

无需 Owner 填写工时、标注所有报错或逐项证明“这是无意义测试”。Owner 自然反馈的体验是证据来源，但不代替技术事实核对；也不要求为结束观察额外回复一次满意度问卷。

报告纳入下一次已授权且适合的文档更新，或先在既有任务中交付；不为同步一个计数或观察状态单开元数据 PR。正常任务的既有结束说明已经足够时直接引用，不要求所有任务额外写一份治理总结。若观察记录本身开始显著占用工作，应先缩减记录，只保留影响结论的事实，不建设新的监控工具来维护观察工具。

## 八、设计情境核对

以下用于本步语义核对，不是新测试套件，也不要求日常逐项演练。

| 情境 | 本设计预期 |
| --- | --- |
| U7 已完成，但十四天没有新任务 | 实施完成、真实效果证据不足；不阻断开发，不自动唤醒或制造任务 |
| 五个样本中两项阻断、一项取消 | 都列入观察，分别说明原因，不只统计两个成功任务 |

| 本地候选可用，但归档暂时上传失败 | 可以继续独立本地审阅；正式发布等待必要归档恢复，不重复生成或验收不变内容 |
| 本次检查先发现错误分母，修复后交付 | 记真实缺陷发现及必要修复成本，不算“测试阻断开发”的误报 |
| Owner 先发现图片缺失，随后增加检查 | 记对应漏检与修复；新增检查不能冒称在此次交付前发现了该错误 |
| 外部 API 500，自动续查后继续 | 记执行故障和正确续作；不记产品缺陷、不要求把历史红灯改绿 |
| 新工具每次只运行一秒，却反复要改配置和 fixture | 总维护成本仍可能高；检查其实际收益，不能只展示运行时间 |
| 没有核心修改和真实回滚 | 相应生产使用效果未观察；保留实施验证，不凑任务、造故障或重跑演练 |
| 实施结束后发现一个独立的治理改造机会 | 提出有限建议，按现有授权边界判断是否另立任务；不把观察转为无限整改 |
