## 一、先定义结果，再选择证明方法

本步回答“怎样才算把这件事做好并交付”，不决定必须运行哪些命令或测试。完成标准是所承诺结果应满足的条件，不自动成为每次都要重新运行的测试清单。

第 4 步根据这些条件确定触发、最小验证、独立预期和结果复用。已有证据仍适用于本次相关对象时可以复用；已失效、没有执行或不覆盖承诺结果的证据不能充当通过结论。

计划是否足以执行，依 Step 2 第 2.1 节判断。定义交付结果时，可按需要用自然语言说明改变的结果、交付对象和位置、输入、直接关联能力及判断依据；这些是描述结果的参考维度，不新增必填表单或计划审批条件，也不要求摘要绑定或逐文件审批。

## 二、六类任务的完成标准

以下各行按真实目标适用，不以文件目录分类。一个任务可同时涉及几类结果，但仅组合实际相关要求；不因此拆成多轮 Owner 审批。

| 任务类型 | 承诺的结果与实际交付对象 | 完成标准 | 直接关联范围 |
| --- | --- | --- | --- |
| 普通 UI、内容和交互 | 在约定页面、入口及使用情境中实现明确变化；对象是实际可操作页面及所需数据/资源 | 约定操作产生正确反馈，内容和数据表达符合要求，完成该操作必需的资源能够使用，直接关联行为未被破坏。Codex 负责确认机械可用性；人工体验或内容验收按 Step 2 的已确认安排执行。不因任务属于 UI 类别而新增人工验收，也不因此取消已有验收约定；有效验收结果按既定规则复用 | 修改的用户路径及它实际依赖的共享能力；不自动要求检查全站全部交互 |
| 新赛制、新赛事或新产品接入 | 让约定用户通过约定入口使用完整的本次能力；对象是从已批准输入到实际页面的整套相关结果 | 来源与公开范围正确；约定内容和功能完整、可到达且可用；真实输入能够经过处理进入实际展示；适用的名称、分类、颜色、图片、统计等没有因接入遗漏而失效；直接受影响的既有产品保持其约定行为 | 本次新增产品链及实际修改的共享路径；是否需要 MTGO 与 Tabletop 协同交付由已批准业务范围决定，不能自行合并统计或捆绑无关产品 |
| 周期性数据或内容更新 | 将已批准周次、赛事或内容更新反映到约定产品；对象是本次输入集合及其派生输出 | 纳入和排除范围正确；应更新的展示与统计已更新；相关总量、分母和缺失说明符合已确认含义；不漏项、不重复、不混入未批准输入。不应受本次批准输入及其直接派生影响的既有内容，保持约定行为。符合批准输入、约定时间窗口和既定业务规则的相关派生变化，不因数值不同于旧值而被视为异常；也不得仅以“自动生成”为理由接受尚未解释的差异 | 本次更新范围、直接派生结果及受影响读取路径；没有相关变化的规则、机制和页面不因更新重复验证 |
| 分类规则内容修改 | 在同一已确认输入集合上实现批准的分类变化；对象是规则变化、前后分类结果及适用的产品输出 | 实际迁移与批准变化一致，意外迁移已解释并处理；共享使用该规则的相关来源遵循同一赛制含义；需要交付的派生产品已经反映新分类，而非只证明分类器能运行 | 受改规则影响的同输入对照与相关消费者；成功的全量漂移和 Owner 决定可复用；执行机制本身改变时另适用核心机制要求 |
| 核心机制修改 | 修改一个承担重要含义或恢复责任的机制，同时保持其约定行为；对象是机制输入、输出及实际调用入口 | 对照独立于当前实现的已确认预期，正确情形得到正确结果，关键异常得到约定处理；实际调用链能够使用该机制；相关产品的含义和已批准边界保持成立 | 机制真实影响的调用方和结果；具体核心名单、情境和检查范围在第 4 步确定，不因“核心”二字自动运行全部测试 |
| 治理或文档修改 | 让指定规则、说明或工作方式清楚、一致且能够执行；对象依任务目标为设计材料，或已实施的规则与工具 | 设计任务交付完整可判断的方案，未决定项不伪装成已确认；实施任务还须使实际入口、模板及执行机制符合新规则，并移除对应旧影响。状态、引用等只处理本次直接相关范围；真实效率效果按约定观察，不凭文档通过宣称已证实 | 本次规则的活动引用与实际执行入口；不自动扩成全部历史文档清理或产品 bug 修复 |

上述属性是可能适用的示例，不构成固定字段检查清单。适用范围依据已确认产品要求及本次实际影响判断，不要求 Owner 在每项任务中重新枚举已有要求。具体检查触发与结果复用由第 4 步确定。

适用属性按已确认业务含义判断：真实无色、未知、不适用和遗漏不能混为一谈。图片要求针对本次交付按上述适用范围应使用的资源和既定降级行为；有图片字段不等于实际可用，也不新增“全站所有图片在任何时刻都必须在线”的要求。

## 三、如何判断本次结果成立

### 3.1 验证对象覆盖实际交付

根据任务承诺，关注输入与结果含义、真实读取或操作路径、以及约定交付位置。局部函数通过、数据能解析、页面地址返回成功，分别只能证明其实际覆盖的事实，不能单独推导出整个交付已经完成。

例如，新增产品的数据生成成功，但入口不可访问或必需展示属性遗漏，新增产品尚未完整交付。反之，一次文档设计任务不因没有部署到生产而未完成，因为部署不属于它的交付目标。

任务若只交付私有预览，就判断该预览是否完整可用并保持私有；任务若承诺正式上线，私有预览通过或 PR 合并都不足以宣布最终完成。预览、验收和发布是事实状态，不因此生成额外授权关口；授权与人工验收依已验收 Step 2。

### 3.2 正确答案不从当前结果倒推

完成结果依据已确认业务含义、Owner 已批准的变化、能够独立核实的输入事实或独立预期判断。不得因为新输出已生成，就把它当正确答案；也不得为了保留旧数字而拒绝正常获准的数据更新。

对占比、总量和缺失状态，先确定对象是否覆盖完整集合、分母及排除规则是什么、如何舍入，再判断结果。例如三个显示为 33.3% 的项目合计 99.9%，不能仅凭显示值不等于 100% 判错。这个例子说明判断方式，不规定所有统计都采用同一种舍入容差。

### 3.3 不重复已经成立的结论

分类规则修改已经在相同输入上完成前后对照，且实际迁移已获批准时，不因为提交、PR、合并或切换工作区重新要求同一漂移和业务验收。相关规则、输入、处理机制或实际影响变化时，只处理因此失效的结论。

已有分类证明不等于新派生产品已经生成并使用新分类。若交付目标包含发布新结果，还需完成相应派生和交付，并回答该新对象新增的问题；这不意味着重新做一次相同分类审阅。

UI 或其他成果在 Owner 审阅时保持稳定；独立工作、修复后复用验收以及只重审变化部分的边界，统一依 Step 2 第 2.4 节，不增加新的摘要或字节一致性 Gate。

### 3.4 直接关联范围按结果影响判断

直接关联，是指本次变化可能改变所承诺结果，或改变维持该结果所需的输入、共享处理、资源选择及实际读取行为。不是“同一个目录下的所有东西”，也不是“只要没有改前端文件就与页面无关”。

本步不要求对每项任务做全仓库依赖图。Codex 根据实际改动和使用路径识别必要影响，具体验证方法在第 4 步落实。出现超出现有授权的新业务或制度选择，按 Step 1 原则 4 处理；发现技术依赖不自动产生新的审批。

## 四、首次启用与候选到公开的生命周期

首次状态是合法业务状态，不能只按已经长期运行的产品设计完成条件。不是每个任务都必须经过下表全部状态；按批准的起点和目标判断。

| 实际情形 | 应成立的结果 | 不能作为完成前提的错误要求 |
| --- | --- | --- |
| 首次接入，没有旧目录、旧产品或旧基线 | 从已批准输入和明确预期产生本次所需结果；初始化内容和范围正确 | 必须先存在上一版成功产品、旧事件或旧验收记录 |
| 私有候选 | 在约定预览入口完整可用，实际可访问受众与发布状态均符合已批准范围；不得因预览而扩大公开范围，或未经批准作为正式产品发布。未列入导航或目录，本身不能证明候选处于私有范围 | 为了验证候选，先把它正式公开 |
| 已批准转为公开产品 | 批准的内容和约定功能一起对外可用；不遗漏承诺部分，也不扩大来源或公开范围 | 所有其他赛制也必须同时重新验收或发布 |
| 业务上允许的空数据、未知或不适用状态 | 清楚表达其真实含义，相关页面和操作按既定要求处理 | 编造数据填空，或把所有空值视作实现失败 |
| 已批准的内容需要更新派生输出 | 约定输出实际反映批准变化，使用已批准输入而非顺带接入新数据 | 因输入赛事未变就拒绝必要生成，或因重新生成就重开全部业务审阅 |

生命周期的初始化、目录组织与发布机制如何实现，留给后续设计。这里定义的是合法结果，不指定旧工具、状态枚举或旧证明链必须保留。

## 五、已有问题与本次交付边界

| 问题情况 | 对本次完成判断的影响 | 处理方向 |
| --- | --- | --- |
| 本次变化引入或加重的缺陷 | 属于本次交付问题，不能按完成报告 | 范围内修复，确认受影响结果；不通过改期望掩盖缺陷 |
| 本次明确承诺修复的已有缺陷 | 承诺尚未成立前不能按完成报告 | 按已确认目标修复，不把它重新归为历史遗留而排除 |
| 原有缺陷实际阻止本次承诺成立 | 即使不是本次引入，相关交付仍未完成 | 处理必要依赖；需要新业务、权限或制度取舍时按已验收边界提出具体问题 |
| 已有且与本次交付无关、未被加重的缺陷 | 不自动成为本次任务的清理前提，也不据此要求全站重新验收 | 如实保留已知状态，按后续产品安排处理，不将本次完成描述成整个产品没有问题 |
| 暂不清楚是否由本次引入、是否影响承诺结果 | 尚不能直接宣布无关或已完成 | 查明实际影响与已知事实，不先追加全部测试；未知原因如实说明 |

“无关”不能只用存在时间或文件位置判断；必须与本次结果及直接依赖分开。把问题写入已知清单不能替代本次应完成的修复。本次治理设计也不会因此自动获得 P14 产品修复授权。

## 六、交付说明的最小内容

说明本次实际交付了什么、可以在哪里使用或审阅、哪些必要结论已经成立或复用、是否仍有影响完成的未解决问题即可。以现有成果和记录为依据，不要求固定模板、完整日志粘贴或再造一份验收台账。

不得把“技术验证完成”“Owner 已验收”“约定发布完成”互相替代；根据本次任务终点报告真实状态。实际发布方法和最小发布确认留给第 5—6 步，不在本步规定每次上线重复整套产品检查。

长期治理收益、持续运行稳定性等需要真实使用才能观察的效果，和已完成的设计或实施结果分开说明。不为获得观察数据制造无意义开发任务，也不把尚未观察说成已经成功。

## 七、情境推演

以下是完成标准的设计核对，不是项目测试执行结果，也不强制今后每次逐项运行。

| 情境 | 判断 |
| --- | --- |
| Pauper 分类漂移符合批准迁移，但新产品必需的代表牌图片和颜色展示因接入遗漏而失效 | 分类结论可以成立，完整新产品交付尚未成立；不能用分类测试通过替代产品可用性 |
| 本次只改一个筛选操作，原有另一个独立页面有已知图片问题且没有被本次影响 | 判断本次筛选及直接关联行为，不把无关页面修复变成前置条件 |
| 筛选改动使用的共享资源选择逻辑同时破坏另一入口 | 是实际受影响范围，不能因原计划只写一个页面而忽略本次回归 |
| 第一个 Melee 候选没有旧事件目录，但已批准输入和初始预期明确 | 首次结果可据此判断，不要求先有旧成功候选 |
| 候选对批准的预览受众完整可用，访问范围符合私有约定，且未作为正式产品发布 | 符合私有目标；不能要求先公开才算候选成功。仅未列入导航或目录，不能据此认定私有 |
| 已验收的同输入分类迁移，在创建 PR 后输入和规则均未变 | 复用原结论，不重做分类审阅；若任务包含新产品发布，继续完成该交付 |
| 更新一期数据后，本期总量及相关滚动窗口统计合法变化 | 按批准输入、约定时间窗口和已确认口径判断，不以历史数字固定不变作为正确性要求；不能只因结果由生成器产生就认定差异正确 |
| 治理文档重写了授权原则，但正式生效的 PR 模板仍强制旧 Gate | 对整体治理实施任务而言尚未替换完成；对当前仅设计任务，不冒称已实施即可 |
| 核心函数在独立情境正确，但实际产品入口没有调用修正后的机制 | 机制局部结果不能证明承诺的产品结果已交付 |
| 第 3 步文档已交付并获验收，但实际产品 bug 仍存在 | 若这些产品修复不在设计任务范围，可认定设计完成；不能因此宣称产品 bug 已解决 |

## 八、本步交付与后续范围

本步形成六类任务的完成标准、判断依据、生命周期、已有问题边界与最小交付说明，版本 1.1 已于 2026-09-11 获 Owner 验收。未改变 Step 1、Step 2 的已验收原则，没有新增审批或测试执行要求。

第 4 步将据此确定检查资格、具体触发、最小对象和独立预期；第 5—6 步确定运行、发布与恢复方法。本步不预定测试文件、数量、框架、必须全跑的任务类型或新的永久证明链。

本次已完成设计、验收与收尾留档，不实施新治理、不修复 P14、不运行项目测试、不提交或部署。下一步建议按明确授权进入第 4 步。
