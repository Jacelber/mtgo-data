## 一、日常流程的目的与终点

日常流程要让 Codex 在一次有效授权内完成约定交付，同时保留真正需要 Owner 判断的位置。授权与有限停止条件统一依 Step 2，完成标准依 Step 3，检查触发、资格与复用依 Step 4。本步说明怎样执行，不增加一套权限或检查清单。

正常路径为：恢复任务与授权 → 准备环境和相关输入 → 实现并形成候选 → 补足必要检查 → 完成约定的人工验收 → 继续约定交付 → 确认结果并收尾。

这是工作顺序，不是要求每项任务经过全部阶段。设计文档的交付对象是可审阅文档；仅私有预览的终点是批准范围内可用的预览；已约定公开发布的任务持续到相应发布确认。自动检查与实现可以交替进行，不能等到最后才验证所有内容。

人工验收仅按已确认计划设置；没有约定该验收点的任务，不因上述顺序自动新增。Owner 已验收后，提交、PR、必要 CI、合并及适用发布在原授权内连续推进，不逐项请求许可。交付完成以后不留下无限自行修复权，依 Step 2 判断后续任务或已有维护授权。

## 二、正常工作如何推进

| 环节 | Codex 应做的事 | 何时继续及保存什么 |
| --- | --- | --- |
| 恢复任务 | 读取当前明确指令、已确认计划、简短当前状态和已有成果；按影响读取必要业务规则。识别交付终点、验收点和已完成部分 | 范围清楚且获授权就执行，不重读整段历史、不重开已有选择。模糊目标按 Step 2 先明确计划；不要求先补一份授权文件 |
| 准备环境和输入 | 确认正在操作的工作区、分支、相关当前版本及输入。优先复用同一交付的可用环境与成果；只准备本次所需能力 | 环境准备不是产品验证。原输入有效时不重新抓取；有新数据到达不自动纳入本次批准集合 |
| 实现与形成候选 | 修改约定内容，必要时生成派生结果并准备可审阅入口；按 Step 4 就近验证发生变化的结果/机制 | 保存可恢复使用的候选和适用结论。没有实际生成需要就不重建；输入没变但规则改变导致输出过期时，需要更新相应派生结果 |
| 补足必要检查 | 选定实际相关检查，复用有效证明，补足新增问题；产品结果使用真实数据和读取路径 | 必要结论成立才进入依赖它的后续动作。检查错误可以范围内修正，但不能只删红灯或改变正确答案 |
| 约定人工验收 | 给 Owner 稳定、具体、可判断的成果，说明本次变化及影响判断的未决问题；技术可用性先由 Codex 确认 | 等待该判断时，不修改待验收成果或判断依据；允许继续已授权且真正独立的工作。验收后复用与局部重审依 Step 2 第 2.4 节 |
| 完成交付动作 | 按计划提交、合并、提供预览或发布候选；先确认这些操作是否已发生，避免重复创建或覆盖 | 合并只是公开交付中的中间事实。必要 CI 依 Step 4 选取新增验证或有效复用，不以工作流重新触发要求全套新绿灯 |
| 确认并收尾 | 确认约定位置实际提供相应成果；报告完成、仍未完成和已有问题的准确范围，更新必要当前状态 | 复用平台和现有成果记录，不为记录提交号再造 PR。设计/技术完成不等于长期治理收益已验证 |

这些环节之间的失败按第五节处理。有限停止条件仍只有 Step 2 已确认的那些；工作区变化、检查失败次数、分支变化、合并和发布日期本身不产生新授权要求。

## 三、最小运行环境与统一入口

### 3.1 环境只承担执行需要

每个交付使用一个可识别的工作环境，默认采用独立分支和适合并行工作的隔离工作区。同一交付继续时优先复用原可用工作区，不因重试、验收、上下文压缩或合并自动新建。原工作区确实不可用或存在无法安全混用的修改时，再转移必要成果；不覆盖来源不明的改动，也不因此重做有效输入和验收。

任务涉及集成、公开状态或远程交付时，确认所需远端事实，不能把旧本地分支当作当前生产或主分支。之后只在实际集成、远程动作或有变化迹象时刷新对应事实，不在每条命令前重新读取整套仓库状态；不依赖远端事实的本地设计工作不以云端查询为前提。云端事实、任务授权和候选内容回答不同问题，不能相互替代。

运行环境采用项目声明的解释器、依赖和配置；本地与 CI 使用相同的受支持依赖约定。环境准备按本次操作需求分层：文档审阅不加载分类器和浏览器，页面预览不因此安装全部采集依赖，分类检查不顺带准备生产凭据。

优先使用已配置、满足项目约定的运行时；缺少依赖时定位实际解释器和缺失项，在隔离环境恢复已声明依赖。不得先随意换系统解释器、全局安装或升级所有包来碰运气。任务确需新的依赖时，按普通范围内实现选择和 Step 1 原则 4 判断，不另设“任何依赖变化均须审批”。真实平台或网络限制仍如实处理。

环境确认只报告必要能力是否可用，失败时明确是解释器、依赖、路径、配置还是实际权限问题。导入失败意味着产品检查尚未执行；不能记录成分类器、候选或业务结果错误。同一环境已确认且相关依赖未变时，不重复整套环境准备。

### 3.2 一个受支持的日常入口，少量可独立恢复的操作

新体系提供一份简短日常运行说明，指向一个受支持的运行入口。入口可以是薄封装，内部调用现有合格工具；不建设任务数据库、工作流平台或新审批引擎。具体文件与命令名称在第 7 步结合最终布局确定，下表已确定每项操作的责任和副作用边界。

| 逻辑操作 | 输入与输出 | 副作用与失败边界 |
| --- | --- | --- |
| 环境准备 | 指定所需能力，返回实际运行时及可用性或具体缺失原因 | 仅准备任务所需隔离环境；不运行产品检查、抓取或发布 |
| 准备候选/预览 | 指定已有输入、相关实现和目标成果，返回可识别候选及审阅入口 | 允许必要本地生成；优先复用已有候选。采集是另一个明确动作，仅在任务已经包含时执行；预览不得自行扩大可访问受众 |
| 检查 | 指定实际交付对象及需要回答的问题，返回执行、失败、未完成、不适用或有效复用的事实 | 按 Step 4 执行；不自动生成另一份候选、不改期望、不发布。不使用默认全量作为无参数兜底 |
| 交付 | 指定候选、目标及计划内交付范围，调用对应提交/PR/发布动作并返回操作标识 | 不隐式重新抓取、分类或生成产品。已发生的动作继续跟踪；必要条件未成立时不执行依赖动作，仍可查询和修复 |
| 查询/续作 | 指定已有任务、候选或操作，读取实际状态；明确需要继续的未完成环节 | 查询本身只读；重试有副作用的动作前先辨明远端是否已成功。续作不能自动从头运行，也不能偷偷扩大目标 |

这些是接口能力，不要求新建五套脚本，也不要求 Owner 逐操作输入命令或许可。检查选择的依据由 Codex 从实际改动和计划判断，入口不把未知路径、缺少旧标记或 PR 格式不符自动转为全量执行。

入口必须能说明自己现在处于哪一步、针对什么对象、是否已经执行及下一步缺什么条件。已有工具或平台日志能表达的事实不再复制为永久台账。包装层的错误不能被误报为凭据过期、产品失败或 Owner 授权不足。

## 四、候选、验收与发布对象如何保持一致

### 4.1 候选是一份可定位成果，不是新的审批凭证

候选可以是版本化文档、页面及配套数据、或者可部署产物，取决于交付目标。需要时能从现有记录找到：对象在哪里、使用哪批输入和相关实现、已有验证与验收覆盖什么、还缺哪个交付动作。信息可由现有文件、产物标识、日志和任务记录共同提供，不要求固定表格、签名、全链摘要或每 PR 再建档案。

在候选仍用于审阅、交付或恢复故障时，不清理其唯一副本及必要输入。正常收尾后的保存期限和可部署版本归档由第 6 步定义，本步不要求无限保留所有中间文件。

验收时使用稳定候选和稳定判断依据；对候选的实质修正形成可区分的新版本，不在 Owner 正在看的入口中悄悄替换内容。已有验收仅在实际影响范围内失效，技术修复恢复原决定时可复用，不按文件字节或提交号不同自动重开验收。

### 4.2 默认发布实际验收的产物

对于需要生成产品的任务，目标流程是先形成可部署候选，再对该对象完成必要检查和约定验收，发布时直接使用它。发布操作不能暗中读取更新后的输入、重新分类或生成另一份产品，却沿用旧候选的验收结论。

如果发布平台必须执行打包或环境适配，尽量将影响产品内容的步骤前移至候选形成阶段。无法前移的必要变换须明确其实际影响，验证新增差异；不得因称为“部署步骤”就假定输出等同。相关业务或体验未变时复用验收；改变 Owner 已决定的维度时，只提交受影响部分，依 Step 2 处理。

现有平台或工具暂不支持直接发布候选，并不意味着允许偷偷重建。实施时先修正相关入口或按上述方式完成可判断的适配；没有有效方法确认最终对象符合要求时，暂停受影响交付。具体存储、跨环境取用与完整版本组成在第 6—7 步落实，不把当前流水线的限制固化为新治理原则。

### 4.3 从私有候选到公开产品

预览的实际可访问受众与发布状态必须符合批准范围，未列导航不等于私有。若公开状态会改变目录、路由、统计或打包内容，应在受控候选环境形成面向正式发布的结果，再完成相关验证；不能先公开才证明是否可用。

公开前只补环境和状态转换新增的问题。原输入、分类迁移、无关页面与业务验收不会因“现在准备公开”全部失效。改变未经批准的受众或业务公开范围，依 Step 1 原则 4；已包含在计划内的公开动作不重复申请授权。

## 五、失败从哪里继续

### 5.1 先区分失败位置和远端实际结果

| 发现的问题 | 保留什么 | 从哪里继续 |
| --- | --- | --- |
| 实现或候选结果错误 | 正确输入、未受影响候选部分和结论 | 修复实际原因，必要时只更新受影响派生结果，按 Step 4 补验证；Owner 判断边界变化才局部重审 |
| 测试预期、样本或选择逻辑错误 | 独立业务预期及未受错误影响的证明 | 修正方法，重新取得它原本未能证明的必要结论；不顺手覆盖期望，不让其它检查陪跑 |
| 缺依赖、错误解释器或本地工具异常 | 已有候选、输入和成功验证 | 恢复所需运行能力后，从尚未执行的操作继续；不把环境报错误当产品失败 |
| GitHub 等状态查询暂时失败 | 已成功的产品检查和现有远端操作 | 对同一对象重新查询；必要时有限退避。只读查询恢复无需新的业务验收或流程例外 |
| 请求超时，无法判断 PR、合并或发布是否已发生 | 原请求目标、已有操作标识和候选 | 先查询实际结果；已经发生则继续跟踪。确认原操作不会再产生该副作用，或有依据确认同一操作可以安全重试时，才重试写入；暂未查到记录不等于未发生，状态未知时不盲目重复写入 |
| 必要证据丢失或不可访问 | 尚可定位的实际对象和其它有效证明 | 优先恢复记录；确实无法恢复时允许补做对应验证，不为遵守“不重跑”而永远卡住 |
| 发布未成功或发布确认失败 | 可部署候选、原验证和已知远端状态 | 按失败位置恢复传输、部署或确认；已知发布不符合要求时按第 6 步已授权恢复策略处理，本步不授予任意回滚 |
| 出现新的业务决定、实际权限限制或缺少不可替代信息 | 已完成成果和不受影响工作 | 按 Step 2 暂停相关动作，具体说明需要什么；不把所有技术故障一起提交 Owner 作例外决定 |

暂未查到记录，不单独构成“确认未发生”。原操作可能仍在受理、执行或状态未知时，继续查明；只有确认原操作不会再产生该副作用，或有依据确认对同一目标、同一内容的重试不会产生额外副作用时，才重试写入。使用现有操作标识和平台能力，不默认另建新请求；不能仅凭“发布同一个版本”推断安全重试，也不为此新增永久台账。无法确定时，不盲目重复写入。

任务暂停、取消或目标变更时，停止发送与当前指令不符的新操作，并核对本任务已发出、仍可能产生相关影响的远端操作。在指令范围及实际权限内，取消或阻止不再获准的待执行影响；不能波及其他任务。这是落实已有指令的必要处理，不逐操作重新申请取消许可。无法取消或无法确认停止时，如实报告已知状态和剩余影响，不能把本地停止报告成远端已停止。已经完成的写入不因任务取消而自动获得回滚授权，仍依 Step 2 和第 6 步恢复策略处理。处理限于本任务必要的停止收尾，不自动创建长期监控，也不假设所有远端操作都可撤销。

重试依据来自可恢复故障、条件变化或已定位的修正，不是“再试几次碰碰运气”。允许对同一提交必要重试，不设固定失败次数触发重新授权；也不无限重复已经证明无效的动作。没有有依据的下一步时，如实报告事实、未知点和缺失条件，不编造根因。

### 5.2 红色运行怎样恢复为可继续交付的事实

产品验证、平台查询和部署确认在实现上须能分开恢复。一次 GitHub API 查询失败，不应使已完成产品验证的证据失效，也不应要求改变提交来触发全部测试。

目标做法是重新查询或重新运行失败的必要作业；若需要新运行承接，明确引用同一相关对象及已有有效结果，只执行缺少的环节。历史失败运行保留真实状态，新的恢复结果记录新的事实，不把旧红灯口头称为绿灯。

平台强制状态仍为失败或无法接收恢复结果时，先区分它是否保护仍未满足的必要条件。真实必要条件未成立，不发布；条件已通过有效方法证明，但状态入口无法表达续作时，修正实际接续问题。切换前的旧强制状态按已授权治理实施与统一切换安排替换；切换后按 Step 2 的范围内修复与 Step 4 的资格标准处理，不要求另起治理任务才能修正普通执行故障。不能靠聊天声明伪造状态，也不要求 Owner 每次批准技术例外；需要改变质量底线或实际外部权限时仍依已验收边界处理。

第 7 步切换前必须让必需检查与续作机制配套：独立查询失败可恢复、有效复用可表达、历史失败不永久否决新的有效结果，且必要产品失败仍会阻止交付。这不是本步提前修改平台设置的授权。遇到无法在实际权限内处理的限制，遵循 Step 2，如实说明具体阻断。

仅仅“整个工作流重新运行了”不必意味着所有产品检查重做；入口应按原对象及证据状态恢复相关环节。恢复入口也不能默认信任任何旧绿灯，适用性依 Step 4 和 G3 判断。

## 六、主分支变化与并发

### 6.1 代码集成按实际影响更新

| 主分支或共享状态变化 | 对候选及证明的处理 |
| --- | --- |
| 无关文档、元数据或独立产品变化 | 保留未受影响证明，完成必要代码集成；不因远端 SHA 不同直接作废候选或要求重跑 |
| 相同文件不同位置变化，但结果可明确合并 | 在原授权内处理；检查是否有真实组合影响，不以“无文本冲突”代替判断，也不自动全量回归 |
| 相关规则、数据契约、共享资源或计算机制变化 | 保留不受影响输入和证明，更新实际受影响候选部分，补足组合后新增验证；只按 Step 2 重审 Owner 判断发生变化的部分 |
| 同一业务含义出现无法从已确认要求决定的冲突 | 不自行选择新的业务结果；说明差异并依 Step 1 原则 4 提出具体问题 |
| 出现新的待接纳数据 | 不顺带并入已验收输入；仅在已有授权与批准范围允许时处理，不能用“主分支最新”代替数据接纳决定 |

集成应保留其他已交付变更。尤其是整站部署：另一个产品的更新即使不影响本任务计算，也可能被旧整站候选覆盖。不能以“与本任务无关，所以可直接发布旧包”处理；应保留最新已交付部分，重组确有必要的组合并确认组合风险，复用未受影响的单项结论。

### 6.2 开发可以并行，共享写入协调

不同任务可以使用独立工作区并行准备。写同一候选、当前状态或部署目标时，识别现有修改及正在执行的操作，协调写入顺序，避免覆盖他人尚未说明的成果。不会影响待验收对象且不依赖其结论的工作才可继续，依 Step 2。

发布前在实际写入边界确认目标当前版本与候选的覆盖关系；同一部署目标的发布需串行协调，并在取得执行机会后重新判断是否仍可发布。这一判断还包括依据当前有效指令，确认任务的暂停、取消或目标变更没有使该发布失去授权；不要求重新向 Owner 申请发布许可。仅排队不保证安全：较旧候选可能在较新产品之后获得机会，必须防止它覆盖新结果。

不要求整个开发过程全局串行，也不对每个提交建立父节点审批链。发现共享状态变化时先判断实际影响，不以任何变化为由重新取得 Owner 授权。恢复与正常发布之间的优先级、取消和防覆盖实现留给第 6 步，本步只明确它们必须共享同一写入协调边界。

## 七、发布确认、报告与结束

公开交付至少需要回答：计划内远端动作是否真正完成，目标位置是否提供预定候选及必需内容，真实环境新增风险是否已经确认。构建成功、合并成功、部署请求已提交，都不能单独替代实际发布确认。

发布确认复用与环境无关的结论，仅检查目标版本、实际入口和环境相关的必要行为；不再次执行同输入漂移、全部统计机制测试或全站浏览。检查范围依 Step 4，部署身份确认、资源范围及失败恢复细节由第 6 步定义。若实际对象不是预定候选，不能沿用预定候选的结果宣布发布成功。

报告只说明成果位置、本次完成的结果、关键验证或复用事实、尚未解决且影响完成的问题及下一步。把产品错误、运行失败、状态未明和真实权限限制分开，不让 Owner 从一串日志中猜下一步该做什么。

交付状态有实质变化时更新简短当前状态，复用已有提交、PR、运行及产物记录；不为每个技术动作增加状态提交，不用 STATUS 记录授予权限，也不要求先把所有远端元数据写回仓库才算技术动作成功。必要收尾信息并入当前获准交付，不能制造仅重复平台事实的独立 PR。

本地文档已验收、产品已发布、长期效果已观察是不同结论；按本次终点如实结束。第 8 步才通过真实任务观察重复劳动、Owner 技术介入和总维护成本的改善，不能把这份设计的完成当作效果已实现。

## 八、实施时的最小验证情境与后续范围

以下是本步设计推演和未来实现验证的输入，不是当前已执行的测试；也不要求所有任务重复运行。入口或对应续作分支实现/改变时，按 Step 4 就近验证正确、错误和正常变化情境，组合时只补新增衔接风险。

| 情境 | 新流程必须做到 |
| --- | --- |
| 同一交付合并后继续上线 | 继续原授权，复用输入和证明；不重新开任务或例行新建工作区 |
| 已验收分类修正，但产品仍是旧分类输出 | 用原批准输入更新必要派生候选，补真实展示结论；不重做同一分类业务验收 |
| 系统 Python 缺少已声明依赖 | 明确检查尚未运行，使用正确隔离运行时恢复依赖；不重抓数据、不把候选判错 |
| 产品检查成功，后续查询 API 暂时失败 | 只恢复查询/状态步骤，同一提交可以重试；保留原产品证明，不要求 Owner 流程例外 |
| 发布请求超时但实际上已经成功 | 查明并继续确认现有部署，不重复发布或生成另一候选 |
| 请求超时后暂未查到记录，但原操作可能仍在受理 | 不把查询无记录当作未执行；继续查明，或在有依据确认同一操作不会产生额外副作用时安全重试；不默认另发新请求 |
| 提交号变化，相关对象与环境未变 | 复用有效结论；相关代码确实变化使原结论失效时则补对应验证 |
| 必要检查发现真实回归 | 阻止相应交付，继续范围内修复；不因已经验收就放行，也不因失败撤销授权 |
| 审阅期间另一个任务修改共享页面数据 | 不悄悄更换审阅对象；处理并发后按实际影响确定哪些结论或验收需要补足 |
| 另一产品已发布更新，本任务持有更旧整站包 | 不覆盖新内容；保留最新已交付部分并补组合验证，不让无关产品重复业务验收 |
| 队列中的旧发布晚于新产品或恢复动作取得机会 | 在实际写入边界拒绝过期覆盖，依第 6 步确定方式续作，不仅依赖排队顺序 |
| Owner 取消任务时，本任务发布仍在队列中 | 停止新的相关操作，在指令与权限内取消或阻止排队影响，不重复申请取消许可；无法确认远端停止时报告剩余影响，已完成写入不自动回滚，不影响其他任务 |
| 任务只要求设计文档 | 完成文档检查、约定验收和留档即到终点，不因为主流程有发布阶段而发起部署 |

本步形成正常流程、环境与逻辑入口、候选一致性、失败恢复、并发与收尾设计。第 6 步继续确定完整可部署版本、保存和恢复策略、部署确认与防覆盖机制；第 7 步落实文件/命令映射、现有工具替换和外部设置统一切换。

本步版本 1.1 已于 2026-09-11 获 Owner 最终确认及验收，收尾留档完成。本次仅设计留档，尚未验证任何运行入口或平台实现，也未改变已验收的前四步。下一步建议按明确授权进入第 6 步发布与恢复设计。
