## 一、恢复什么，以及不恢复什么

产品恢复是把已经保存、仍适合使用的完整可部署版本重新提供到约定位置。恢复过程不抓取新数据、不运行分类器、不计算统计、不从旧源代码重新构建产品。它与修复代码、新候选生成和重新选择业务结果分开。

初版按“一个部署目标对应一个完整产品包”设计。MTGO 与 Tabletop 若共用同一站点部署，就完整保存该站点所需文件；它们的业务统计仍然分离。恢复整个包可能同时撤回两个产品在该次发布中的变化，不能把整站恢复报告成只恢复其中一个赛制或页面。

本步不建设单产品拼装式紧急回滚：从不同版本抽取文件可能破坏共享资源、目录和数据契约。确需保留另一产品的新内容时，按 Step 5 形成新的组合候选并补组合验证；这属于新的候选交付，不能冒称原版本直接恢复。

| 动作 | 能解决什么 | 不能据此声称什么 |
| --- | --- | --- |
| 恢复完整线上包 | 撤回该包中的页面、脚本、公开数据和资源变化 | 不保证撤销外部系统动作、浏览器本地状态或已被复制的数据 |
| 修复源代码与生成器 | 避免下一次候选再次产生同一错误 | 不代表线上已经更新，也不等于恢复旧产物 |
| 调整业务数据、撤回公开信息或修正外部记录 | 按明确范围处理相关源头和已发生影响 | 不因页面恢复自动取得该动作授权 |
| 修复新治理自身故障 | 恢复新原则下的正常执行能力 | 不恢复整套旧治理，不回退仓库来重新启用旧 Gate |

## 二、完整可部署版本的组成与最小记录

### 2.1 包的边界

完整包包含实际部署所需的页面、前端脚本与样式、批准公开的数据和目录、已使用的本地资源，以及保持路径和运行行为所需的部署文件。前端运行确实依赖的配置或 Schema 也应包含；不能只保存一份统计 JSON 或一个提交号。

包不包含与产品运行无关的治理规范、CI 工作流、生成器环境、原始采集响应、私有候选、凭据、缓存或全部中间产物。不能因为“完整”而把整个仓库打包公开。恢复使用当前受支持的部署工具，不执行归档中的旧脚本，不让旧产品包恢复旧治理权威。

完整性以部署依赖闭合为准，不宣称控制外部服务。外部图片地址、第三方 API 或域名服务仍可能变化；其失效未必能靠旧包解决。只有已在批准范围内本地化的资源纳入包，不借归档新增抓取、复制或公开范围。

### 2.2 版本记录保持最小

每个包应能定位其不可变版本标识、云端位置、完整性校验值、所属部署目标，以及现有来源/验证记录。发布后关联实际部署记录及结果；不再复制全量测试日志、Owner 对话或提交父节点证明。

完整性可使用平台已有的可靠校验值；不足时对最终包计算一个校验值，取用时核对。它回答“拿到的还是所选完整包吗”，不代替产品正确性、来源可信度或 Owner 授权，也不扩展成每个文件、每个阶段的签名系统。

同一部署目标只需一份最小当前控制记录，分别表达实际部署事实、产品确认结论、适用恢复前版及正在处理/已失效的写入操作。实际已经部署不等于已经确认可用，最后确认可用的版本也不必是当前实际服务对象。优先复用平台部署与运行标识；缺少必要事实时才补最小状态，不新建平行数据库或要求每次查询都写一份台账。它是执行与并发控制事实，不是 STATUS 授权文件或新的人工审批凭据。

包由受支持的候选流程存入受控归档，不能只凭一个校验值接受来源不明的外部压缩包。下载与展开须拒绝损坏、越界路径或脱离目标目录的链接；不能让恢复覆盖工作区或读取包外文件。这些机制按 Step 4 K3/K4 验证，普通恢复只做必要对象核对，不重演攻击样例。

## 三、云端保存、期限与失效

### 3.1 已确认的保存方向

以受控访问、独立于临时工作区和 CI 清理周期的云端持久归档为主。该位置必须能由获准发布和恢复入口取用，并支持不覆盖已有版本、必要保留和删除。不能把“曾经公开过”视作将全部历史版本永久公开的授权；候选及归档的可访问受众继续受已批准范围约束。

具体服务尚未选定。第 7 步在实施前核实可用存储、访问控制、容量成本、发布入口取用方式和删除能力；优先复用满足要求的已有设施。新增外部账号、权限或付费选择依 Step 1 原则 4，不默认为本次设计已经授予。无法落地持久存储时，应如实提出设计/实施缺口，不能将本地唯一副本或会自动过期的 CI 产物悄悄当作等价替代。

本地可以保存最近恢复包以加快处理，CI 产物可以用于传递；二者均不是唯一恢复保障。不要求新增跨云双活、永久全量备份或后台监控平台。

### 3.2 建议保留规则

| 对象 | 本步建议参数 | 清理边界 |
| --- | --- | --- |
| 当前线上完整包 | 在它仍是当前线上版本期间固定保留 | 不按年龄或普通清理删除唯一可用副本 |
| 最近一个仍可用于恢复的完整前版 | 在未被新的适用前版替代前固定保留，即使超过 30 天 | 新版本确认后再调整保留引用，不能先删再上传 |
| 其它正式发布包 | 自实际发布起保留 30 天 | 期限后可随正常获准归档维护清理；被当前事件、验收或恢复引用时暂不清理 |
| 未发布或失败候选 | 任务仍在审阅、交付或故障处理中时保留；结束后保留 7 天 | 若承担当前恢复或问题定位所需唯一证据，延至相关处理结束；不因此保留全部临时环境 |

30 天与 7 天是本步的初始设计建议，不是测得的最佳值。实施前用真实包体积及发布频率核对成本；如需改变承诺的恢复窗口或固定保留保障，说明影响后依已确认决策边界处理，不靠系统静默过期降低保障。

清理只针对已明确归档对象和已到期引用；不能借此删除源数据、Git 历史、其它任务资料或必须保留的记录。本设计不自动创建定时清理任务；可以在已授权发布收尾时做相关归档整理，首次启用前明确安全选择范围。

### 3.3 保存失败与恢复资格失效

新候选成为正式发布前，确认它已经完整保存，且当前存在的适用恢复包仍可定位和取用。校验可复用同一对象已取得的完整性结果，不要求每次下载所有历史包或演练回滚。

若新包尚未保存成功，或该次发布依赖的恢复包不可用，先恢复必要归档能力，不覆盖当前线上结果；这只暂停受影响的生产写入，不暂停设计、实现和其它独立工作。不能因归档检查失败反而先回滚一个运行正常的站点。

归档存在不代表永远可以恢复。已知包含需要撤回的公开内容、相关契约已不兼容、会复现本次故障、或来源/完整性无法确认的包，应标为不适用。保留与恢复资格分开：需要排查而保留的错误包不能列为可用前版；存在明确删除要求时，保留策略不能阻止执行已获准删除。

首次启用若没有旧可用包，不编造历史基线。优先从仍可取得的真实已部署产物建立基线，确认其实际覆盖和已知问题；不能从当前主分支重新生成并声称拿回了原线上版本。确实没有可恢复旧版的首次发布，需要在该任务计划中明确其恢复限制和失败处置，再按计划执行，不制造永久的首次发布例外审批。

“可用”指与该版本适用范围相符的必要结果已有有效证明，不是整个站点历史 bug 清零。首次治理迁移不因 P14 已有无关缺陷而要求全部修复，但不能把已知无法完成恢复目标的旧版标为可用。

## 四、正常发布与发布确认

1. 使用 Step 5 形成并已完成必要验证及约定验收的候选。需要组合其它已交付更新时，先形成可区分的新组合候选并补相关验证，再进入发布。
2. 完成云端归档与必要完整性确认。取得该部署目标的写入机会后，确认当前有效指令、实际线上版本、候选覆盖范围和恢复前版仍相符。
3. 由当前受支持部署器取用指定包发布，不读取当前输入重新生成，不执行包内旧工具。需要重试时依 Step 5 区分未发生、已发生和未知，不盲目重复写入。
4. 如实关联已确认发生的实际部署对象及操作，不等待产品确认全部通过；再按下表取得产品确认结论，分别更新可用与恢复资格。实际对象尚未确定时保留未知状态，不将最后已知版本冒充当前事实。只有满足相应必要确认且仍适用的版本，才能取得可用或恢复资格；新包上线但确认失败时，保留仍适用的原恢复前版，不将故障包提升为可用前版。历史失败记录不改写，新的事实关联现有操作。

| 必要发布确认 | 最小方法与限度 |
| --- | --- |
| 操作真正完成且对象正确 | 平台实际部署记录对应指定目标和包；发布提交号可作来源，但不能强求回滚产品来源等于当前主分支 SHA。平台标识不能证明线上内容时，结合一个已有或最小非敏感版本标识核对实际服务对象 |
| 必要产品内容实际可用 | 对受影响入口及环境相关资源做聚焦确认：不只判断返回成功，也确认关键数据被读取、必要图片实际可用或合法降级、关键操作有预定反馈。复用与环境无关的漂移、计算和未变页面结论 |
| 公开与组合边界成立 | 目标受众和正式入口符合批准范围，必要文件没有遗漏，未混入私有对象；整站包没有撤回别的已交付更新。使用本次必要范围，不再巡检所有历史数据 |

新部署可能尚未对外一致可见时，保持“发布确认中”，按平台实际状态和聚焦读取继续判断。超时、API 暂不可达或一个尚未更新的缓存结果不单独证明产品错误，也不自动触发回滚；不能因为平台任务绿色就提前报告成功。

恢复成功同样需要确认所选旧包已实际提供服务，但不重新要求批准过的分类迁移、全量统计测试或恢复机制演练。恢复是否解决所针对的故障须取得具体结果；仅部署旧包成功而页面仍坏，不能报告故障恢复完成。

## 五、Owner 指令触发恢复

### 5.1 本步建议的授权模型

只有 Owner 明确下达回滚指令才恢复。普通发布或故障修复授权不包含 Codex 自行决定回滚；发现缺陷、检查失败或 CI 红色都不自动触发。收到指令后直接执行对应恢复，不逐动作再询问许可，也不授予历史任务永久监控或恢复权。

本步验收是确认设计，实际存储配置、入口实施、普通发布或恢复仍须属于已授权工作并遵守统一切换安排。Owner 对具体任务的更窄指令优先；任务暂停或取消后，不能借此前发布授权自行回滚已完成写入，按 Step 5 的停止收尾与已有恢复授权处理。

### 5.2 执行核对不重新判断是否值得回滚

- Owner 已决定回滚，不要求 Codex 证明故障严重、复现故障、将当前版标为失败或重跑产品测试，才执行该决定。
- 当前实际线上对象仍是指令对应版本，没有后来交付改变恢复所涉及的范围；在取得写入机会时再次确认。
- 指定目标默认是本次发布前实际在线、已经确认可用且当前仍适用的完整版本；核对归档可取用、完整且未因撤回要求或相关不兼容失效。不重新证明旧版能够解决故障，不自动另选更早版本。
- 恢复只撤回本次发布在同一部署目标内带来的变化，不撤回后续其它交付。整站恢复可能撤回本次同时发布的 MTGO 与 Tabletop 更新，这一连带范围明确包含在本策略的已验收取舍中。
- 核对实际权限及未结束写入，落实指令包含的自动发布暂停，避免冲突操作覆盖恢复结果。

报告恢复对象和整站影响后连续执行；仅有实际对象、归档或冲突写入障碍时查明对应事实。不以重新证明整个产品正确为恢复前提，也不把机械核对变成对 Owner 决定的再审批。

没有回滚指令时，范围内诊断和修复继续，不因任何故障类别自行回滚。已有后续交付、需要选择更早版本或扩大撤回范围时说明具体影响，不能擅自扩大原指令。

恢复只选择指令对应的前版，不在多个历史版本间试退。对同一目标的传输或确认故障可以依 Step 5 必要重试；确认旧版实际提供服务后如实报告，不自动选择更大范围。归档中保留更早包不等于已授权撤回更多交付。

### 5.3 回滚后的自动发布暂停与解除

Owner 回滚指令包含暂停该部署目标的自动发布，登记恢复意图时一并保存。回滚完成、撤销恢复意图、修复代码、测试通过或单次发布修复版都不自动解除；采集、准备、诊断和其它已授权工作继续。暂停无自动到期时间，不设置隐性后台等待任务。

解除依据 Owner 明确要求“恢复自动发布”，或事先明确授权“完成约定修复后恢复自动发布”且条件已满足。Codex 执行解除，不重复询问，也不凭普通修复授权推断可以解除。解除指向当前这一次恢复暂停，不能用旧指令解除后来的暂停。已发出写入和恢复意图须先处理清楚；解除只恢复后续自动流程，不自动制造一次新发布。单次任务发布与恢复自动更新是两个不同动作。

## 六、恢复步骤、并发和防止再次覆盖

### 6.1 恢复的执行顺序

1. **固定恢复目标与范围。**记录本次故障部署、拟恢复包及选择依据，复用现有操作记录。先取用并核对目标包，不边覆盖线上边尝试找齐文件。
2. **协调该目标的写入。**在当前授权内暂停或取消会与本次恢复冲突的待执行发布，使它们不能在恢复后自动重放；不取消无关任务。新提交合并不等于允许它随即覆盖恢复结果。
3. **处理已经发出的操作。**核对是否仍有会改变该部署目标的运行中请求。请求取消不等于远端停止；能安全取消则取消并确认，不能确认时不让恢复与未知写入竞跑。必要时等待已发出操作到可判定状态，再重新判断恢复条件；依 Step 5 报告剩余影响，不启动无限后台监控。
4. **取得独占写入机会并复核。**检查当前指令、线上实际部署和所选包仍适用。若线上已被其它交付改变，旧恢复请求失效，重新判断实际故障与范围，不强行恢复。
5. **部署所选完整包。**只下载、核对、必要解包/传递并发布；不抓取、分类、计算、构建或执行旧治理工具。恢复使用当前可信部署机制，产品来源可以是旧版本。
6. **确认并更新事实。**按第四节分别表达已经发生的实际部署、产品确认结论和适用恢复前版，不等故障消除才承认版本已改变。确认所选旧包实际提供服务及目标故障的恢复结果；失败时保留原目标、包和事实，从具体失败处处理，不报告成功，也不擅自换更早版本。

执行中断或换环境续作后，在下一次可能冲突的写入前，核对远端操作、实际服务对象与现有控制记录；记录过期时根据查明事实修正，无法判定时保留未知状态，不依赖旧记录继续写入。这是对现有事实的恢复，不新增审批台账或无关产品重测。

### 6.2 正常发布与恢复使用同一写入边界

所有会写同一生产目标的受支持入口，包括合并触发、手工触发、重试和恢复，必须遵循同一协调机制。仅在某一个工作流配置串行不能保证其它入口不会覆盖；第 7 步须核对实际入口与相关平台设置。无法纳入的真实外部写入能力须明确报告，不能宣称已获得端到端防覆盖保障。

初版采用目标级串行写入，加上当前操作是否仍有效的核对。正常发布登记准备时的实际部署基准；恢复决定使与其冲突的旧请求失效。写入前将原基准/操作与当前受控记录比较，旧请求不能因曾经获准而永久有效。可使用现有唯一部署操作标识，不只比较产品版本号：即使恢复后内容回到 A，它也是一次新的部署，旧的“基于 A”排队请求不能因此重新合法。

有效性判断与实际写入必须处于同一协调保护范围，不能查完版本后释放保护再发布；保护持续到远端副作用已可判定。具体使用平台串行能力或最小原子控制记录，在实施时选择并验证，不建设提交父链审核或多阶段授权系统。

恢复请求应优先于尚未执行且会冲突的普通发布，通过使相关待执行操作失效、取消或重新判断来实现；不假设平台天然按请求先后或恢复优先级排序。已经开始的写入不能靠标记失效撤销，必须按第 6.1 节查明其实际状态。

恢复之后，旧任务若仍有有效授权，可保留输入和证明重新形成合适候选，处理故障并补受影响验证后继续；不能自动重放失败包，也不要求把所有正常开发都暂停。仅治理文档变更不自动部署产品，避免修复治理时又把故障产品发布回来。

## 七、无法恢复与恢复后的源代码处理

| 情况 | 处理原则 |
| --- | --- |
| 恢复包缺失、过期、损坏或权限暂不可用 | 保留当前已知线上状态，恢复取用能力；不能以重新生成冒充旧版恢复。需要更早目标或新存储权限时依实际影响处理 |
| 目标包包含现已禁止公开的数据或会破坏新契约 | 不部署该包。处理撤回或新候选修复所需决定，不能为了回滚重新公开应撤回内容 |
| 归档或部署平台整体故障 | 如实说明恢复暂不可执行，保留目标和候选；本地缓存可辅助，但不能绕过访问或发布边界，也不能声称本机文件等于线上已恢复 |
| 部署响应未知 | 先查实际线上版本和操作状态；按 Step 5 的安全重试条件处理，不连续发多个恢复请求 |
| 已回到目标版本但故障仍存在 | 报告产品恢复未达到目标，调查实际原因；不自动试退全部历史版本 |
| 页面恢复不能撤销采集、公开泄露、外部写入或用户本地状态 | 说明恢复的实际限度，必要的独立处理按相应授权执行；不把“页面看起来正常”当作影响已全部消除 |

线上恢复后，同一交付内的必要源代码修复继续按 Step 2 执行，避免下一次生成再次引入故障。不能直接回退整个仓库到旧提交，因为这样可能撤销其它业务修改并重新带回旧治理；必要代码修正以当前规则和实际影响为依据。

若任务目标是上线某个新功能，恢复到旧版通常只是故障止损，不等于该新功能已经交付。若任务只要求恢复可用服务，则按该明确终点报告完成。Owner 暂停、取消或改变目标时遵守当前指令，不借“还需修根因”扩大任务。

## 八、首次启用与机制验证

整体设计确认并获准实施后，先准备受控归档和取用能力，再接入正常发布与恢复入口及共享写入协调，逐块验证后统一切换。不可先删旧发布能力，再等待尚不存在的新恢复路径；旧治理在统一切换时退出，不保留活动回退开关。

首次建立的基线包要来自可核实的实际产品产物，标明已知限制；必要检查针对完整取用、真实入口与恢复目标，不借此要求全站旧缺陷清零。初始归档和恢复入口未就绪时，继续无关设计和实现，受影响生产切换暂不进行。

机制故障情境在隔离准备环境或专用验证目标中完成，不主动损坏、清空或回退生产产品来制造验证证据；真实发布或恢复时，另行确认该次实际结果。

| 实施/机制变更时的最小情境 | 必须证实的结果 |
| --- | --- |
| 正常候选发布，并有适用前版 | 保存的是实际候选，正常交付和恢复引用正确；没有重新抓取、分类或生成 |
| 恢复指定完整包 | 验证目标实际提供所选版本，所针对问题消失；当前治理和部署工具未回退 |
| B 已实际部署，但产品确认失败，或确认前执行中断；A 为发布前适用版本 | 查明实际对象并分别记录确认结论，保留仍适用的 A；不将 B 自动提升为可用前版，不让旧控制记录成为后续写入依据 |
| 包缺失、损坏或内容超出目标路径 | 拒绝无效恢复，原线上内容不因取用失败被清空；不执行归档旧脚本 |
| 超过 30 天仍是当前版或唯一适用前版 | 固定保留有效，普通清理不会删掉恢复保障；无关过期对象可清理 |
| API 查询失败或第三方资源故障 | 不误判为本次包错误并触发无效回滚；产品证明仍可复用 |
| 当前版本已被后续交付改变 | 原恢复请求不再覆盖新结果，范围问题如实处理 |
| A → B → 恢复 A 后，旧的基于 A 发布请求继续执行 | 旧操作仍然失效，不因产品版本号再次相同而绕过防覆盖 |
| 请求取消但远端部署仍可能运行 | 不报告已停止，不与未知写入竞跑；先确认实际结果，再继续必要动作 |
| Owner 取消任务，或旧包的公开资格被撤回 | 不沿用旧任务/旧包资格继续恢复；处理必要停止收尾，不自动扩大权限 |
| 两产品共用部署包，回滚将一起撤回本次更新 | 能准确说明和确认整站范围；存在后续另一产品更新时不按原包自动回退 |

这些是设计情境，不是当前测试结果。不在每次普通开发、发布或恢复重做故障演练；K3/K4/G3 的机制变化按 Step 4 验证，日常操作只确认实际对象及本次必要结果。

## 九、已确认设计与后续落实

- 已确认：以云端持久归档为主；具体存储、权限和成本实施前核实。
- 本步已验收取舍：一个部署目标使用完整包；当前版和最近适用前版固定保留、其它正式包 30 天、结束候选 7 天；按 2026-09-12 Owner 修订，只有 Owner 指令触发回滚并暂停自动发布，解除依明确指令或提前授权；目标限定为对应前版，不自动跳选更早版本。
- 第 7 步落实：具体云端存储与成本、包路径/命令映射、现有流水线改造、外部设置和所有写入入口接入方式；不足之处必须在切换前解决，不能把未实现的方案当成已有保障。
- 第 7 步部署失败核查：确认实际机制失败时是否保持原完整版本。若可能留下部分写入，须在切换前明确识别方式、未结束写入的处理及 Owner 指令下的恢复路径，不能将已确认的部分损坏归为“线上未受影响”。无法确定操作归属或排除其它写入影响时按未知状态处理，不擅自扩大恢复范围；本项不是对当前平台部分写入行为的断言，也不授权机器决定回滚。
- 当前未执行：存储创建/付费、权限更改、包归档、发布、恢复、项目测试或实际治理切换。设计验收本身不授权这些动作。

本步版本 1.1 已于 2026-09-11 获 Owner 验收，收尾留档完成。下一步建议按明确授权进入第 7 步整体替换与实施安排；不重新打开前五步已确认原则。

## 参考的平台约束

以下是本轮核实的通用平台资料，不是本仓库设置或实现的实测结论：

- GitHub Actions 产物有到期清理，默认保存 90 天；下载要求登录并有仓库读取权限。因此不能仅凭“存放在 Actions”认定它是永久或 Owner 私有的归档。[下载工作流产物](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)
- 删除工作流运行会同时删除其关联产物。因此恢复保障不能只依赖一条可被清理的 CI 运行。[工作流产物](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)
- GitHub 支持按共享并发组限制部署，但环境名称本身不会让未配置对应并发的其它入口参与协调。新设计仍需核对所有实际写入入口。[使用 GitHub Actions 部署](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments)
