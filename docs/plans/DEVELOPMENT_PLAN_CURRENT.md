## 3. 已完成单元：B 构筑统计身份迁移

以下保留已批准的 B1—B4 范围。先前宣布 B 完成过早；本次已补齐 B2 输入兼容和 B4 对应验证，并完成受影响产物同步。实现、验收证据与范围限制见 [B 记录](CONSTRUCTION_IDENTITY_IMPLEMENTATION.md)。

目标：同一副牌仅更换同一实体的合法别名时，构筑向量、平均牌表、出现率、Core/Flex、代表牌表、偏离度与跨周比较不应变化。

### B1 固定统计旧侧与影响清单

保留本轮最终分类结果、原始输入及旧统计实现；从原始表示独立计算旧侧，不能让新归一化先作用于旧基线。盘点各实体别名／多面表示实际进入的平均牌表、基准、偏离度、medoid、归一化锚点和跨周比较。按实际依赖确定涉及赛制、周次与当前公开产品，不先全站重建。

### B2 接入已有身份能力

复用本轮建立的实体解析与别名能力，必要时整理为分类和统计可共用的入口，不另建别名表。实体识别与分类用途分离：Atraxa 等即使在颜色分析中作为目标忽略，其实际张数仍须进入构筑统计。分割牌／历险牌按实体计一次；同副牌两个别名先合并张数，出现率每副只计一次。

保留普通／雪境基本地的既有比较等价口径，不将其称为同一实体。原始牌名、来源、玩家、赛果、套牌稳定标识及已有 Unknown 接纳定位不因此次统计迁移而改写；确有消费者依赖计算身份时明确列出，不顺带重定义记录 ID。

### B3 核对所有实际消费者

检查均值、出现率与 Core/Flex，再检查 medoid、距离、P99 归一化锚点和近期变化度。阈值、权重、窗口和主／备牌统计范围沿用现行规范。通过身份合并导致的实际统计变化逐项解释；不能仅改一个 `deck_vector` 后假设其他入口自动一致。

使实际依赖的统计版本／生成指纹表达身份变化；不为统计迁移无故更改已确定的分类语义，也不靠刷新期望或摘要接受差异。

### B4 验证并同步允许更新的产物

- 正反例：同实体别名替换不变；同副牌两别名合并张数且出现率只计一次；不同实体不误合；分割牌及 SP//dr 等名字不误拆；基本地比较口径不变。
- 独立手算小样本验证均值、出现率、Core/Flex 和距离；真实样本核对 medoid、锚点与跨周影响，避免用新自动输出充当预期。
- 固定 A 的分类结果和成员集合，确认 B 的差异来自统计身份，而非再次调整类别或赛果。
- 只重建实际受影响且允许更新的当前统计／基准与消费者，保护已接受编辑内容及历史档案。确需历史重述时展示具体对象与影响，不能批量改写历史以求一致。
- 沿用现有检查和本地产物同步入口；保留 A 的证据和候选，不从分类采集重新开始。发布继续暂停。

B 实施未引入新的套牌归属判断，四赛制原始输入及现有分类结果保持不变。补齐写法兼容将共享身份契约升级为 1.1.0，分类摘要及派生绑定相应更新；不能把“结果未变”误写成“摘要未变”。后续真正未知的实体对应关系仍按具体问题取证，不扩成全局规则猜测。

### 已批准开发单元：日常采集与周维护生成解耦（本地实现与验证完成）

Owner 补充：每日新采集内容通常要在周维护确认分类器和分类后才进入前端，因此无需每天生成一套暂不消费的公开产物。行为分析暂缓实装。此前优先建设按赛制／生成器细分日更的建议被本节取代；不再先优化本来可取消的常规生成。

修改前核对：

- 公开统计通过 `publication.public_events` 和 `data_admissions` 取得明确接纳的赛事集合。新采集赛事不会仅因到达时间而自动公开。
- `.github/workflows/update.yml` 的定时链仍为 fetch → build → publish；全局输入无变化才跳过 build。有新原始输入时仍会调用公开统计、矩阵、完整度、八强、Landing 等生成入口。
- fetch 无仓库写权限，成功采集结果通过仅保留一天的临时附件交给 build；最终由 publish 把 `data`、`fetched.txt` 与 `stats`、`reports` 一起提交。直接关闭 build 会切断成功采集结果的现有持久化路径。
- weekly-readiness 的作业依赖和取用提交也接在 publish 之后；其新版本内部已具备从保留输入构建分类审阅材料的能力，但不能仅改 job 的 if 条件就假定所有旧依赖成立。
- 代码仍会在数据提交变化后请求自动 Pages 准备。已接纳赛事的赛果补录、缺失来源补齐等也可能影响既有公开产品。因此不把“主要是无效计算”夸大为“当前每天绝无前端变化”，本次没有查询线上运行记录来量化实际发生频率。

已批准目标：

1. 保留现有每日采集频率、来源校验、去重和重试；增加独立于公开生成的采集结果持久保存。限定写入实际采集输入及采集状态，不改分类接纳、公开统计或 Landing，不请求 Pages 准备。新记录尚未分类是正常待审状态，不应使成功采集丢失。
2. 待审周次、来源完整度等通知从保留输入和已有维护记录取得，不要求先更新公开产品。完整分类表、Unknown 及竞争诊断在周维护开始、有关输入／规则变化或明确诊断时按需准备；它们是审阅材料，不等同于公开统计。复用现有入口，不另建维护流程。
3. 周维护取得既有要求的完整分类确认及明确赛事接纳后，再生成相应统计、矩阵、完整度、八强等必要产物。复用现有阶段结果及独立发布验证；Landing 仍按已有内容验收单独处理，不因新数据获准就覆盖旧内容。
4. 保留手动修复／重建入口，不额外安排固定周几自动生成。建议已接纳赛事的补录输入也先保存，公开刷新交给周维护或明确修复任务；若存在必须每日刷新的真实消费者，先列出具体对象再决定保留必要小分支，不能默认把整套日更生成留作兜底。

验证重点：日常采集后新输入可靠保存而 `stats`／公开目录不变，不触发 Pages；失败重试不重复或丢失输入；待审通知和完整分类材料无需日更公开生成即可得到；同一已确认输入下，周维护生成结果与原流程相同；旧 Landing、未接纳赛事及其它赛制边界保持。必要的依赖粒度优化放在这条路径成立之后，有实际重复才继续。

Broodscale 3＋1、Sell-Sword／Otter 未确认色源配置按真实新样本维护，不把已确认范例插值为全局门槛；不扩展为全部父类重写。Legacy、新赛制产品、结构分类及相似度／机器学习替代仍不进入此次计划。
